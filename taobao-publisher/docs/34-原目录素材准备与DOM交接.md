# 原目录素材准备与 DOM 交接

2026-10-05。本会话按用户选择的“复用浏览器登录状态、先准备整批素材、再填写商品”建立交接层。用户已确认另一个开发会话正在同一工作区实现协议上传；本会话不继续修改该会话的请求发送与目录接口模块。

## 当前可验证的行为

以下均为 `verified（本地隔离）`，不表示真实淘宝已接受这些请求。

- `media_manifest.build_media_manifest` 递归记录商品根目录、子目录、原文件名、文件大小和 SHA-256。图片以外的资料文件不上传。不会把主图、SKU、详情目录压平，也不会给原图加 `tb_` 前缀。
- `snapshot_media_batch` 在任何上传前校验整批并创建临时快照；上传读取快照，采集原文件不变。源文件被修改、增删或目录改变时，旧清单失效。
- `prepare_media_batch` 按账户执行素材准备，只有全部商品返回完整回执后才正常返回；它本身不填写商品、不保存草稿、不提交。失败保留完整商品回执；`ProductMediaPreparationError` 另保留当前商品已确认的文件，不能将部分结果冒充 `PreparedProductMedia`。
- `PreparedProductMedia` 逐一核对账户、商品、相对路径、原名、目录和源文件摘要。`selection_plan` 使用真实 SKU 的 `image_path` 对应图片，不按图库显示顺序猜规格。
- `pipeline.run(..., prepared_media=..., account_profile=...)` 是 Python 内部交接参数。表单阶段进入实际商品目录，再按准确子目录、全名、完整图片地址和页码选图；拿不到对应文件时明确失败，不重新上传来掩盖定位错误。
- 主图回执按位置保存，消除“不同目录都叫同名.jpg”时，后一个文件覆盖前一个回执的问题。SKU 与详情沿用同一份已准备素材。
- 本地图片目录记录允许安全的原始文件名，不再只接受历史 `tb_` 名称。

## 修复的协议适配器衔接问题

初始 `upload_client.make_upload_product` 忽略 `prepare_media_batch` 传入的临时目录，从原文件读图；所有图片都发到一个商品目录，却在输出回执中拼出原子目录。这会形成不存在的远端路径。另外按文件名建立全局字典，无法区分主图与 SKU 的同名图片。

8 项反例先失败，修复后通过。当前适配器的约定是：

```python
folder_resolver(account_profile, (product_folder, *subdirectories)) -> folder_id
```

必须传完整路径，解析器返回实际目录 ID。不同路径返回相同 ID 时，在传图前停止。适配器从已验证的快照按目录分组上传；回执必须与本次目录 ID、文件名和数量一致。目录解析器本身的实际平台实现仍由协议会话负责，不能把此本地契约当成已建好淘宝目录。

## 尚未接通的部分

证据等级 `unknown（当前真实平台）` / `candidate（候选实现）`：

1. **默认桌面入口尚未调用 `prepare_media_batch`。** 当前 `_run_taobao_publish_task` 仍直接进入单件商品流水线；没有内部准备回执时，保留原 DOM 上传路线。因此本轮不能声称“点击开始上传已改为整批先传图片空间”。
2. 另一会话维护的 `upload_page`、`picturecenter` 为候选协议实现。当前浏览器会话下实际请求字段、目录创建与查询、响应结构、CORS、图片地址与 DOM 卡片地址的对应关系，须由允许访问的环境验证。
3. 本会话代码审查发现，`PageSession.read_tb_token` 把页面表单凭据返回 Python，再放进后续表达式；这与该模块“凭据不出浏览器”的说明不一致。**本会话未应用对这个并行编辑模块的修复**。建议请求发送会话把读取和使用留在同一个页面表达式中，只回传状态与去敏回执。此处没有读取任何真实凭据。
4. “所有图片先上传”的批次协调器、工作线程注入准备回执、失败回执持久化与恢复仍需接入。不要把准备回执开放为任意 HTTP JSON 或接受前端指定的图片 URL；它应由当前账户任务在内部生成。
5. 没有真实速度数据，不宣称协议上传已经提速。当前代码只消除了本地交接中的目录混淆和重复上传入口。

预期接线顺序：建立本批商品清单 → 调用账户绑定的素材准备端 → 保存每件商品完整/部分回执 → 全批准备完成 → 逐件调用现有流水线并传入 `prepared_media` → DOM 选图与必填回读 → 提交前停止。前端右侧无需新增平台专用配置区。

## 验证边界与协作

`test_prepared_media_manifest.py` 覆盖原名快照、账户/内容变化、取消与部分失败；用隔离浏览器运行真实主图/SKU/详情处理器。HTTP 工作线程模型通过内部注入准备回执验证交接，**没有证明默认工作线程已经生成了回执**。

`test_upload_product_bridge.py` 覆盖原目录与同名文件、快照变化、错误目录 ID、缺失/重复/改名回执、后续目录失败时保留前面文件。使用内存上传端，不访问淘宝。

对应验证记录为 `outputs/prepared_media_full_validation.json`。本轮与另一会话共享工作区，打包需要统一冻结源码后执行；没有把正在并行修改的候选上传模块当作已验证桌面版本交付。

本会话重新核对了最初 Browser Use 拒绝记录：它是站点安全策略拒绝读取发布类目页和商家身份页面，并禁止以原始 CDP、其它浏览器或插件取得相同被拒绝内容；不是用户未授权，也不是 Auto-review。此次只做源码、隔离页面和本地测试，没有通过协议适配器绕过该限制。
