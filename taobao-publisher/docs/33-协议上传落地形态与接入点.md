# 33 · 图片空间协议上传：落地形态与接入点

> 前置：[31 · 端点取证](31-图片空间协议上传端点取证.md)（接口长什么样）、
> [32 · 去重复用](32-图片空间去重复用.md)（云端已有图如何少传）。
> 本文讲**代码怎么组的、什么时候才允许上传、还差哪一步才算生效**。

## 0. 一条硬约束：只在淘宝上架时上传

用户明确要求：**日常采集不上传，只有走到淘宝上架才把图传进图片空间**，
避免图片空间被采集过程堆积。

代码里这条约束落在三处，任何一处不满足就**不会发出上传请求**：

| 位置 | 约束 | 违反时的行为 |
|---|---|---|
| `authorization.WriteAuthorization` | 必须有 `upload_image` 写授权 | `WriteNotAuthorizedError`，**在发出第一个请求之前** |
| `upload_client.make_upload_product` / `upload_page.PictureSpacePageUploader` | 上传入口只在「媒体准备」里被调用 | 采集链路没有引用它 |
| `scripts/probe-image-space-upload.py` | 命令行还要 `--i-understand-this-writes` | 直接退出，不发请求 |

采集侧（`/api/capture/*`、`src/utils.py` 的采集流程）**完全不引用**
`taobao_publish.upload_*` 任何一个模块——这是可以用 `grep` 验证的事实，
不是文档承诺。

## 1. 模块分工

| 模块 | 职责 | 关键点 |
|---|---|---|
| `upload_api.py` | 契约 + multipart 编码 + 响应分类 + 本地护栏 | 纯计算，不发请求；端点/字段/上限都来自 bundle 原文 |
| `upload_client.py` | 传输层可替换的客户端（HTTP 侧） | `CookieHttpTransport` 用调用方给的 cookie；**没有任何重试** |
| `upload_page.py` | 在**已登录页面**里发（cookie 不出浏览器） | `FormData` 由浏览器组，响应仍回 Python 分类 |
| `cdp_ws.py` | 极简 CDP（标准库 WebSocket） | 读 cookie、开临时页、`Runtime.evaluate` |
| `picturecenter.py` | 目录树 / 建目录 / 按目录查文件（mtop，`candidate`） | `dir.add` 返回的 `pictureCategoryId` 就是上传用的 `folderId` |
| `cloud_index.py` | 云端已有图 → 复用/上传/歧义 的判定 | 纯函数，不猜 |
| `scripts/probe-image-space-upload.py` | 实时取证 CLI（默认零写入） | `preflight` 不需要登录也能证明环境 |

## 2. 一次上传发生了什么

```
本地采集目录（只读）
  └─ media_manifest.build_media_manifest  →  文件清单（相对路径 + sha256 + size）
       └─ snapshot_media_batch             →  临时快照（上传前再校验一次，原图不动）
            └─ 云端已有图？cloud_index.index_cloud_media（读 mtop file.query）
                 ├─ reuse    → 直接用云端回执（**不重传**）
                 ├─ upload   → 走下面的协议上传
                 └─ ambiguous/blocked → 明确失败，交人工
                      └─ upload_api.UploadEndpoint.build_url()
                           POST https://stream-upload.taobao.com/api/upload.api
                                ?appkey=tu&folderId=<目录ID>&watermark=false
                                &picCompress=false&_input_charset=utf-8
                           multipart: file=<图片>、name=<文件名>
                           （浏览器路线由 FormData 组装）
                                └─ classify_upload_response
                                     ├─ 200 + success=true + object.url（CDN 白名单）→ 回执
                                     ├─ BAXIA_BLOCKED / 验证码文案 → **停手，不重试**
                                     └─ 其它 → 带平台原文的失败
```

**为什么逐张一个请求**：响应里的 `object` 只对应一个文件，多文件时哪张失败要靠
数组顺序对齐，而顺序没有契约保证。单张一请求换来「回执与本地文件一一对应」，
这是后面选图不出错的根基。

## 3. 与 DOM 路线的关系

现有 `page.upload_files_to_media`（点主图空位 → 素材中心 iframe → 塞
`input[type=file]` → 点「完成」落库）**保持不动**，协议路线是并存的一条：

| 维度 | DOM 路线 | 协议路线 |
|---|---|---|
| 前提 | 必须停在发布填写页，且素材中心弹层已打开 | 任意 `taobao.com` 页面（或已登录的 HTTP 会话） |
| 上传后拿到什么 | 文件名 + 图片空间 UI 里的卡片，需再查一次目录 | `object.url` + `pictureId`，当场可用 |
| 平台限流 | 队列里逐项 `error` 文案 | `BAXIA_BLOCKED`，同样停手不重试 |
| 落地证据 | 实测跑通（E-123 等） | **尚未实测**，见 §5 |

两条路线共用 `WriteAuthorization` 与「不绕过风控」的红线。

## 4. 已经离线验证到什么程度

`python -m pytest taobao-publisher/tests -q`：

* `tests/test_upload_api.py`（46 项）：端点 URL 形态、multipart 逐字节形态
  （**对面是真实 HTTP + 本仓库严格解析 multipart 的 mock 服务端**，
  校验字段名/文件名/Content-Type/分隔串闭合）、体积/格式/重名护栏、
  授权门在发请求前就拦、限流即停且保留已成功回执、10 种失败响应分类。
* `tests/test_picturecenter.py`（17 项）：mtop 请求的 api 名/入参/签名、
  目录树与文件清单解析、同名目录必须按完整路径定位、
  解析不出来的响应必须报出**实际键名**。
* `tests/test_protocol_media.py`（18 项）：素材路线开关（未设置=DOM、
  非法值报错不回退）、协议回执与本地身份对账（缺回执/非 https 必须失败）、
  页面身份核对（**同名不同 URL 必须失败，不许将就**）、
  整商品文件夹上传计划（多用途去重、缺主图/缺文件报错）。

**这些证明的是「我们发出去的东西符合契约 + 接线正确」，平台行为由真机验证覆盖（见 §5）。**

## 4.1 协议优先路线怎么开（整批传整个商品文件夹）

```powershell
# 默认仍是 DOM 路线（一行行为不变）
$env:TAOBAO_MEDIA_ROUTE = 'protocol'      # 打开协议优先
$env:TAOBAO_UPLOAD_ALLOW_WRITE = 'upload_image'
python -m taobao_publish ...              # 走发布流水线
```

打开后 `upload_images` 阶段的行为：

1. 按商品条目算出**整件商品的图片清单**（主图 + SKU + 详情，同一张图只传一次）；
2. 先按图片空间**已有的同名素材**复用（`find_product_images`，不重复上传）；
3. 缺的那些**一次 POST 进图片空间**（`folderId=0` = 根目录，与 DOM 路线的
   「上传至全部图片」是同一位置）；
4. 在页面上按**回执里的完整 URL** 逐张核对（`find_media_images`）——
   同名但地址不同就失败；
5. 选图、回读、后续阶段**完全复用原来的代码**（`page.select_media_image` 等）。

收尾语义与 DOM 路线一致：每张主图选入后都要回读位数与 URL 顺序，不一致就
`READBACK_MISMATCH`；**绝不把「传上去了」当成「主图设好了」**。

| 开关取值 | 行为 |
|---|---|
| 未设置 / `dom` | 原来的 DOM 文件输入框路线 |
| `protocol` | 协议上传 + DOM 选图 |
| 其它任何值 | **直接报错**（不回退）——静默回退会让人以为跑的是协议 |

## 5. 真机验证结果与仍缺的部分

### 已真机跑通（2026-10-05，E-212..E-214、E-216）

| 项 | 实测结果 |
|---|---|
| 上传 | 800×800 JPEG → `success:true`，回执 `object.url = https://img.alicdn.com/imgextra/i4/2214966481149/O1CN01…_!!2214966481149.jpg`、`pictureId`、`pix=800x800` |
| **整批上传（生产钩子）** | 真实商品目录 `ID-990093704786` 的 **4 张主图一次传完**，4/4 拿到地址与 `pictureId`；命名 `tb_<商品ID>_main_<槽位>_<sha前32>.jpg` |
| HTTP 形态 | `POST` + `multipart/form-data`，query `appkey=tu` / `folderId=0` / `watermark=false` / `picCompress=false` / `_input_charset=utf-8` |
| body 字段 | 只带 `water="false"` 就进业务；加 `name` 无影响；`file` 是文件字段 |
| `_tb_token_` | **必须真实**。假值（`x`）→ **404**（Tomcat 错误页）；真实值 → 业务响应 |
| 请求来源 | **必须与端点同源**。在 `item.upload.taobao.com` / `qn.taobao.com` 页面里发 → `TypeError: Failed to fetch`（跨源 CORS）；开在 `stream-upload.taobao.com` → 成功 |
| token 读取 | 从 **CDP** `Storage.getCookies` 读。页面脚本读 `document.cookie` 在素材中心页会抛 `SecurityError: Access is denied for this document` |
| 平台校验 | 真的校验内容：1×1 图 → `NOT_ALLOW_UPLOAD_1x1_IMAGE`；3 字节假 blob → `TYPE_NOT_CONFIRMED`。**失败也是 HTTP 200 + `success:false`** |
| 货架核对 | 上传后的图**确实出现在图片空间「全部图片」**里（按名字在素材中心页面上读到了） |

### 仍然缺的（`unknown`，不会用默认值糊过去）

| 项 | 现状 | 怎么才能升 `verified` |
|---|---|---|
| 超过 3MB 的图 | bundle 有 mtop 分片直传编排，本模块**未实现** | 需要真机拿 `uploadUrlList` |
| 上传频率 / 并发阈值 | 只有前端口径（`BAXIA_BLOCKED` 文案） | 需要可复现的频率实验；在此之前**不做自动重试** |
| 未签协议账号是否被拦 | 本次账号已签，没被拦 | 换未签账号试一次 |
| 商品专属目录的 `folderId` | 本次用根目录 `0` 成功；页面目录节点**不暴露内部 ID** | 用建目录（`dir.add`）或附件 DOM 线索 |

### 已证伪：不要再去拼 mtop 目录接口（E-215）

`mtop.taobao.picturecenter.console.dir.query` / `file.query` 的调用形态已从真实页面
逐参数取证（GET、`data` 在 query、`jsv=2.6.1`、`type=dataType=originaljsonp`、
`callback=mtopjsonp<N>`、**不带 `timeout`**、带 `ttid=<会员ID>@taobao_WEB_x.y.z`、
`dir.query` 的 `data` 是空对象），但**自己发四种形态（POST+body / GET+query / JSONP /
带真实 ttid）全部返回 `FAIL_SYS_ILLEGAL_ACCESS::非法请求`**，而同一 api 在浏览器里每次都成功。
结论：**目录树与文件清单继续走已经跑通的 DOM 路线**，协议上传不依赖它。
如果将来要再攻，方向是 appKey 权限（不是签名、不是参数）。

对应的 blocker 记在 [06-阻塞项](06-阻塞项.md)，证据日志见 E-207 及以后。
