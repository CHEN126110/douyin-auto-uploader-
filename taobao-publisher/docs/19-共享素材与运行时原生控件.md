# 共享素材与运行时原生控件

2026-10-05，继续按用户要求推进淘宝商品填写，保持共同前端，并停在提交前。本文区分代码已经支持的行为、本地模型证明和当前店铺尚未实测的部分。

## 本次解决的问题

此前主图和 SKU/详情使用不同的图片识别逻辑。后者额外依赖 `img.alt`，并将静态 `candidate` 标记视为必须停止的条件；即使已有相同素材卡片处理器，仍可能在图片阶段提前退出。详情还与属性填写绑在同一个阶段，不能单独显示进度或失败原因。

现在主图、SKU 和详情共用 `page.build_media_image_expression`。它在图片空间的可见卡片中匹配完整文件名，接受 CSS Module 类名后缀，排除上传队列、隐藏项和文件名前缀误匹配；回执必须包含唯一完整 HTTPS 图片地址。只有完整查找明确返回不存在，才允许首次上传，未知错误和搜索不完整不会转换为“需要上传”。选图前再次核对地址，选图后继续核对目标位置。原上传队列到达、点击完成落库的流程保留，队列文字不被当作已入库素材回执。

自定义规格和原生详情处理器不再因 `candidate` 标签一律提前结束。适配器只接受明确列出的原生控件，且各写入阶段必须声明 `runtime_selector_keys`。执行时交叉检查声明，再逐步验证当前 DOM 的所属区域、唯一性、类型、可用状态和原有内容，最后回读名称、数量、图片及顺序。`unknown`、`rejected`、缺失定位或没有对应处理器的控件仍会明确报错。

这些检查验证本次动作的前提，不会把静态平台证据改成 `verified`。`WRITE_ELIGIBLE_EVIDENCE`、协议字段映射和提交授权门没有被放宽。

## 执行顺序及边界

当前提交前流程有 11 个阶段：

连接浏览器 → 基础检查 → 选择类目和品牌并进入下一步 → 上传商品图片 → 标题与基础信息 → 类目属性 → SKU 名称及图片 → 商品详情 → 物流 → 价格库存 → 回读。

- 没有指定品牌时，继续使用用户指定的无品牌规则，保留实际选项原文。
- 自定义规格当前支持单个规格维度；完整名称不截断，也不把多维组合猜成单维。
- 已有规格表、抽屉内容或详情内容保留，不覆盖来源不明的编辑。
- 新增规格/图片按钮可能提交表单时不点击；超出当前输入框长度限制时不写入。
- 候选详情仅接受已定位的原生 `contenteditable`。普通 `textarea` 的 HTML 含义未知时不强行写图；iframe 和平台私有编辑器尚未实现。
- 详情的成功依赖已上传图片回执，并核对完整 URL 和输入顺序，不以图片总数代替对应关系。
- 图片入库、SKU 绑定、详情入位分别记录；素材上传成功不等于已完成整张商品表单。
- 用户本次选择的是提交前填写，程序不保存草稿或点击提交上架。

## 可重复的本地验证

`test_runtime_native_controls.py` 使用当前生产选择器契约，不给候选项提升等级。人工页面在新建隔离浏览器的 `file:` 中执行真实 DOM 表达式；真实保存函数、HTTP 工作线程和发布流水线串联。会话发现、平台导航和图片服务器由模型提供，不能据此声称实际淘宝可用。

该场景走完 11 阶段，模拟上传 5 张图、绑定 2 条 SKU 图片、写入 2 张详情图，最终没有草稿/提交调用。反例覆盖已有资料、普通文本编辑器、超长规格名、可能提交的按钮、未知契约和缺失运行时验证声明。

产物：[当前契约原生控件模型结果](../outputs/runtime_native_pipeline_handoff.json)。共同前端消费同一结果，仍提示整页必填尚未确认；生产必填读取器当前只覆盖 `visible_property_label_required`，`completePage=false`，不把模型全阶段成功报告成真实整页完成。

测试隔离也已加强：旧用例依赖提前返回避免默认浏览器查找，新逻辑放行后暴露了这项隐患。该用例改成纯契约验证，并为包内测试增加外网、应用端口和实际浏览器端口的连接拦截。后续浏览器模型使用临时端口及本地页面。
