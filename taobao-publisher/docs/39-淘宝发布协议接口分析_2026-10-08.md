## 1. 总体架构判断

淘宝发布页（`item.upload.taobao.com/sell/v2/publish.htm`）是 **schema 驱动的 ICMP 组件表单**：

1. 选类目 → 拉该类目的**组件树 schema**（139KB 的 JSON，描述每个字段的 uiType/必填/数据源）；
2. 前端按 schema 渲染表单，用户/自动化填写的是**组件状态**；
3. 保存/预览/提交时，把整棵树的状态**序列化成一个 jsonBody**（约 70 个顶层键）POST 回同域接口。

**主链路不走 mtop 网关**（没有 mtop 签名/token 难题），全是 `item.upload.taobao.com` 同域的
普通表单 POST，会话靠 cookie。mtop 只出现在**图片空间**（素材中心读接口）和详情装修等外围，
且是 GET JSONP（Script 标签）形式。

## 3. jsonBody 字段结构（核心交付）

### 3.1 保存草稿请求（本轮实证抓全）

```
POST /sell/draftOp/update.json?catId=201581801
Content-Type: application/x-www-form-urlencoded

id=1732803961
dbDraftId=1732803961
jsonBody={ …24704 字符的 JSON… }
globalExtendInfo={"startTraceId":"…","skuDecoupling":"true","noIcmp…":…}
```

`jsonBody` **70 个顶层键**，与 previewDraftSubmit（69 键）**68 键重合**——
草稿体仅多 `dbDraftId`、`draft-btn`。即：**预览和保存用的是同一份表单状态序列化**，
差别只在 scene 与草稿标识。这印证了"一份状态、多个出口"的架构判断。

### 3.2 关键字段实测形态（对应 field_mapping.json 的运行时证据）

| 字段 | 实测形态 | 说明 |
|---|---|---|
| `catProp` | `{"p-<pid>":{"value":<vid>,"text":…}}` 或多选数组 | 键带 `p-` 前缀；适用场景 `p-583353398` 多选为数组 `[{"value":39239143821,"text":"全天候穿戴"}]` |
| `sku` | 数组：`{skuPrice:"9.90", skuStock:100, props:[{name:"custom_-1", text:"奶白 / 均码", value:-468237067, img:"https://img.alicdn.com/…", pix:"1920x1920"}], salePropKey, skuStatus:1, …}` | 价格字符串（元）；props 带完整 CDN 图 URL |
| `customSaleProp` | `[{name:"custom_-1", uiType:"skuUniqueTitle", showUploadImage:true, maxPropItems:1, items:[…]}]` | 自定义销售属性，**uiType=skuUniqueTitle**（见 §3.3 标题之谜） |
| `price` / `quantity` | `9.9` / `"500"` | 一口价数值 + 总库存字符串 |
| `mainImagesGroup` | `{"images":[{url:"https://img.alicdn.com/imgextra/i2/…jpg", pix:"1920x1920", name:"主图_01.jpg"}]}` | 主图 = 素材中心 CDN URL 列表 |
| `tbExtractWay` | `{"template":{"value":"67793807680","orderedSFExpress":false},"value":["2"]}` | 运费模板 ID 为字符串 |
| `startTime` | `{"type":2,"shelfTime":null}` | 上架时间类型枚举 |
| `stuffStatus` | `{"value":5}` | 成色枚举 |
| `subStock` | `{"value":1}` | 库存计数方式 |
| `category.categorySelect` | `{id:201581801, name:"长筒袜", idpath:[1625,201566823,201581801], path:[…]}` | 类目三段路径 |
| `id` / `userId` / `catId` | `1088290423673` / `2214966481149` / `201581801` | **发布页打开时平台已预分配 itemId** |
| `croRule` | **字符串**（内嵌 JSON）：`{"url":"asyncOpt.htm?optType=croRuleAsyncCheck…","input":["id","userId","catId","title","desc","sku","price",…]}` | 校验规则描述符，非数据 |
| `auctionType` | `"b"`（一口价） | |
| 32 个空值键 | `fromLocal / snapshotId / saleProp / shopcat / *-card …` 为 `{}`/`null` | 卡片占位与未启用功能 |

### 3.3 标题之谜（重要发现，待实证）

- previewDraftSubmit（6 次）与 draftOp/update.json 的请求体里**都没有标题文本**——
  全层级无 `title` 键，全文检索无标题词。
- 但 croRule 的校验输入清单里**有** `title` 和 `shopping_title`。
- 同时自定义销售属性 `uiType="skuUniqueTitle"`。

两种解释（均待实证，倾向①）：
1. 该账号发布流启用了**智能/sku 唯一标题**：标题由平台基于「类目 + 属性 + SKU 文本」合成，
   表单态不携带标题；最终标题在提交时由服务端拼装。
2. 草稿/预览容忍缺标题，标题在正式提交时才随 `title`/`shopping_title` 字段上送。

对实现的意义：**协议化时不要试图在草稿体里找标题字段**；标题策略需单独实证
（在页面填标题后对比 jsonBody 差异即可定位，低成本）。

## 4. 草稿箱语义（本轮两个意外实证）

### 4.1 上限 10 条，满了保存会被对话框拦截

run54 的 `save_draft:ok` 是**误判**：草稿箱当时已满 10 条，点「保存草稿」后平台弹
`next-dialog-quick`：「草稿箱最大保存 10 条草稿，如果继续保存，请删除不用的草稿〔确定〕」，
**没有发出任何写请求、没有存下草稿**。当前 `stage_save_draft` 把「出现新对话框」一律当成功，
而这句是**拦截性**文案 → 后续代码修复方向：对话框文本分类（拦截类 vs 结果类），
命中「最大保存/删除不用的草稿」应判 blocked 并给出清理建议。（本次只记录，不改代码。）

### 4.2 「确定」= 授权平台自动删旧草稿

对话框点「确定」后，平台**自动连发** `POST /sell/draftOp/delete.json?dbDraftId=…`
清理旧草稿（观察到 3 连发 + `name=deleteDraft` 埋点），随后该类目草稿箱清零。
**账号里的历史草稿（10-03、10-08 的自动命名草稿）已被平台此流程删除**——
均为测试期自动草稿，删除动作是平台对话框流程的标准行为。

### 4.3 清空后保存成功，走 update.json

草稿箱清空后再点「保存草稿」：`POST /sell/draftOp/update.json` 200，
草稿列表出现 `草稿_2026-10-08 22:16:52`（id=1732803961）。
前端 bundle（29.js 草稿模块）同时定义 `add.json`/`update.json`/`draftList.json`
常量与 `edit/save/auto/click` 四种模式——**页面本身有自动保存草稿机制**，
历史草稿多为自动保存产物；有 dbDraftId 时走 update，否则走 add。

## 5. 协议化可行性评估

| 能力 | 可行性 | 依据 |
|---|---|---|
| 草稿保存/删除/列表 | **高** | 同域表单 POST，请求体结构已抓全；jsonBody 与页面态一一对应 |
| 类目树 / 类目属性 schema | **高** | asyncOpt 系列同域 GET/POST，响应即 ICMP 组件树 |
| 运费模板/规则校验查询 | **高** | 同上 |
| 预览渲染 | 中 | previewDraftSubmit 已实证，但响应 62KB 渲染模型需再解读 |
| 图片空间读（目录/文件） | **低（不建议）** | mtop JSONP + 已观察到 punish 风控路径 |
| 图片上传 | 维持 DOM/素材中心弹层路线 | 上传写接口未实证 + 风控考量 |
| 最终提交发布 | **不做** | 红线；且需 shopping_title 等字段的最后实证 |

**结论**：草稿层（保存/读取/校验/预览）具备完整的协议化条件，且与 DOM 路线共享同一份
jsonBody 状态模型——可以先做「DOM 填表 → 协议保存草稿/预检」的混合形态；
图片与提交维持现状。是否落地、何时落地，由后续任务决定。

## 6. 遗留问题清单（下一步实证的低成本路径）

1. **标题字段**：填标题前后 diff jsonBody，定位 title/shopping_title 的真实载体。
2. **提交端点**：只能靠「点到为止」的授权实验或文档证据补全，本轮不动。
3. **previewDraftSubmit 响应模型**：62KB 预览 JSON 的结构解读（对"提交前自检"有价值）。
4. **startTime.type 枚举表**：实测到 0（立即）/2，其余枚举待补。
5. **stage_save_draft 对话框分类修复**（代码改动，另行安排，见 §4.1）。
