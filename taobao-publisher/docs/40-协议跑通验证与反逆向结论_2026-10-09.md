# 40 - 协议跑通验证与反逆向结论（2026-10-09）

> 承接 `39-淘宝发布协议接口分析_2026-10-08.md`。本文记录**协议方法的实测跑通结果**：
> 用从浏览器导出的会话，在页面之外**自构造 HTTP 请求**逐级调用发布主链接口。
> 红线遵守：不真提交发布、不绕过验证码/风控；测试内容用真实商品数据，不带任何测试/逆向标记。
> 证据文件：`tmp/session.json`（会话快照，本地产物）、`tmp/proto-*.py`（实测脚本）、
> `tmp/draftOp-add-body.txt`（全量请求体）。

## 1. 反逆向机制排查结论（先于实测完成）

对 run52/run54 抓包的全部请求头、query、body 做特征扫描，结论：

| 机制 | 主链路（item.upload.taobao.com 同域） | mtop 图片空间 |
|---|---|---|
| 签名（sign/_m_h5_tk） | **无** | 有（mtop 标准签名） |
| CSRF 令牌 | `X-XSRF-TOKEN` 头，值 = `XSRF-TOKEN` cookie，**会话级固定值** | — |
| 安全 SDK 标记 | 仅 `bx-v: 2.5.37`（静态版本号，部分请求携带，缺它也能通） | bx-ua / bx-pp / bx-et 完整体系 |
| 风控惩罚 | **未观察到** | `_____tmd_____/punish` + x5secdata + 滑块验证码（run54 实证触发） |
| 必需条件 | cookie 会话 + XSRF 头 + Referer + UA + X-Requested-With | 高风险，不建议协议化 |

**主链路的协议门槛只有「有效会话 + XSRF 令牌」，没有签名算法需要逆向。**
x5sec/滑块那套只会在 mtop 图片空间这类高风险路径触发——我们的策略是**避开**（不协议化图片空间），
而不是对抗（红线：不破解验证码）。

### 社区逆向情报（用于预判，不用于对抗）

- x5sec 惩罚流程结构：punish HTML（`window._config_` + challenge）→ 加载 program.wasm/ET/NC
  → `_____tmd_____/slide` 提交 `slidedata + x5secdata + ppt`，请求头带 `bx-pp`（wasm PoW 签名）、
  `bx-et`（`window.etSign(url)`，异常时降级为固定串 `nosgn`）。
- `bx-ua` 以 `231!` 前缀为识别特征；x5sec 与 cookie/UA/设备指纹/行为轨迹强绑定，
  同会话高频请求是主要触发因子。
- 启示：**低频、单会话、避开 mtop** 是主链路协议化的安全边界；一旦出现 punish 响应，
  正确动作是停止并报告，而不是生成滑块数据。

## 2. 跑通实测记录（逐级）

### 2.1 只读冒烟 ✅

自构造请求（Python requests + 导出 cookie + XSRF 头）：

- `GET /sell/draftList.json?catId=201581801` → 200，返回真实草稿列表（与页面一致）
- `POST /sell/v2/asyncOpt.htm?optType=taobaoCatProp` → 200，返回 88KB 类目属性 ICMP schema

### 2.2 写操作·原样重放 ✅

`POST /sell/draftOp/update.json?catId=201581801`，表单 `id/dbDraftId/jsonBody/globalExtendInfo`
原样重放 → 200，草稿 `lastModify` 从 `2026-10-08 22:16:53` 变为 `2026-10-09 23:02:46`。
**服务端接受自构造请求并真实落库。**

### 2.3 写操作·字段级修改 ✅（端到端闭环）

- 第一次改 `quantity` 500→520：**未生效**——总库存由 SKU 库存派生，服务端以 sku 为准。
- 改 5 个 SKU 的 `skuStock` 100→101、`quantity`→505 → 200 success。
- 独立回读：在浏览器加载 `draft.htm?dbDraftId=1732803961`，页面渲染为
  **5 组 `9.90/101` + 总库存 505**——协议写入的数据经平台自己页面确认一致。

**至此「读 → 写 → 字段级写 → 独立回读」全链跑通。**

### 2.4 新建草稿 add.json ❌（载荷形态未实证，不阻塞）

两种载荷变体（去掉 dbDraftId / 带商品 id）均返回 HTML 错误页而非 JSON，未产生新草稿。
**不阻塞工作流**：发布页打开时平台即预分配 itemId 并建立草稿上下文（页面还有自动保存），
业务上「新建」由打开发布页完成，协议层只需 `update.json`。
若未来需要纯协议新建，需先抓一次真实 add.json 首存请求（当前证据不足，如实标注）。

### 2.5 观察到的附带行为

- 停留在发布页的 tab 会**周期性自动保存草稿**（草稿名每分钟级更新）——bundle 29.js 的
  `auto` 模式实证。协议写与页面自动保存基于同一份草稿 id，无冲突，但要意识到页面在线时
  草稿会被页面态覆盖：**协议写入前应确保页面不在编辑同一草稿，或先同步页面状态**。

## 3. 最终结论

| 能力 | 状态 |
|---|---|
| 读：草稿列表 / 类目属性 schema | ✅ 协议跑通 |
| 写：保存草稿（update.json，字段级） | ✅ 协议跑通，页面回读一致 |
| 新建草稿（add.json） | ❌ 载荷未实证（不阻塞，页面打开即建上下文） |
| 图片空间 | 不协议化（x5sec 风控实证），维持素材中心 DOM 路线 |
| 最终提交发布 | 不做（红线） |

**协议方法在「草稿层」已跑通**：cookie 会话 + XSRF 头即可调通主链路，无需逆向任何签名算法。
可落地的形态保持 39 号文档的判断：DOM 填表 → 协议保存草稿/预检的混合形态。
落地到代码是后续独立任务，本文档不含实现改动。
