# 28 · 上传后子目录定位与图片名称

2026-10-05，用户提供了新版的实际错误：上传队列已接收，但21张带`tb_`身份前缀的素材未找到；另以手动操作截图说明，必须进入商品父目录的「主图 / SKU / 详情页」子目录，才显示对应图片。本轮据这一新事实继续修复，E-196的受阻审查不再代表没有可推进的新输入。

## 证据与判断

- `verified` 用户反馈及视觉事实：[截图与出处](../captures/user_media_subdirectory_selection_20261005.json)。图中主图目录被选中，显示五张原始名称图片，排列顺序与编号顺序不同。
- `verified` 源码缺陷：`prepare_media` 上传后只把「全部图片」作为预期目录交给 `locate_uploaded_images`。后者仅查当前目录和该预期目录；二者相同时实际只查一处，旧错误却称“当前目录及商品用途目录”均未找到。
- `verified` 本地复现：模型将上传成功的图片保存在本商品三个用途子目录，根目录没有图片。修改前4项反例失败，其中21文件用例产生与用户同类的错误。
- `candidate` 卡片结构适配：图片背景、文件名及标题属性可以位于相邻节点。旧定位只读背景内文本，不能识别这种结构；截图支持研究这个方向，但不能证明真实DOM父子关系。当前适配只有在直接父容器恰好对应一张图和一个卡片时才允许使用旁边的名称。

用户说截图用于说明手动方法，因此不能把 `主图_01.jpg` 等原名当作程序上传的文件已被平台改名的证据。没有改为按图片顺序、相似名称或原始basename猜选；`tb_`完整名称及内容身份继续保留。

## 修改

1. 上传后的定位接收本商品名称和本批各用途的文件清单。先查当前/预期上传目录；尚未找到的文件再按用途进入本商品对应子目录，记录每张图的实际完整目录。
2. 后续每个主图位置、SKU图片和详情素材继续使用该目录及完整URL回执，避免停在父目录或上一个用途目录中查图。
3. 图片名称读取支持背景内文字、同一图片直接父容器中的可见相邻名称，以及完整title属性。选择控件仍限定在图片背景内；不从整个图库、隐藏相邻名称或其它图片借名字。
4. 错误改为列出实际查询过的目录，以及未能识别或进入的用途目录。没有查过子目录时不再声称已经查过。
5. 平铺图库全部找到时仍立即返回，保持一次上传和上传前后两次查询；本次没有增加自动重传。
