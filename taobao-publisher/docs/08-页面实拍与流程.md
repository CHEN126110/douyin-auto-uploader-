# 08 · 页面实拍与流程（2026-10-03 首次直接看到）

> 本文与 [01-平台入口与路线判断.md](01-平台入口与路线判断.md) 的区别很重要：
> **01 是文档推断，08 是实拍**。01 说「文档里写着有两条类目路径」，
> 08 说「我看到了它长什么样」。
>
> 证据等级：实拍画面 = `verified`（针对「有什么」），
> 但对「DOM 选择器 / 接口字段名」仍然是 `unknown`——**画面证明不了这些**。

## 1. 怎么看到的

用户日常 Chrome 里已经登录并打开了 `https://item.upload.taobao.com/sell/ai/category.htm`，
但这个 Chrome **没有开调试端口**，CDP 连不上（原因见 `05-证据日志.md` 的 E-025）。

试过的两条路：

| 尝试 | 结果 |
|---|---|
| UI Automation 读页面 | **失败**。Chrome 不向 UIA 暴露网页内容，只给出浏览器 UI 的 103 个元素；请求后等 25 秒数量不增长（E-027） |
| `PrintWindow` 截窗口画面 | **成功**。用 `PW_RENDERFULLCONTENT` 把窗口渲染到内存 DC，得到完整画面。已做成 `scripts/watch-publish-flow-visual.py` |

## 2. 看到了什么

### 外壳

页面跑在**千牛（Qianniu）工作台外壳**里：左上角是千牛 Logo +「商品发布」。
顶部有蓝色提示条：「亲，欢迎使用新版商品发布，点击查看使用教程」。

> 这条值得注意：**新版**商品发布。意味着旧教程/旧帖子里的页面结构可能已经不同，
> 不能照抄别人的选择器——这也正是本子项目坚持「先取证再实现」的原因之一。

### 类目选择页的主体：两张卡片

页面主体是**横向并排的两张卡片**：

| 卡片 | 内容 |
|---|---|
| **搜索发品**（左，主卡片） | 搜索框，placeholder 原文为「**可输入产品名称、类目关键词、条码信息**」；框内右侧有一个**相机图标**（即「以图发品」入口）；右侧蓝色「**搜索**」按钮 |
| **以图发品**（右，被窗口右边缘裁掉一部分） | 可见一个按钮 |

这**直接印证了 E-003**（官方文档说的「搜索发品」与「以图发品」两条路径）——
而且比文档更具体：**相机图标是嵌在搜索框内部的**，不是独立入口。

### 发布历史

搜索框下方有一行：「**发布历史：中筒袜 | 长筒袜**」。

这说明：① 该店铺此前发布过袜子类目；② 页面会记住用户最近用过的类目关键词，
点一下就能复用。对自动化是个提示——**这个区域会随账号状态变化，不能当作稳定锚点**。

## 3. 第二个页面：发布表单（选定类目后自动跳转）

### 跳转 URL（**这是本轮最有价值的一条实证**）

选完叶子类目后页面跳到：

```
https://item.upload.taobao.com/sell/v2/publish.htm
    ?catId=201581801
    &gpfRenderTrace=215045e017909573296543228e0dde
    &fromAICategory=true
    &keyProps=%7B%7D          ← URL 解码后是 {}
    &fromAIPublish=true
    &newRouter=1
    &paramCacheId=merge_route…
```

| 参数 | 含义（实测） | 用途 |
|---|---|---|
| **`catId`** | **叶子类目 ID 的本次样本** `201581801`（9 位数字，不代表所有 ID 的位数） | 已落成 `constants.PUBLISH_FORM_CATEGORY_PARAM` |
| `fromAICategory` / `fromAIPublish` | 这次是从「AI 发品 / 类目页」进来的 | 只作来源标记 |
| `keyProps` | 关键属性，开始为空 `{}` | 说明关键属性是**后续填的**，不是类目页带的 |
| `newRouter` | 新版路由开关 | — |
| `gpfRenderTrace` / `paramCacheId` | 渲染追踪 / 参数缓存 | 噪声，**不要**当稳定契约 |

**这条把 `item.category_id` 的证据强度推上来了**：本次叶子类目 ID 样本 `201581801` 为9位数字、
通过 URL 的 `catId` 传递。

但契约里它**仍然是 `candidate`，没有升 `verified`**，原因必须说清楚：

> `catId` 是**页面导航参数**，不是**提交体的字段名**。
> 契约门要求「`platform_field` 非 null 且证据 `verified`」才允许进真实写操作——**这是协议路线的门**；DOM 路线看的是写关键选择器。
> 把 `catId` 填进 `platform_field`（协议路线的字段），等于把导航参数当写字段用——那是错的。
> 所以这条证据记录在 `evidence.note` 里，`platform_field`（协议路线用）保持 `null`。

### 表单页结构

顶部四个 tab：**基础信息 | 销售信息 | 物流服务 | 图文描述**

左侧常驻「**填写助手**」帮助面板（内容随聚焦字段变化）。实测标题相关的原文：

> **填写要求**
> 1、1个中文按照2个字符计算，**最多允许输入字符数以标题填写栏右侧数字为准**
> 2、需重点突出商品核心卖点，语句简洁明了、通顺，内容遵循广告法要求
> 3、商品标题=商品描述+相关属性，需与商品当前类目、品牌、品名、重要属性（材质/功能/特征等）、销售规格一致
> 4、错误填写可能会引起流量减少甚至商品下架，请准确填写
> 5、标题直接影响商品的搜索曝光机会
> 6、标题和描述关键词是否违规自检工具：**商品合规工具**

→ **设计含义**：标题上限**不是固定 60**，而是显示在输入框右侧、**随类目变化**。
本次长筒袜画面已确认 30 个汉字 / 60 字符；该证据不能推广为所有类目的固定上限。
真实校验仍需读目标表单的计数规则。`rules.json` 的 `unknown_rules` 中旧状态文字尚待同步，
当前 `len(title)` 校验也尚未实现中文按2字符计数。

#### 基础信息 tab（属性区）

是一张「属性名 + 控件」的栅格，控件要么是「请选择」（下拉）要么是「请输入」。

**完整属性清单**（实测，类目：女士内衣/男士内衣/家居服 >> 短袜/打底袜/丝袜/美腿袜（新）>> 长筒袜）：

| 属性名 | 标记 | 控件 | 备注 |
|---|---|---|---|
| **材质成分** | 「重要」 | **上传吊牌图片** +「添加材质成分」 | 在属性区最上方；是图片控件，不是下拉 |
| **面料** | 「重要」 | 请选择 | |
| **上市年份季节** | `*` 必填 | 请选择 | |
| 编织工艺 | | 请选择 | |
| **吊牌价** | | 数字输入 +「元」 | placeholder 就是「数字」 |
| 防滑设计 | | 请选择 | |
| 风格 | | 请选择 | |
| 缝头工艺 | | 请选择 | |
| 厚薄 | | 请选择 | |
| 抗菌处理 | | 请选择 | |
| 款式细节 | | 请输入 | |
| 里料 | | 请选择 | |
| 是否商场同款 | | 请输入 | |
| 图案 | | 请选择 | |
| 袜口弹性材质 | | 请选择 | |
| 款号 | | 请输入 | |

下方折叠区：「展开 ⌄ 宝贝类型：全新 / 采购地 / 趋势标签」。

左侧「填写助手」在聚焦属性区时的说明原文：

> **商品属性**：商品属性是消费者了解商品、决策购买的重要依据。完整且准确地填写商品
> 信息，有利于商品在搜索和推荐中高效透出，帮助消费者精准定位目标商品，清晰了解商品的
> 优势以提升转化；错误填写可能面临商品流量损失或下架处罚。
>
> **温馨提示**：带「\*」为必填信息，右侧标注为该信息主要的应用场景。
>
> **应用示例**：面板里直接嵌了一张示例截图（标注了「筒长 / 风格 / 适用季节 / 裤型 / 适用性…」）

> **这就是 `item.props` 的真实形态**：属性名与控件类型由平台按类目下发，值必须从下拉里选。
> 印证了官方「属性必须动态映射、禁止硬编码 pid/vid」的要求。
>
> **对设计的含义（模型缺口）**：`PropEntry` 目前只能表达「属性名 → 属性值名」。实测显示
> 还需要表达三件事：① 是否必填（`*`）；② 控件类型（下拉 / 文本 / **图片上传**）；
> ③ **「重要」标记**（平台标注的权重，影响流量）。而且「材质成分」是**上传吊牌图片**
> 而不是选值——`PropEntry` **表达不了**。已记入待办。

#### 销售信息区（字段级实证）

| 字段 | 必填 | 控件 | 实测细节 |
|---|---|---|---|
| **销售规格** | — | 「+ 创建规格」按钮 | 提示「近期已升级SKU面板…」；**SKU 是「创建」出来的，不是预先存在的表** |
| **一口价** | ✅ `*` | 数字输入 + 「元」 | 下方动态提示原文：「**本类目常规价格最低是1.00元**，请规范标价行为」 |
| **总库存** | ✅ `*` | 数字输入 + 「件」 | UI 预填默认值 `1`；提示「总库存不包含新增批次库存 设置批次库存发货时效」 |
| **购买须知** | ❌ | 文本 | 计数器 `0/60` |
| **商家编码** | ❌ | 文本 | 计数器 `0/64` |

**两条重要结论**：

1. **「一口价」与「总库存」是独立于 SKU 的字段**——不是 SKU 行里的价格/库存。
   截图只确认它们是**商品级**独立字段；与 SKU 价格区间或库存汇总的关系没有在画面中证明。
   早先资料提到的区间约束仍为 `candidate`，需要当前表单或 schema 单独验证。
   → 影响 `mapping.py`：`sku.price` / `sku.stock` 之外，还需要表达
   「商品级一口价」与「商品级总库存」。目前 `PublishItem` 里**没有**这两个字段，
   这是设计缺口，已记入待办。
2. **价格下限是类目级的、平台实时下发的**（本条类目是 1.00 元）。
   不能在本仓库写死全局值；读不到时应作为 blocker 而不是用 `0.01` 放行。

其他可见元素：右上角「**批量导入**」入口；右侧浮层广告「SKU『批量生成神器』」
（批量秒级生成SKU / 自动对齐平台规范 / 解析回填更多参数）。

## 4. 这次收获对契约的影响

| 契约条目 | 之前 | 现在 | 说明 |
|---|---|---|---|
| `constants.PUBLISH_WORKBENCH_URL` | `verified` | `verified` | 画面确认 URL 无误 |
| 两条类目路径 | 文档推断 | **实拍确认** | 相机图标嵌在搜索框内 |
| **发布表单页 URL 与 `catId`** | **未知** | **`verified`** | 新增 `constants.PUBLISH_FORM_URL` / `PUBLISH_FORM_CATEGORY_PARAM` |
| `item.category_id` | `candidate` | **仍是 `candidate`**（证据变强） | `catId` 是导航参数，不是写字段名 |
| `item.props` | `candidate` | **仍是 `candidate`**（形态已知） | 知道是「属性名+控件」栅格，仍不知字段名与属性值来源接口 |
| `sku.price` / `sku.stock` | `candidate` | **仍是 `candidate`** | 商品级一口价/总库存已在画面中确认；SKU 行字段形态与提交体字段名仍未取证 |
| `selectors.json` 共19项，其中15项写关键 | `unknown` | **仍是 `unknown`** | 画面**推导不出** CSS 选择器 |

**发现的设计缺口（已记入待办）**：`PublishItem` 里没有「商品级一口价」与
「商品级总库存」这两个字段，而平台表单里它们是**独立的必填项**。
现在的模型只有 SKU 级价格/库存，映射不出这两项。

## 5. 后续两条路

| 目标 | 需要什么 |
|---|---|
| **理解流程**（本文档已完成大半） | 视觉观察器就够。走一遍即可 |
