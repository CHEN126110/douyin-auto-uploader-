## 1. 两个痛点的根因（逐行）

### 1.1 "必须先上传到图片空间再选图"——一半是平台约束，一半是认知

**平台侧（不可绕过，`verified`）**

* 发布页上**没有常驻的 `input[type=file]`**：实测 0 个；点「本地上传」之后 iframe 里才出现 1 个
  （`docs/05` E-101/E-104）。
* 图位只能通过**点图片空间卡片**填写：`media.image_card` 的契约写明"点它即选中并回填主图位，
  **不需要确认按钮**"（`contracts/selectors.json:381-391`）。
* 槽位身份**不在可写的 JS 状态里**：在 `window` 全部对象、React fiber/props、React 根上搜该图的
  `O1CN` 与 `pictureId`，**命中 0**（`docs/06:587`，E-226）。
* 代码里**不存在**"本地文件 → 表单隐藏字段/直传 URL"的通道（全仓库无此实现）。
* 平台自己的「本地上传」也是同一个顺序：**传到图片空间 → 再从库里挑**。

> 结论：**"先图片空间、再选图"是淘宝的物理顺序，不是本项目的设计缺陷。**
> 任何方案（包括官方工作台）都绕不过去。能优化的只有"谁来做、做多快、落到哪个目录"。

**工具侧（这才是真问题，`verified`）**

工具**没有**让用户手工预上传，两条路线都是自己读本地文件：

```python
# form_adapters.py:604-606  DOM 路线：把本地路径直接塞进上传框
result = page.upload_files_to_media(client, [entry['path'] for entry in batch],
    context_id=context_id, rename_to=list(pending), expected_sha256=[entry['sha256'] for entry in batch])
```
```python
# page.py:382-398  真正落到 CDP
payload = {"files": [str(p) for p in files], "objectId": remote}
self.send("DOM.setFileInputFiles", payload, timeout=timeout)
```

所以用户看到的"先传空间再选图"，是**工具在替用户执行这两步**——问题在于这两步的开销：

| 妥协点 | 位置 | 量级 |
|---|---|---|
| 弹层打开**固定等 3 秒**（E-265 证明不许改短） | `page.py:2928-2947` | 每张图 3s |
| 上传后必须点「完成」才落库，再回读 `landed` | `page.py:3256-3274` | — |
| 等上传队列逐项 success | `page.py:3101-3118` | `timeout=120` |
| 上传前整批复制临时目录 + sha256 复算 | `page.py:3144-3160` | 每批一次全量 IO |
| **按名字**找图要滚动遍历全库 | `page.py:3800-3816` | 327 张时 `search_incomplete`、5–13 秒 0 命中（E-222） |
| 每张主图重开/重关弹层 | `stages.py:2750-2767` | 张数 × 弹层开销 |
| 全量扫商品子树建索引 | `media_library.py:514-558` | 目录数 × 5s 上限 |

**这一节的正解**：不要试图"绕过图片空间"（做不到），而是让**上传走协议、选图按 ID、
目录按商品归档**，把"图片空间"这件事从用户视野里彻底拿掉。

### 1.2 "图片落在根目录"——默认路线被硬编码，能分目录的路线默认关闭

**根因链（四环，每环都有行号）**

**① 默认路线（DOM）的上传目标是被强制锁死的**，不是"碰巧"落根目录：

```python

if initial.get('value')=='全部图片': return initial     # 已经对了就直接返回
...
raise page.FieldMismatchError('上传目标未回读为全部图片，尚未发送文件')
```
调用点在 `page.py:3167-3168`（`ensure_all_images`）。**它只接受「全部图片」这一个值**，
回读不出该值就不发文件。DOM 上传接口本身也**没有目录参数**。

**② 协议路线是唯一能分目录的路线，但默认关闭**：

```python

raw = env.get(ENV_MEDIA_ROUTE)          # TAOBAO_MEDIA_ROUTE
if raw is None or str(raw).strip() == "":
    return ROUTE_DOM                     # 未设置 = DOM（保持既有行为）
```
```python

    return None                          # 钩子为 None → prepare_media 走 DOM 分支
```

**③ 桌面应用从来没设置过这个开关**：`tauri-app/python-sidecar/app.py` 全文无
`TAOBAO_MEDIA_ROUTE`；设置它的只有研究脚本（`scripts/run-live-publish.py:27`）。
→ **用户在界面上点多少次上传，走的都是 DOM → 根目录。**（`verified`，代码事实）

**④ 即使开了协议路线，目录也必须"预先存在"**：

```python

    client, item.record_name, folder_name, context_id=context_id)   # ← 没传 creator
```
```python
# media_library.py:156-163  creator 为 None 时直接抛错
raise PageError('图片空间里没有目录 {!r}／{!r}，而当前页面没有可用的建目录入口。'
    '请在**素材中心**（图片空间 → 素材中心）建好该目录后重试。')
```

## 3. 方案对比：哪种最快最稳

### 3.1 判据

一条上传方案要同时满足四件事才算"完整"：

1. **能落商品目录**（用户诉求）；
2. **快**（图片张数是量级大头）；
3. **稳**（不靠"翻遍全库找名字"这种概率性动作）；
4. **可续**（风控/中断后不整批重来）。

### 3.2 四个候选

| 方案 | 上传方式 | 目标目录 | 选图方式 | 实测/证据 | 判定 |
|---|---|---|---|---|---|
| **A. 纯 DOM**（现状默认） | 点「本地上传」→ `setFileInputFiles` → 等队列 → 点「完成」 | ❌ **强制「全部图片」根目录**（`upload_panel.py:52-73`） | 按名字滚动遍历（有 `pictureId` 时才按 ID） | 每张 3s 弹层 + 队列轮询；按名字在 327 张时 `search_incomplete`（E-222）。今天的探针想驱动「上传至」下拉改目录，两种取法都失败（`select_ambiguous` / `upload_to_label_missing`）——**即"DOM 路线改目录"没有可用入口**，而生产 DOM 路线本来就只认「全部图片」，默认值恰好满足 | ❌ 不满足 1 |
| **B. 纯协议（含 mtop 建目录）** | mtop `dir.add` + `upload.api` | 想分目录 | — | `dir.add`/`dir.query` 被网关拒（E-278，`rejected`）；上传本身真机可用 | ❌ 死路 |

### 3.3 为什么 C 最快（拆开算账）

**关键实测数据**

* `upload_images` 阶段：**127.2 秒 → 27.2 秒**（E-272）。
  拆开看更清楚：其中真正"上传"只占极小部分，**127 秒里绝大部分是"逐张选图、每张白等
  20–25 秒超时"**（根因是逐字比 URL —— 槽位回读是转码地址 `…_320x320q80_.webp`，
  与期望形态永远不等，E-264）。这说明：**DOM 路线的成本结构里，"等待与定位"远大于"传输"。**
* 协议路线把"等待与定位"换成两件确定的事：
  ① 上传当场拿到 `pictureId` + `object.url`（E-212）；
  ② 选图按 `pictureId` 一次命中（E-228），**不再遍历图库**（E-222 的 5–13 秒 0 命中直接消失）。
* 复跑更省，两级复用：
  ① **云端已有图复用**（按商品级文件名认出空间里已有的 5 张，直接复用不重传）——
     实测那一次**省了约 10 分钟**（`docs/05` 生产路径端到端验证节）；
  ② **上传回执账本**（身份 = 相对路径 + sha256 + **目录**）让本次已传过的直接复用，
     被风控打断后可**只补没传的**，不整批重来（E-220）。
* 目录建一次就幂等：`ensure_child_directory` 已存在直接返回 folderId（`media_library.py:218-246`）。

**结论**：C 的耗时 ≈ `建目录（一次，约 10 秒）` + `N × 1.2 秒限速` + `N × 选图（0.16–5 秒）`；
A 的耗时 ≈ `N ×（3 秒弹层 + 队列等待 + 遍历定位）`，且**张数越多差距越大**。

### 3.4 为什么 C 最稳

|---|---|---|
| 触发风控 | 队列逐项 `error` 文案 | ✅ 已知形态：`FAIL_SYS_USER_VALIDATE`+`RGV587_ERROR`，分类器判 `VERIFICATION_REQUIRED` 并**即停不重试**，附人工验证入口（E-217/E-220） |

```
① 采集 → 本地商品目录（ID-xxx/{主图,SKU,详情页}）+ 商品资料入库
② 用户在面板设：类目、标题/导购标题、价格、库存、备注、SKU 规格
③ 点「保存」→ 本地快照（已有，含版本指纹）
④ 点「上传商品」→ Sidecar 建任务 → pipeline.run_from_record
   ├─ session / precheck
   ├─ select_category        （类目 + 默认「无品牌」）           ✅ 已真机
   ├─ upload_images ★本轮核心
   │   1) media_manifest 扫本地目录（相对路径 + 名称 + sha256 + 角色）
   │   2) 账本 + 云端索引对账 → 已传且**目录一致**的直接复用（不重传）
   │   3) 缺图：ensure_cloud_folders 开一个素材中心标签，
   │      幂等建 全部图片/<商品名>/{主图,SKU,详情页}，
   │      从 li[value] 读三个 folderId（建完立刻关标签，不打扰表单）
   │   4) 按 folderId 分组，页面内 **XHR** POST upload.api
   │      （1.2s/张限速，逐张记账，风控即停）
   │   5) 回页面按回执 URL/pictureId 核对 → 主图逐位置、SKU 逐行、详情按序选入
   │   6) 回读主图位并按 O1CN 身份 + 顺序核对（不一致即 READBACK_MISMATCH）
   ├─ fill_base / fill_props / fill_required_attrs / fill_skus
   ├─ fill_detail / fill_freight / fill_price_stock
   ├─ set_listing_time        （默认「放入仓库」——最危险的「立刻上架」是平台默认值）

⑤ 前端展示进度与停点；「上传完成」≠「已上架」，两者分开显示
```

**用户视角**：设好资料 → 保存 → 点一次上传 → 图自动进 `图片空间/商品名/用途/` 并自动入位。
**用户不需要**预先手工传图，也不需要进图片空间点任何东西。

### 9.2 第三轮：把"判定不存在"这件事做扎实

第 3 条风险（虚拟列表让"读不到"≠"不存在"）光靠 fail-closed 还不够——
它会**误伤真实场景**：如果一个目录确实没有子目录，读不到就是读不到，
fail-closed 会把"本该建"变成"拒绝"。所以加了**有界等待**并把判据收紧：

| 机制 | 行为 |
|---|---|
| `ROLE_FOLDER_WAIT_SECONDS = 3.0` + `_wait_for_role_folder()` | 进目录后**轮询**角色目录；**一旦父目录渲染出任意子目录就立刻停止等待**（那一刻起"读不到"才等于"不存在"）；到上限还没渲染 → 交给 fail-closed 门 |
| 仍复用 `directory_folder_id` | 保留"同一路径命中多条即报错"的歧义守卫，不因为新逻辑把它绕过去 |
| 商品目录本身不存在时 | **不走这道门**（`product_path` 为假）→ "全新商品第一次上架"这条主路径不受影响 |

回归 **28 项全通过**；真机复核生产函数仍能解析出三个角色目录（`主图→…825689`、
`SKU→…796193`、`详情页→…530083`）。

### 9.9 第八轮：把那条陈旧断言修成不变量（它当时正遮住整段检查）

上一节记下这条断言时我以为它只是"报个假失败"。**实际更严重**：它抛的是未捕获异常，
**整个文件在 313 行中止**——后面约 50 行用例（取消、必填否决、原生范围校验……）**从来没执行过**。
一个让检查静默失效的断言，比一次假失败危险得多。

两处都改成"从源头推导"，而不是改数字：

| 原断言 | 新断言 | 为什么更强 |
|---|---|---|
| `result.steps.length === 11` | 从 `constants.py` 读 `STAGE_ORDER`，断言阶段名序列 **等于 STAGE_ORDER 去掉 `submit`** | 不只数量对：**名字与顺序**都对，且"停在提交前"这件事被显式钉住 |
| `every(step => step.status === 'ok')` | 除 **`save_draft`**（未请求保存草稿时**按设计** skipped，E-268/E-273）外都必须是 `ok` | 把"草稿是可选项"这条设计写进断言，而不是要求它必须执行 |

修后：`node frontend_publish_flow.cjs` → **`{"success": true, "total": 79}` / exit 0**
（此前从未执行的那批用例现在全跑且全过）。

**同一轮还打通了新字段的跨边界核对**：`notice` 一开始被 `check-ui-sidecar-fields.py`
判成"死字段"——因为检查器只认**顶层字面量键**，而我写的是条件展开
`...(x ? { notice } : {})`，对它不可见。修法**不是放宽检查器**（那会削弱它），
而是把前端写成检查器能看见的形式（`notice: …trim()`，空串表示"没有"）。
现在三边一致：`types 声明` = `界面会写` = `Sidecar 会读`，都含 `notice`。

> 方法论的第四条：**检查器看不见的写法，等于没写**。要么写成它能看见的形式，
> 要么改检查器——但改检查器一定是**加强**，不是放宽。
