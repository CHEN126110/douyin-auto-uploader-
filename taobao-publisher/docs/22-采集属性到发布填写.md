# 22 · 采集属性到发布填写

## 本轮根因

现有采集结果包含 `parameters`，但两个导入入口只保存标题和 SKU，没有将这些参数交给发布端。进一步检查源头发现：淘宝代码取的是 `res.params.trackParams`，1688 取的是 `tradeModel.offerIDatacenterSellInfo` 的标量项；这些数据没有商品参数来源证据，不能直接作为待发布商品属性。

本轮移除这两处错误投影。属性采集只读取可见、明确标为商品参数的结构化表格或 `dl`，以及旧商品参数列表。没有识别到时记录 `not_found`，关闭参数采集时记录 `disabled`；不根据标题推导季节、性别或材质。当前 DOM 适配属于 **candidate**，隔离模型证明其执行语义，尚未验证当前线上商品页覆盖率。

## 数据交接

`record.captured_attributes` 是新增的可空 JSON 文本字段。旧库通过幂等的新增列迁移保留原资料，旧记录默认没有采集属性。内容限定为版本、来源、状态、明确的名称和值；同名冲突、损坏 JSON、未知来源和状态不一致均报错，不从埋点或任意字典生成默认值。

单品导入和店铺批量导入都保存该字段，编辑商品时保留；商品版本指纹包含规范化后的属性，修改属性后不能继续使用旧上传版本。导入的删除/创建记录在一个 SQLite 事务内，创建失败会回滚原记录。此迁移不会给旧商品编造缺失参数；旧商品需要新的有效采集结果才会获得这些属性。

## 填写范围

自动匹配范围是 `上市年份季节 / 适用季节 / 适用年龄 / 适用性别 / 适用场景`。只有当前页面标为必填、字段名完全一致且唯一时才使用采集值。用户显式填写的属性优先，品牌继续使用已指定的无品牌选择流程；售价、库存、物流和销售规格不从采集参数覆盖。

支持原生文本、多行文本、原生下拉，以及现有可搜索属性下拉。原生下拉必须有唯一且可选的精确文字；属性下拉每步检查目标行仍然存在且唯一，禁用前缀匹配。填写后回读，最终核对时再次按同一属性读取，避免把选项 ID 与展示文字混用或漏掉后续重绘造成的值变化。

未知复合字段、近义名称、未匹配到的源字段不会被猜测转换。未采用的字段及原因进入阶段回执，缺失必填项仍由最终必填检查明确报告。这里没有建立材质百分比、资质文件或物流承诺的自动映射。

## 验证边界

- `tests/test_capture_attribute_storage.py` 使用独立 SQLite/Flask，验证两个导入入口、保存保留、版本绑定、迁移及写失败回滚。
- `tests/test_captured_attributes.py` 使用新建、禁外网的 headless 浏览器和本地合成页面，验证可见参数读取、名称/选项精确匹配、异常控件、来源冲突、品牌/显式值不覆盖、变更回读及真实本地 HTTP 线程流水线。
- [本地流水线回执](../outputs/captured_attribute_pipeline_handoff.json) 明确标记 `local_synthetic_browser_only`。平台会话、类目导航和上传服务器使用模型替身；没有对真实淘宝上传、保存草稿或提交。

本轮结果不能证明当前用户商品已经补齐属性，也不能证明真实淘宝所有必填项已填写完成。当前会话对淘宝商家后台的工具访问限制保持有效。


最终部署已完成。淘宝完整回归 1265 项、业务安全与存储 254 项、共同前端 79 组及类型/构建检查通过；23 个模块的冻结执行内容与源码一致，4 份契约和 68 个源文件清单核对通过。统一启动入口重启后，健康、运行文件哈希和单实例检查通过，运行库仅以只读表结构检查确认新增列存在。见[验证摘要](../outputs/desktop_capture_attributes_validation.json)。
