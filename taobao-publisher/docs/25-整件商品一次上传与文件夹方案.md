## 路线选择

| 路线 | 当前事实与开发状态 | 判断 |
|---|---|---|
| 独立图片空间拖入父文件夹 | 用户画面显示目录层级；隔离浏览器可完整枚举多层目录；尚未实现并验证真实素材页上传、重名合并和分页选择 | 适合单独整理素材，继续保留研究证据，不作为本轮默认入口 |
| 发布页一次备齐全部图片，再分用途选入 | 已接入现有桌面发布阶段；多文件输入支持时只触发一次文件选择；主图、SKU、详情共用上传回执 | 默认实现，少一次页面跳转，并保留现有共同前端 |

一次准备只包含该商品实际需要的主图、SKU 图和详情图，不把商品目录里的资料文件或未使用图片混入上传。新缺图平铺上传至「全部图片」，名称包含商品身份、用途、内容摘要及必要的主图位置；原始采集文件不改名、不覆盖。不同用途或不同主图位置保留各自身份，这不是按字节跨用途去重。

## 实现

1. 在 `form_adapters.prepare_media` 中验证全部本地图片，按用途查找已有缓存；已确认目录不存在只表示没有这份缓存，不伪造上传回执。
2. 对缺图在「全部图片」再做整批查询。已有明确名称、完整 URL 和目录回执的素材复用；其余文件合并成一个上传调用。
3. `upload_panel.ensure_all_images` 在发送文件前选择并回读「上传至全部图片」。原生 select 和受控 Fusion 候选均要求唯一、可用且回读一致；未知结构直接报具体错误。
4. 原生 multiple 输入一次发送全部缺图。只能接收单文件的输入仍按其实际能力发送，不把一次准备错误描述成底层只发生一次网络请求。
5. 队列限定到当前可见上传面板，忽略隐藏旧面板；逐文件成功后仍检查整批「上传中」状态。点击「完成」之前再次核对本批文件，缺失、重新加载和同名重复不会沿用早先的成功状态。
6. 「完成」只在唯一上传面板内点击。之后严格查询图片卡片及目录回执，主图逐位置选入，SKU 按完整规格绑定，详情按输入顺序使用相同素材回执。上传结果不等于商品已发布。

未知响应、平台拒绝、目录歧义仍明确报错，没有增加自动重传或用默认素材补齐的路径。共同前端布局与平台账户绑定方式没有改动。

## 文件夹技术研究

`verified` 的范围仅限浏览器能力。公开的 [CDP Input 协议](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Input.pdl)包含带文件路径的 DragData 和拖入事件；[MDN 的目录 Entry 说明](https://developer.mozilla.org/en-US/docs/Web/API/DataTransferItem/webkitGetAsEntry)要求反复读取目录直到返回空批，Chromium 单次读取可能最多返回 100 个条目。

隔离测试使用新建的无账户浏览器及只返回内存 HTML 的临时本地 HTTP 服务，向拖入目标提供合成目录 `123/主图`、`123/SKU`、`123/详情页`。105 张 SKU 加其它 4 张文件共 109 项，目录身份及所有相对路径全部一致。最初 `file:` 来源可接收目录却在枚举时出现 EncodingError，切换到自建 HTTP 来源后通过；该差异不是淘宝错误。[测试回执](../outputs/native_folder_drop_capability.json)。

目录拖入事件与普通 file input 的多个文件不是同一种数据结构。不能把父文件夹路径直接塞入普通多文件输入，并期待网站自动创建整棵目录。生产端的整文件夹入口仍未启用；隔离枚举成功不证明真实淘宝服务端完成了上传、合并或去重。
