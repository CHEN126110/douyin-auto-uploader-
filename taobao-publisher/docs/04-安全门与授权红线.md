# 04 · 安全门与授权红线

> 本文是 [`AGENTS.md`](../AGENTS.md) 第 1 条「默认零写入」的详细说明。
> 改动任何与写操作相关的代码前必须读完。

## 1. 两把锁

### 第 1 把锁：写操作白名单

```powershell
$env:TAOBAO_UPLOAD_ALLOW_WRITE = 'upload_image,save_draft'    # 逗号分隔
```

- **未设置或为空 → 零写入。**
- 只放行列出的操作。可以只开 `upload_image` 不开 `save_draft`，便于分阶段联调。
- **未识别的词元不会被当成授权**。`TAOBAO_UPLOAD_ALLOW_WRITE=1` / `=true` / `=all` /
  `=*` 一律**不授予任何权限**（有单测逐个覆盖）。想开就是老老实实写操作名。
- **非字符串值也不授权**（`1` / `True` / `["upload_image"]` / `b"..."`）。环境变量本来
  就只会是 str，出现别的类型说明调用方在造东西。
- 未识别的词元会被回报出来让人知道自己写错了，但**先过 `safe_token_label`**：
  只有**操作名形态**（小写字母开头的蛇形命名，如 `upload_image`、`uplod_image`）
  才原样显示。

> 判据原先是「普通标识符」`^[A-Za-z0-9_]{1,32}$`，对抗性审查（2026-10-02，F5）实测
> **32 位十六进制 mtop token**、`AKIA…`、去掉连字符的 `sk-` 密钥**全部命中**，
> 于是用户误写进这个变量的密钥会被原样写进 `run()` 的产物。现在收紧为操作名形态：
> 拼写错误仍然看得见，密钥形态一律隐去。

### 第 2 把锁：提交二次确认

```powershell
$env:TAOBAO_UPLOAD_ALLOW_SUBMIT = '1'    # 必须**精确**等于 "1"
```

- **只保护 `submit_publish`**（不可撤销的动作）。
- 提交需要**两把锁同时满足**：
  - 白名单里必须有 `submit_publish`；
  - 且 `TAOBAO_UPLOAD_ALLOW_SUBMIT` **精确**等于 `1`。
- 少任何一把都不行：
  - 只有第 1 把 → 抛 `SubmitNotAuthorizedError`；
  - 只有第 2 把 → 抛 `WriteNotAuthorizedError`（白名单里没有它）。
- **不做任何形态归一**：`"1 "` / `" 1"` / `"1\n"` / NBSP 或全角空格包裹的 `1` /
  数字 `1` —— **一律不解锁**。判据是 `isinstance(x, str) and x == "1"`。

> 早期版本用的是 `str(...).strip() == "1"`，对抗性审查（2026-10-02，F6）实测出上面
> 那一整排变体都能解锁。不可撤销的动作不该容忍任何形态上的含糊。

**为什么要两把锁**：单独一个环境变量不可能把不可撤销的提交打开。
误操作要同时踩中两个开关。

## 2. 授权从哪里读

研究与显式提交入口从环境变量读（`WriteAuthorization.from_environment`）。
主页面新增的“开始淘宝填写”由后端构造有限的一次性 `for_form_filling` 快照，
只允许图片上传和已登记的表单输入操作族，不授予提交或修改已发布商品。
`fill_only:true` 必须同时为 `dry_run:false`、`stop_before_submit:true`，否则拒绝。
它不会修改环境变量、不会点击保存草稿，也不会继承环境里的提交解锁。

请求不能传任意操作白名单或提交权限，`contracts/publish_item.schema.json` 的
`options` 也不能扩大授权。`fill_only` 表示固定的桌面填写动作，服务端决定精确
权限集合；旧真实提交入口仍需环境白名单与提交第二把锁。

### ⚠️ 界面上的「真实发布」开关**不是第三把锁**

`TaobaoPublishPanel.vue` 有个模式开关（`publishMode`），选「真实发布」时
请求里带 `dry_run: false` + `stop_before_submit: false`。

**它只是调用方的选择，不是授权。** 该旧真实提交入口的授权仍然只在环境变量里。
开着界面开关而没开环境变量，流水线会在写操作前停下
（请求里的 `dry_run` 与 Sidecar 的白名单**两道都要过**）。

所以真实发布要**三件事**：

1. 界面上选「真实发布」（每次还会弹确认框，写明发到哪个店、不可撤销）；
2. Sidecar 的 `TAOBAO_UPLOAD_ALLOW_WRITE` 含 `upload_image,save_draft`；
3. 提交还要 `TAOBAO_UPLOAD_ALLOW_SUBMIT=1`。

**1 在客户端，2/3 在服务端**——前两件都能被绕过，第 3 件不能。

`run()` 会校验 `authorization` 的类型。传入鸭子类型对象（`require()` 空实现、
`is_granted()` 恒 `True`）能架空整个授权门——对抗性审查（2026-10-02，F10）实测过
这种对象能让 9 个阶段全量执行，所以现在是硬性类型检查而不是靠自觉。

`from_grant()` 只用于测试与内嵌调用方，源码里明确标注了这一点。

## 3. 三道门是独立的

「有授权」不等于「能发布」。三道门必须**各自**通过：

```
门 1  授权门     写操作在白名单里？（提交还需第 2 把锁）
门 2  证据门     走哪条路线，就守哪条路线的证据门
门 3  数据门     标题/SKU/图片本身合法吗？
```

有单测专门证明门 2 独立于门 1：
`test_authorized_write_still_blocked_by_evidence` —— 即使把四把权限全开，
依然因为证据缺口被拦下。

### ⚠️ 门 2 分路线：**协议路线看 `platform_field`，DOM 路线看选择器**

这是**两条路线，两个门**，别混：

| 路线 | 门 2 的判据 | 现状 |
|---|---|---|
| **mtop 协议** | `field_mapping` 里每个字段 `verified` 且有 `evidence.source` | **不可用**（0 个 verified） |
| **DOM** | `contracts/selectors.json` 里**写关键选择器**全部 `verified` | **可用**（30/30） |

判据在 `contracts.write_route_status()`：

```python
"protocol_write_ready": contracts_ok and not field_blocked,      # 字段
"dom_write_ready":      contracts_ok and not selector_blocked,   # 选择器
```

**当前走 DOM 路线**，所以「字段映射 0 个 verified」**不构成发布阻塞**。
读 `readiness` 时别看错那一栏——`blocked_required_fields` 只关协议路线，
`dom_write_ready = True` 才是本次的门。

> 这条澄清是因为两处出口犯过同一个错：CLI 面板把协议路线的字段缺口印成
> 「真实发布前必须补齐」（第 41 轮修），就绪度的三个出口同样（第 42 轮修）。
> **文档这一处是第三处。**

### 原生候选控件的运行时验证

静态 `dom_write_ready` 不是所有扩展控件的实际填写证明。自定义规格和详情处理器现在对明确支持的原生控件执行条件验证：`StageHandlerSpec.runtime_selector_keys` 必须声明用途，动作前检查当前 DOM 的范围、类型、唯一性及原有内容，动作后核对完整值和图片。未声明、未知、已否定或没有对应处理器的控件仍拒绝执行，静态 candidate 不被自动提升为 verified。

此机制只适用于已实现的 DOM 控件处理器，不放宽协议字段证据、`WRITE_ELIGIBLE_EVIDENCE` 或提交授权。普通 textarea 不因可输入就被当作 HTML 编辑器。详见 [共享素材与运行时原生控件](19-共享素材与运行时原生控件.md)。

### 门 1 在**三个层次**上强制

不是只写在文档里的策略，代码里三道都拦：

| 层 | 位置 | 作用 |
|---|---|---|
| 1 | `stage_precheck` 预检**计划里的**写操作 | 在**动页面之前**就拦下（实测 14ms） |
| 2 | `run_stage` 在 `spec.run(ctx)` **之前** `authorization.require(operation)` | 处理器根本不会被执行，**一次点击都不会发生** |
| 3 | Sidecar 构造 `from_environment()` 或有限 `for_form_filling()` 快照 | 固定动作范围；填写快照没有提交权限 |

**第 2 层是关键**：它保证「被拒」发生在**动作之前**，不是之后
（第 49 轮踩过反面：拒绝写在包装层，而表达式已经点过了）。

### 这道锁**实机验证过**

`scripts/verify-submit-lock-holds.py` 发 `stop_before_submit=false`
（允许走到提交），而白名单里没有 `submit_publish`：

```
[OK]   连接调试浏览器   1516ms  CDP 就绪
[FAIL] 发布前置检查      14ms   前置检查未通过：1 条阻塞项

error.code = PREFLIGHT_BLOCKED
blockers   = ["SUBMIT_NOT_AUTHORIZED"]
detail: submit_publish 不在 TAOBAO_UPLOAD_ALLOW_WRITE 白名单内
        （当前白名单：save_draft,upload_image）
```

**拦在预检，页面一次都没碰。**

**门 2 的强制点有两处**（缺一不可）：

1. `FieldSpec.write_eligible` 要求三条**同时**成立：平台字段名是非空白的字符串、
   证据等级是 `verified`、**有 `evidence.source`**。把约束放进 `write_eligible`
   本身，字段才真的写不出去。
2. `build_platform_payload` 在 `validate_contracts` 返回非空时**直接返回空载荷**。

> （**协议路线**的强制点；DOM 路线的门看选择器，见第 3 节）
> （**协议路线**）早期版本的 `platform_field` 只做 `bool()` 判断（`"   "` / `123` / `["cid"]`
> 都算「有字段名」），而「标为 verified 但没有 source」只被打印、没人消费——
> 载荷照样产出，`describe_readiness` 还报 `publish_route_ready=True`。
> 对抗性审查（2026-10-02，F7/F8）实测出这两处，现已修复。

**门 3 里的一条额外约束**：页面的 DOM 事实（工作台是否渲染、是否有遮挡弹层）是
**三态**——`True` / `False` / `None`（未评估）。只读预检下 `None` 出告警，
真实写入前**升级为阻塞**。不能因为「还没测」就当「没问题」。

## 4. 脱敏

红线第 3 条：禁止把 cookie、token、`_m_h5_tk`、`_tb_token_`、`cookie2`、手机号、
店铺敏感信息、完整签名 URL、未脱敏请求头写进仓库、日志或产物。

`taobao_publish/sanitize.py` 是**唯一**允许把原始数据转成产物的地方。要点：

| 处理对象 | 行为 |
|---|---|
| cookie 串 | **保留名字、抹掉全部值**（研究需要知道哪些 cookie 存在，不需要值） |
| `_m_h5_tk` / `_tb_token_` / `cookie2` / `sgcookie` / `tfstk` / … | 整体抹值，且**不管键是 `_m_h5_tk=` 还是 `"_m_h5_tk":`** |
| 敏感请求头（Cookie / Set-Cookie / Authorization / X-Token / Referer） | **整段**抹值（`sanitize_headers` 与 `sanitize_payload` 两条路径一致） |
| URL 里的敏感 query 键 | 逐个抹值，参数名**先做百分号解码再比较** |
| URL 里出现签名类参数 | **整条 query 抹掉**（含 `%73ign=`、`sign%3D` 这类编码变形） |
| 手机号 | 抹掉。兼容 `+86` / `0086` / `86` 前缀、`-` 与空格分组、全角数字、数字型标量 |
| 邮箱 | 整体抹掉 |
| 递归结构 | 敏感键的值整体抹掉（**三份名单都查**），超深嵌套截断 |
| `bytes` 标量 | 解码后按文本脱敏（不能成为绕过通道） |

**签名 URL 为什么整条 query 抹掉**：`sign` 由 `_m_h5_tk` 令牌派生，泄漏
`sign` + `t` + `data` 等于交出去一次**可重放的请求**。所以只要出现签名类参数，
整个 query 都按敏感处理。

**幂等**：对已脱敏文本再跑一次结果不变（有单测）。多层调用不会产生叠加污染。
**不破坏 JSON**：脱敏后的产物仍然是合法 JSON，可以继续被解析。

**两道落盘守卫**：

| 守卫 | 用在哪 | 严格度 |
|---|---|---|
| `assert_clean()` | 普通产物（`outputs/`、`tmp/`） | 残留登录态即抛错 |
| `assert_capture_ready()` | **`captures/`**（要进仓库） | 更严：只要出现 `_m_h5_tk` / `Cookie` / `Authorization` 这类标记、且附近看不到脱敏占位符，就抛错 |

`python -m taobao_publish sanitize` 会根据输出路径**自动**选择守卫——写到
`captures/` 下就走严格的那道。

> 这条自动选择是补的一个真实缺口：`captures/`（进仓库）与 `tmp/`（原始产物）之间
> 原先只有 README 里的手工命令约束，没有任何自动校验。
> 对抗性审查（2026-10-02）用官方命令实测出四个真实泄漏，现已全部修复并加了
> 逐条回归测试（`AdversarialRegressionTest`）。

## 5. 原始产物与脱敏产物的边界

```
探针（Node）
  └─ 原始产物 → taobao-publisher/tmp/     ← 已 gitignore，绝不进仓库
       │
       └─ python -m taobao_publish sanitize <raw> <out>
            └─ 脱敏产物 → taobao-publisher/captures/   ← 可以进仓库（过严格守卫）
```

**探针本身也做了一层防护**：`probe-publish-workbench.mjs` 的页面内脚本
**刻意不读任何输入框的 `value`** —— 页面可能已经被卖家填过资料。它只采集
「页面上有什么控件」这类结构事实。

## 6. 三个「不做」

### 不做风控绕过

`cdp.probe_session` 与 `preflight.check_page_snapshot` 一命中风控标记
（`sec.taobao.com` / `punish` / `bixi.alicdn.com` / `captcha`）就**立刻停手**
并交人工处理。`mtop.classify_response` 对非 JSON 响应中的 baxia / x5sec 标记
返回 `RISK_CONTROL_HIT`。

**不做自动重试**——重试正是风控最敏感的触发模式。

### 不做登录绕过

登录态缺失（URL 命中 `login.taobao.com` 等）就是阻塞项，提示人工扫码。
`protocol-research-taobao-20260908/AGENTS.md` 已实证两条「复用现有登录态」的路
**都失败**，且明确写了「不要再重试」：

1. 冷复制 cookie 库失败（Chrome 127+ App-Bound Encryption → `v20` 前缀，
   实测 63 条淘宝 cookie 全部失效）。
2. 主 profile 开调试端口失败（Chrome 136+ 拒绝
   `DevTools remote debugging requires a non-default data directory.`）。

### 不做兜底

红线第 4 条。具体落到代码：

| 场景 | 处置 |
|---|---|
| 库存缺失 | 留 `None` → 阻塞项。**不默认 0 或 999** |
| 价格解析失败 | 留 `None` → 阻塞项。**不默认 0**（0 元会被平台当真价格） |
| `record.content` JSON 解析失败 | 抛 `ValueError`。**不返回空列表**（「解析失败」与「确实没有 SKU」必须区分） |
| 运费模板匹配不到 / 歧义 | 失败。**不返回默认模板 ID** |
| 字段无平台映射 | `EVIDENCE_INSUFFICIENT` 阻塞项。**不编默认值** |
| 契约自检有问题 | 拒绝组装平台载荷（**不是**只打印问题） |
| 缺 Pillow 无法校验图片尺寸 | 阻塞。**不静默跳过**（跳过会让「没检查」被误读成「检查通过」） |
| `_m_h5_tk` 形态非法 | 返回 `None`（fail closed），让调用方去刷新 token |
| 阶段未实现 | `NOT_IMPLEMENTED` 失败，**不静默跳过** |
| 阶段未登记 / 处理器声明与登记表不一致 | `CONTRACT_INVALID` 失败，**不执行处理器** |
| 页面 DOM 事实未评估 | 三态 `None`：只读预检下告警，真实写入前**升级为阻塞** |
| 请求体写了 `options.dry_run: false` | **无效**。请求体只能收紧不能放宽（见下） |

## 7. 端口守卫

| 端口 | 用途 |
|---|---|
| 9333 | 抖店 FXG CDP |
| 9334 | **淘宝 CDP** |
| 3300 | MCP Streamable HTTP |
| 5001 | Sidecar |

`cdp.assert_taobao_port()` 与两个 Node 探针都在**建立任何连接之前**校验端口。
连错实例会把抖店的登录态当成淘宝的用，属于必须中止的错误——所以是前置校验，
不是拿到结果再判断。有单测断言「端口校验先于任何网络调用」。

## 8. 请求体只能收紧

`run()` 的 `dry_run` / `stop_before_submit` 只可能被请求体里的 `options`
**往严的方向**改：

```python
if options.get("dry_run") is True:
    dry_run = True          # 收紧：把非 dry-run 拉回彩排
if options.get("dry_run") is False:
    pass                    # 放宽：无效，必须由调用方在代码里显式决定
```

理由：如果请求体能把彩排变成真实发布，那么任何能构造请求体的地方都是写入口。
