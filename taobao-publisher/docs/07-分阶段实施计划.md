# 07 · 分阶段实施计划

> 原则：**先取证，再实现**。每个阶段都有明确的退出条件（exit criteria），
> 达不到就不进下一阶段。不要为了「有进展」而跳步实现没有证据的阶段。

---

## 阶段 0 · 环境就绪（人工，约 10 分钟）

**动作**

```powershell
[Console]::OutputEncoding=[System.Text.Encoding]::UTF8
Set-Location <仓库根>

# 启动淘宝调试实例（独立 profile）
node protocol-research-taobao-20260908/scripts/start-taobao-cdp-chrome.mjs

# 验证可达且已登录
node protocol-research-taobao-20260908/scripts/check-taobao-cdp-environment.mjs
```

在打开的窗口里**扫码登录一次**，然后打开发布工作台：
`https://item.upload.taobao.com/sell/ai/category.htm`

**退出条件**

- `http://127.0.0.1:9334/json/list` 可达。
- 该 profile 内淘宝已登录（登录态随 profile 持久化，之后不用反复扫码）。

**已知会踩的坑（不要重试，见 R-001 / R-002）**

- 复制系统 Chrome 的 cookie 库 → App-Bound Encryption 让 `v20` cookie 全部失效。
- 在用户主 profile 上开调试端口 → Chrome 136+ 直接拒绝。

## 阶段 1 · 结构取证（只读，约 30 分钟）

**动作**

```powershell
# 窗口 A：勘察页面结构
node taobao-publisher/scripts/probe-publish-workbench.mjs

# 窗口 B：被动观察请求（你自己手动操作发布流程）
node taobao-publisher/scripts/capture-publish-requests.mjs --seconds 600
```

手动操作建议按这个顺序走，**每走一步停下来看看观察器输出了什么**：

1. 选类目（走「搜索发品」，顺手记下类目推荐接口）
2. 填标题
3. 填类目属性（观察拉取「必填属性 + 属性值列表」的接口 ← **最重要**）
4. 加销售属性（颜色 / 尺码）
5. 上传一张主图（观察图片上传接口 ← **第二重要**）
6. 填价格库存
7. 展开运费模板下拉（观察模板列表接口）
8. **不要点提交**。到「保存草稿」为止即可。

**退出条件**

- `tmp/` 下产出两个原始文件。
- 能回答：类目接口叫什么？属性列表接口叫什么？图传到哪、返回什么？
- 每个结论都有具体的请求作为出处。

## 阶段 2 · 证据回填（约 20 分钟）

**动作**

```powershell
# 脱敏（原始产物绝不进仓库）
python -m taobao_publish sanitize taobao-publisher/tmp/tb_workbench_probe_raw_XXX.json `
                                       taobao-publisher/captures/tb_workbench_probe_20261002.json
python -m taobao_publish sanitize taobao-publisher/tmp/tb_publish_requests_raw_XXX.json `
                                       taobao-publisher/captures/tb_publish_requests_20261002.json

# 契约自检（必须干净）
python -m pytest taobao-publisher/tests -q
```

然后手工编辑 `contracts/field_mapping.json` / `contracts/selectors.json`：

- （**协议路线**）把有证据的字段 `platform_field` 填上，`evidence.level` 升到 `verified`，
  **`evidence.source` 必须指向 `captures/` 里的具体产物**（自检会强制）。
- 把有证据的选择器填上，同样升 `verified`。
- 在 `docs/05-证据日志.md` 追加新的 E-xxx 条目。
- 证伪的东西追加 R-xxx 条目。

**退出条件**

- `python -m taobao_publish readiness` 里 `verified` 计数 **> 0**。
- 契约自检 0 问题。
- 每个 `verified` 都有可追溯来源。

**注意**：契约自检有一条守则——`selectors.json` 里填了 `selector` 但证据还是
`unknown` 会**直接报错**。这是防止「先把选择器抄进去，证据回头再补」，
那种做法迟早会变成「抄进去就忘了补」。

## 阶段 3 · 解锁第一个写阶段（约 30 分钟）

**先解锁哪个**：建议 `fill_base`（标题），理由：

- 只需 1 个字段（`item.title`）达标；
- 写操作是 `save_draft`，比 `submit` 安全；
- 能立刻验证「授权门 + 证据门 + 实际写入」这条链路是通的。

**动作**

1. 给 `STAGE_HANDLERS` 注册 `fill_base` 处理器（DOM 路线，用已取证的选择器）。
2. `contracts/field_mapping.json` 里把 `item.title` 升到 `verified`。
3. 跑授权下的真实写入：

```powershell
$env:TAOBAO_UPLOAD_ALLOW_WRITE = 'save_draft'
python -m taobao_publish dry-run --record-id 1 --sku-price 9.9 --sku-stock 100   # 先 dry-run
# 再按需跑非 dry-run（注意：这会真的写平台）
```

**退出条件**

- 非 dry-run 下 `fill_base` 阶段 `status = ok`；
- 未授权时该阶段 `status = failed` 且 `error_code = WRITE_NOT_AUTHORIZED`；
- 两条都有测试覆盖。

**同时必须做的**：给 `taobao_publish/stages.py` 加一条测试，
断言新注册的写阶段在 dry-run 下**必然被跳过**。

## 阶段 4 · 逐个解锁剩余阶段（B-02 ~ B-05）

推荐顺序（按风险从低到高）：

| 顺序 | 阶段 | 依赖的阻塞项 |
|---|---|---|
| 4.1 | `select_category` | B-02 |
| 4.2 | `fill_price_stock` | `sku.price` / `sku.stock` 取证 |
| 4.3 | `fill_freight` | B-04 |
| 4.4 | `fill_skus` / `fill_props` | B-02（属性值列表接口） |
| 4.5 | `upload_images` | B-03 |
| 4.6 | `readback` | 以上字段回读能力 |
| 4.7 | `submit` | B-05 + 两把锁验证 |

**每解锁一个阶段的固定动作**

1. 填契约（字段 + 选择器），升 `verified`，写 `evidence.source`。
2. 注册处理器。
3. 补单测：dry-run 跳过、未授权失败、证据门拦截。
4. 更新 `docs/05-证据日志.md` 与 `docs/06-阻塞项.md`。

## 阶段 5 · 接入 Sidecar 与前端（B-12）

前置条件：**至少 `upload_images` + `select_category` + `fill_base` + `fill_price_stock`
四个阶段跑通**。否则接上去也只能演示不能干活。

**动作**

1. `tauri-app/python-sidecar/app.py` 注入 `sys.path` 后导入（照 `app.py:7735` 的写法）。
2. 新增 `/api/taobao/*` 路由：
   - `GET /api/taobao/readiness` —— 直接映射 `describe_readiness()`
   - `POST /api/taobao/publish/start` —— 启动异步任务
   - `GET /api/taobao/publish/status/<task_id>` —— 进度轮询
3. 同步改 `tauri-app/src/services/api.ts`、`types/index.ts`、Pinia store、Vue 视图。
4. 前端进度条**直接复用** `UploadStepInfo` / `UploadTaskSummary`（进度契约已对齐）。
5. 打包：把 `taobao-publisher/` 加进 `build_sidecar.py` 与 `python-backend.spec`，
   **真跑一次** `python build_sidecar.py` 并用 `CArchiveReader` 核对归档条目。

## 阶段 6 · 端到端验收

**必须全部满足才叫「可用」**：

1. `python -m pytest taobao-publisher/tests -q` 全绿。
2. `python -m pytest tests -q`（仓库全量）不因本次改动变红。
3. `python -m taobao_publish readiness` 显示 `是否存在可用发布路线：是`。
4. 未设 `TAOBAO_UPLOAD_ALLOW_WRITE` 时，跑非 dry-run **必然**在第一个写阶段失败，
   且**平台侧无任何变化**（用卖家后台核对）。
5. 设了写白名单但未设 `TAOBAO_UPLOAD_ALLOW_SUBMIT=1` 时，`submit` 必然失败。
6. 真实发布一件商品到「放入仓库」，人工核对类目 / 标题 / 属性 / SKU / 价格 /
   库存 / 运费模板 / 图片**逐项正确**。
7. `captures/` 与 `outputs/` 里的产物全部通过 `assert_clean`（无残留登录态）。

## 不建议做的事

| 做法 | 为什么不做 |
|---|---|
| 先写 9 个阶段的空壳处理器「占位」 | 会让人以为流水线跑完了。当前 `NOT_IMPLEMENTED` 显式失败是**特性**不是缺陷 |
| 用「猜的选择器 + 失败重试」把 DOM 路线跑通 | 猜错的选择器会写到错误的字段上，比失败危险得多 |
| 为了跑通而把契约门从 `verified` 放宽到 `candidate` | 那等于取消整个证据体系。契约门的价值就在于它现在拦着你 |
| 自动重试风控 / 签名失败 | 重试正是风控最敏感的触发模式 |
| 往代码里塞一份「管控类目资质清单」的猜测版本 | 会让人以为已经被检查过了 |
| 复用抖店的字段名或选择器 | 两套互不相通的体系，见 `AGENTS.md` §0 |
