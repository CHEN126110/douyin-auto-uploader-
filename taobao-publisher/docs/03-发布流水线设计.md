# 03 · 发布流水线设计

## 1. 阶段划分

与抖店 v4（`fxg_protocol_v4.py` 的 `run()`）同构，但阶段内容按淘宝重写。

## 2. 三条嵌进执行顺序的安全设计

### 2.1 静态预检先于一切（连浏览器都不连）

```
run()
 ├─ 0. build_publish_item()          ← 数据不全就到此为止
 ├─ 1. run_static_preflight()        ← 标题/SKU/图片/契约证据
 │      ↑ 有阻塞项 → 直接返回，session_probe 一次都不会被调用
 └─ 2. 按阶段执行
```

有单测专门守这条：`test_invalid_data_stops_before_touching_cdp` 断言
会话探测器调用次数为 **0**。

理由很实际：数据本身有问题时，连上浏览器只会多暴露一次登录态、多跑一轮页面加载，
而且会让报错变得更难查。抖店 v4 也是这么做的（`fxg_protocol_v4.py:1577-1591`）。

### 2.2 写阶段在授权门后面

`run_stage()` 的顺序即安全设计：

```
1. 写阶段 + dry_run        → 跳过（skipped），绝不触碰平台
2. 写阶段 + 未授权          → 失败（WRITE_NOT_AUTHORIZED），不执行
3. 无处理器                → 未实现（NOT_IMPLEMENTED），不静默跳过
4. 执行处理器
```

第 2 步走的是**结构化失败**而不是抛异常给调用方：`run()` 的契约是*总是*返回可展示
的结果。安全性不受影响——`WriteAuthorization.require()` 在**任何平台调用之前**
就抛了，执行器只是把异常转成前端能显示的错误码。

### 2.3 未实现的阶段显式失败

`STAGE_HANDLERS` 只注册了 `session` 与 `precheck`。其余 9 个阶段没有处理器 →
`NOT_IMPLEMENTED` 失败，**并且带上阻挡它的证据缺口**：

```
[NOT_IMPLEMENTED] 该阶段尚未实现 — 阶段「选择商品类目」尚未实现；前置证据缺口：item.category_id
```

这是刻意的：让流水线「跑完」但什么都没做，比让它明确停下危险得多。
有单测守着「`STAGE_HANDLERS` 里只能有只读阶段」。

## 3. 进度上报

回调签名与抖店 v4 **完全一致**，因此前端 `UploadStepInfo` / `UploadTaskSummary`
类型可以零改动复用：

```python
progress_callback(pct: int, msg: str, step_name: str, steps: list[dict])
```

`steps[]` 元素形状也一致：

```json
{"name": "precheck", "label": "发布前置检查", "status": "ok", "elapsed_ms": 3, "summary": "..."}
```

- `status ∈ {running, ok, failed, skipped}`
- 进度百分比用固定锚点 `STAGE_PCTS = (5, 12, 30, 40, 52, 64, 74, 82, 88, 94, 100)`，
  阶段数对不上时线性插值兜底。
- **回调抛异常不会打断流水线**：前端渲染问题不该毁掉发布流程（有单测覆盖）。

## 4. 返回值

```python
PipelineResult(
    success: bool,
    stage: str,               # 停在哪一步
    error: dict,              # {code, message, stage_label}
    steps: list[StepRecord],
    blockers: list[dict],
    dry_run: bool,
    stopped_before_submit: bool,
    data: dict,               # item_summary / readiness / authorization / step_plan / ...
)
```

### `stopped_before_submit` 的语义

它由「`submit` 阶段是否真的执行成功过」**反推**，不是回显入参：

```python
stopped_before_submit = not any(
    run.name == "submit" and run.outcome.ok and not run.skipped_for_dry_run
    for run in runs
)
```

原因：dry-run 下即使调用方传了 `stop_before_submit=False`，提交阶段也只是被跳过。
此时报「未截停」会让人以为提交发生过。**这个字段的名誉比它的字面意思重要。**

### 无论在哪一步失败，都给 `readiness`

调用方永远能看到整体就绪度，不用去猜「到底是数据问题还是代码没写」。

## 5. 错误体系

两层，照搬抖店 v4 的分层但字段体系独立：

1. **错误目录**（`errors.py` 的 `ERROR_CATALOG`）：每个错误码固定携带
   `(category, message, hint)`。前端与测试**只依赖错误码，不依赖中文文案**。
2. **阻塞项**（`Blocker`）：`code / field / detail / severity / evidence / source`，
   可去重（按 `code+field+detail`）。`severity ∈ {blocker, warning}`。

`warning` 的存在是必要的：不是所有异常都该阻止发布。典型例子是
「SKU 数量超过 40 条」——该阈值来自第三方实测帖、未经本仓库复核，
所以只告警并提示需要走虚拟滚动路径（`tests/test_mapping.py` 断言它**不能**是 blocker）。

## 6. 与抖店 v4 的差异（哪些不能照搬）

| 抖店 v4 的做法 | 淘宝侧的处置 | 原因 |
|---|---|---|
| 直接建 WebSocket 干活 | `session` 阶段只读 `/json/list` | 淘宝发布页 DOM 结构一条都没实证，贸然连接没有意义 |
| webpack 注入拿内部模块（`req(90665).bE`） | **无对应物** | 抖店专有；淘宝官方 API 已关闭，只剩 mtop 与 DOM 两条路 |
| 硬编码类目 `cp_id`（2752/3939/…） | **禁止** | 官方明确要求类目属性动态映射；且本地 `clazz` 不是平台类目 ID |
| 运费模板名称三级匹配（exact/contains/tokens） | 收紧为「精确唯一命中」或「包含唯一命中」，歧义即失败 | 抖店曾因猜模板发错店铺 |
| `n_token` 由页内现拼 | 不做对应设计 | 淘宝用 `_m_h5_tk` + MD5 签名，算法已实证 |
| 双路径降级（React 注入 ↔ 离线 body） | 设计上保留「mtop 协议 ↔ DOM」双路线 | 两条都未取证，但现在就把接口留出来 |
| `stop_before_submit` 截停点 | 保留，语义改为「提交阶段是否成功执行过」 | 见上文 §4 |
