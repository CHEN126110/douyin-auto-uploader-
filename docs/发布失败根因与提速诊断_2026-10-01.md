## 3. R1 · 价格库存填不进去（17 次，占失败 44%）—— 已定位到确切根因

### 3.1 现象

错误文本统一形如：

```
价格库存滚动未推进，剩余SKU未填写：榛子蝴蝶结 / 36-40、灰紫格纹 / 36-40、塞纳灰格纹 / 36-40…
｜页面当前可见行：塞纳灰格纹+均码、雾凇格纹+均码、雾凇小花+均码、…
```

注意这条日志本身自相矛盾：**`塞纳灰格纹`、`雾凇格纹`、`雾凇小花` 同时出现在"未填写"和"可见行"两边**。
说明不是"行没渲染出来"，而是**行渲染出来了，但匹配函数认不出它**。

### 3.2 根因：两张词汇表对不上

`_fill_price_stock_and_delivery`（`app.py:6442`）用 `_row_matches()` 把
**数据库里的 SKU 名**（`record.content` 的 JSON）和**页面表格行的规格单元格文本**做匹配：

```python
def _split_sku_name(value):                      # app.py:6461
    parts = re.split(r'\s+/\s+', text)           # ← 只认 " / " 这一种分隔符
    if len(parts) >= 2:
        return ' / '.join(parts[:-1]), parts[-1] # 最后一段当成"尺码"

def _row_matches(row_name, row_size, sku_name):  # app.py:6507
    expected_name, expected_size = _split_sku_name(sku_name)
    ...
    if expected_size and row_size and expected_size != row_size:
        return False                             # ← 尺码不等就否决
```

而页面上真实的规格值**不是**从数据库名字来的 —— 是工具自己写死的：

```python
def _configure_sku_structure(main_tab):          # app.py:6363
    print('选择均码')                             # ← 尺码轴永远只选「均码」
```

于是当源平台的 SKU 名带着真实尺码（`36-40`）时，
匹配函数拿 `36-40` 去比页面的 `均码`，**必然判不等**。

### 3.3 三种必失败形态（用真实代码逻辑复现，8/8 命中）

复现脚本逐字复制 `app.py:6449-6515` 的五个函数执行：

| 形态 | 页面行(名称,尺码) | sku_list 里的 name | 结果 |
|---|---|---|---|
| A 源尺码≠均码 | (`塞纳灰格纹`, `均码`) | `塞纳灰格纹 / 36-40` | ❌ 尺码不等 |
| B 多名用 `+` 连接 | (`S2636组合E`, `均码`) | `S2636组合E+均码` | ❌ 名字集合无交集 |
| C 多规格 `/` 直连 | (`男袜高橡筋款`, `均码`) | `男袜高橡筋款 / 均码/长绒棉/抗起球/独立包装` | ❌ 整串被当尺码 |
| 对照：源尺码就是均码 | (`卡其`, `均码`) | `卡其 / 均码` | ✅ 匹配 |

`+` 的来源也查清了 —— 文件夹模式导入时把文件名里的 `-` 换成了 `+`：

```python
def _derive_sku_name(...):                       # app.py:8232
    candidate = (rest or file_name).replace('-', '+').strip()   # ← app.py:8242
```

所以**数据库里同时存在 `" / "` 和 `"+"` 两种 SKU 名格式**，而匹配函数只懂第一种。

### 3.4 截图实证：规格值就是"完整 SKU 名"

sidecar 在失败时会自动落盘现场快照（`%LOCALAPPDATA%\com.dyin.sock-publisher\output\browser-debug\upload_error_*\`，
含 PNG 截图 + 全页 HTML + 报告 JSON）。`ID-1078276270149` 那 5 次失败留下了完整现场：

截图（`20261001_154018_883395_error_fill_price_and_stock.png`）右侧「消费者效果预览 → 商品规格 → 颜色分类」显示：

```
榛子蝴蝶结 / 36-40      灰紫格纹 / 36-40      塞纳灰格纹 / 36-40
雾凇格纹 / 36-40        雾凇小花 / 36-40      塞纳灰条纹 / 36-40
塞纳灰碎花 / 36-40      奶油草莓 / 36-40      燕麦小梅果 / 36-40
燕麦紫碎花 / 36-40      雾凇蝴蝶结 / 36-40
```

左侧「商品规格」区则显示：颜色分类 12 个规格值、**码数 = 均码**。

**结论得到视觉确证**：颜色分类的规格值就是数据库里的完整 SKU 名（含 ` / 36-40`），
码数轴由工具写死为 `均码`。所以价格库存表格行被解析成
`(row_name='塞纳灰格纹', row_size='均码')`（`/ 36-40` 被 `_split_sku_name` 当尺码吃掉、
又被第二列的 `均码` 覆盖），而匹配时 `expected_size='36-40'` ≠ `row_size='均码'` → **否决**。

报告 JSON 还显示失败瞬间 `page.scroll = {x:0, y:0}`，
与"滚到底→回滚到顶→仍匹配不上→抛错"的路径一致；
traceback 精确落在 `app.py:6828`，与代码走查完全吻合。

### 3.5 为什么表现为"滚动未推进"

匹配不上的行永远进不了 `pending_indexes` 的消解集合，
循环只能一路往下滚，滚到底 → 回滚重扫 2 次 → 仍然匹配不上 → `raise`。
日志里"页面当前可见行"回到顶部第一屏，正是回滚后的现场。
**报错信息把「匹配失败」误报成了「滚动失败」，把排查方向带偏了。**

### 3.6 一处需要补埋点才能定论（诚实标注）

形态 A 与 C 已由截图 + 代码逐字复现双重确证，**否决点唯一是尺码守卫**。

但**形态 B（`+` 分隔）存疑**：按 `_row_matches` 推演，
`_split_sku_name('S2636组合E+均码')` 返回 `('S2636组合E+均码', '')`、
`expected_size` 为空串会跳过尺码校验，**理论上应当匹配成功**。
它却出现在"未填写"名单里 —— 说明那一批的失败另有原因
（`_refresh_row` 按 `data-row-key` 重定位失败、或 `_input_in_row` 每轮拿不到输入框而
`continue`，都会让 pending 永不清空，但**不会**被这条错误信息区分出来）。

**这也是"报错文案把两类问题混为一谈"的直接后果**：
只看错误文本无法判断是"匹配失败"还是"输入框定位失败"。
建议修复时一并补埋点（见 §8.3 的做法）。

### 3.7 修法（建议）

1. **统一分词**：`_split_sku_name` 改为按 `" / "`、`"+"`、`"/"`、`、` 任意分隔符切分，
   返回 token 列表而不是「名称 + 尺码」两段。
2. **匹配判据改为集合包含**：行的规格 token 集合 ⊆ SKU 的 token 集合即算命中
   （行 ⊂ SKU，保证不会把 A 款填成 B 款）。
3. **尺码不再作为否决条件**：工具自己写死「均码」，所以页面的尺码 token 不具区分度；
   应改为"若尺码 token 出现在 SKU 名里就算一致，否则忽略"，而不是直接否决。
4. **加歧义护栏**：若一行同时被 ≥2 个未填 SKU 命中，不要随便挑一个 ——
   记录冲突并走位置兜底（页面行序 = `sku_list` 序），避免写错价格。
5. **修正报错文案**：区分「行没渲染」（滚动问题）与「行渲染了但名字不匹配」（数据问题），
   后者要把两侧的 token 集合都打出来。

## 4. R2 · 提交阶段"假失败"（5 次，最高危）

### 4.1 现场证据（本次实测）

发布浏览器仍开着（CDP 端口 **9500**），页面停在 17:10 那次失败的现场：

```
https://fxg.jinritemai.com/ffa/g/create?
抖店

商品提交成功，继续发布商品视频，分享到抖音
商品提交成功，需审核通过后生效，审核周期为1-2个工作日。
您可以在 "商品管理-审核记录" 中查看审核进度，请耐心等待。

[继续发布] [返回商品列表] [编辑商品] [复制链接]
```

页面 `attr-field-id` 数量 = **0**（表单已卸载），文件输入框 1 个。
XPath 实测：`//*[contains(text(),"商品提交成功")]` 命中 **2**，
`//*[contains(text(),"商品提交成功，继续发布商品视频")]` 命中 **1**。

数据库核对：`record` 表只有一条 `name=ID-1081080198595, status=0, publish_time=None`。

> **即：平台已受理，程序判失败，数据库未落库。**

### 4.2 选择器本身没问题（已实测排除）

用 DrissionPage 4.1.1.4 连上 9500 实测 `_submit_publish` 的判据：

| 定位写法 | 结果 |
|---|---|
| `'商品提交成功，继续发布商品视频，分享到抖音'`（**代码现状**） | ✅ HIT，`tag=div` |
| `text=整句` / `text:整句` / `text:商品提交成功` | ✅ HIT |
| `xpath://*[contains(text(),"商品提交成功")]` | ✅ HIT |

**所以不是元素漂移、不是选择器失效。**

### 4.3 根因：13 秒窗口太短

```python
def _submit_publish(main_tab, record):           # app.py:6869
    main_tab.ele('xpath://span[text()="发布商品"]/..').click()
    success_selector = '商品提交成功，继续发布商品视频，分享到抖音'
    deadline = system_time.perf_counter() + 13.0   # ← 只等 13 秒
    while True:
        if main_tab.ele(success_selector, timeout=0.05): ...break
        if _handle_publish_modal(): ...continue
        if system_time.perf_counter() >= deadline: break
        system_time.sleep(0.15)
```

5 次失败的 `submit_publish` 耗时分别是 13.65 / 13.66 / 13.69 / 13.80 / 17.09 秒
—— **全部跑满窗口**。而平台侧「创建商品 + 图片转存 + 送审」在 13 秒内没返回结果页。

平台的「发布提醒」弹窗（`不修改，继续发布`）当前页面上命中数均为 **0**，
说明这次没有弹窗挡路；失败纯粹是**等待预算不够**。

### 4.4 放大危害的两个设计

1. **判据单一**：只认整句文案。文案改版、页面走的是别的成功分支，都会判失败。
2. **失败路径不落库**：

```python
    if publish_ok:
        record.status = 1
        record.publish_time = time.now()
        record.save()
        return True
    print('发布失败！')          # ← 失败只是打印，record 完全不写
    return False
```

于是"没读到成功文案"被等同于"没发布"，用户重跑 → **重复铺货**。
代码里已经有一句人工提示（`若页面已离开发布页…请先人工核对再重跑`），
但那是靠人记住，不是机制。

### 4.5 修法（建议）

| # | 措施 | 说明 |
|---|---|---|
| 1 | **延长并分级等待** | 把 13s 提到 60~90s，且用多信号判定：成功文案 **OR** 表单已卸载（`attr-field-id` 数=0）**OR** 出现「继续发布/返回商品列表/编辑商品」按钮组 |
| 2 | **新增「已提交待确认」状态** | 超时后不要直接写"失败"，落库为 `status=2`，UI 提示"可能已成功，请到商品管理核对"，并**禁止自动重试** |
| 3 | **重试前查重** | 重跑前先查商品管理/审核记录里是否已有同名商品 |
| 4 | **记录现场** | 超时时把页面 URL、可见按钮文本、`attr-field-id` 数量写进 timing 日志，下次一眼能判 |

> 措施 2 是**根治重复铺货**的那一条，其余是提高命中率。

## 5. R3 · `fill_title` 元素句柄失效（6 次）—— 竞争确认存在，修复见 §12.5

### 5.1 精确失败点

失败在 `app.py:5526` —— 对「商品标题」输入框句柄调 `click()`：

```python
5519: input_element = _get_title_input(main_tab, timeout=0.4)   # 取 #pg-title-input 句柄
5525: _ensure_title_brand_name_disabled(main_tab)               # 窗口内唯一的页面交互
5526: input_element.click()                                    # ← 抛 ElementLostError
```

证据来自 sidecar 自己落盘的 6 份错误报告
（`output\browser-debug\upload_error_*\*_fill_title_report.json`）里的 traceback，6 次完全同形：

```
app.py:5526 input_element.click()
 → clicker.py:58 self._ele.wait.stop_moving()
 → rect.py:29 size → chromium_base.py:389 _run_cdp
 → tools.py:199 raise_error → ElementLostError
```

即 CDP 返回 `Could not find node with given id`（节点在点击瞬间已被从文档摘除）。

### 5.2 根因：Garfish SSR + React hydrate

fxg 发布页是 **Garfish 微前端 + SSR**（捕获的 DOM 里留有 `SSRDataScript`、
`window["__GARFISH_SSR_ECOM_FXG_ADMIN"].dom=...`）。
`_detect_publish_page_stage` 的 step1 判据**可以被 hydrate 之前的 SSR DOM 满足**，
于是代码在表单还没稳定时就取了句柄，约 0.4s 后 React 重建该节点，句柄作废。

排除项（均有证据）：
- **不是本应用主动改动所致**：失败时刻捕获的 1.58MB 全页 DOM 中 `使用品牌名` 节点数为 0
  → `_ensure_title_brand_name_disabled` 提前 return，窗口内没有任何主动 DOM 操作；
  且捕获 DOM 里标题输入框 `value=""`，说明写标题从未发生，死在 click。
- **不是「返回旧版」分支**：该分支只在探针报 `unknown` 时触发，
  而失败恰恰全部集中在探针**最快**报 step1 的运行里；6 份捕获 DOM 都是旧版表单、无「返回旧版」节点。

### 5.3 为什么"看起来已经好了"是个假象

我最初据"最后一次失败在 2026-09-25、之后未复现"推断已被上游等待盖住。
**这个推断是错的**，支线复核推翻了它：

| 事实 | 值 |
|---|---|
| `app.py` 最后修改 | 2026-09-24 22:25:43 |
| 当前 `python-backend.exe` 构建 | 2026-09-24 22:26:13 |
| 最后 2 次 `fill_title` 失败 | 2026-09-25 13:06、2026-09-25 23:55 |

→ **最后 2 次失败跑的就是当前代码**（traceback 行号 5526 / 7040 / 538 与当前文件逐行吻合）。
时间相关性（失败都在 `open_publish_page` 2.06~2.245s 的快路径、
≥2.9s 的 64 次 0 失败）成立，但**同一快区间里也有 7 次成功**
（如 2026-10-01 11:37 的 2104ms）→ **这是竞争，不是必然**。
09-26 之后没复现只是没掷中。

`_settle_to_stage()` 只保证「阶段到了」，**不保证「表单节点已稳定」**。

### 5.4 修法（建议）

1. `5519` 只用于确认输入框存在；**把取句柄挪到 `_ensure_title_brand_name_disabled` 之后**。
2. click 前加稳定性判据：`_wait_until`（interval 0.05，timeout ~1.0s）
   要求 `input#pg-title-input` 连续 3 次可见 **且** 标题区 `outerHTML` 哈希不变。
3. 把 `click()` / `input()` 包成**捕获 `ElementLostError` 后重取句柄重试一次**
   —— 现有 `_click_element_safely` 的三分支重试只覆盖"点击失败返回"，**不覆盖句柄失效后的重新定位**。
4. 治本：在 `_open_publish_page` 的 `_settle_to_stage` 判据里加「DOM 稳定」条件
   （step1 探针为真 **且** `document.readyState==='complete'` **且** 标题区 outerHTML 间隔 ~0.3s 两次采样一致）。

## 6. R4 · 码数「均码」分组选不中（5 次）

```python
def _configure_sku_structure(main_tab):          # app.py:6363
    size_picker.click()
    if not _wait_until(lambda: bool(_find_uniform_size_group(main_tab)),
                       timeout=1.2, interval=0.04):
        raise Exception('未找到码数均码分组选项')   # ← 4 次
    ...
    if not _wait_until(lambda: bool(_find_uniform_size_leaf(main_tab)),
                       timeout=0.8, interval=0.04):
        raise Exception('未找到码数均码叶子选项')   # ← 1 次
```

级联菜单是异步渲染的，预算只有 1.2s / 0.8s。
`_find_uniform_size_group` 已经用了 `_find_first_visible_element`（单次 JS 批量探测，已优化），
所以**不是探测慢，是菜单压根没在预算内出现**。

## 14. 重建 sidecar 的实操记录（2026-10-01 已执行）

### 14.1 构建曾两次"假死"，根因是 numba 的 JIT 缓存

`python build_sidecar.py` 在受限环境里会卡在：

```
INFO: Looking for dynamic libraries      ← 之后 30+ 分钟零产物、CPU 一直烧
```

实测两次都停在这里（第二次 1861 秒 CPU、workpath 只产出 `base_library.zip`）。
定位过程：

1. 用最小 onefile 构建验证 **PyInstaller 本身没问题**（6.8 秒完成）；
2. 逐个试重依赖：`numba` / `onnxruntime` / `scipy` 单独 import 都正常，
   **`pymatting` import 挂起**；`import rembg` 同样挂起
   （`rembg/bg.py:24-28` 在**模块顶层** `from pymatting... import ...` +
   `from skimage.morphology import disk, opening`，`rembg/__init__.py:11` 顶层 `from .bg import remove`）；
3. 试环境变量：

| 变量 | 结果 |
|---|---|
| 无 | **挂起** |
| `NUMBA_CACHE_DIR=<工作区内目录>` | ✅ `import pymatting` 立即成功 |
| `NUMBA_DISABLE_JIT=1` | ✅ 成功（但会改变运行时语义，未采用） |

**根因**：numba 默认把 JIT 缓存（`.nbi`/`.nbc`）写在 site-packages 源码旁，
受限环境下该写入被拦，numba 反复重试 → 表现为"CPU 一直烧但零进展"。

**正确构建命令**：

```powershell

python build_sidecar.py
Copy-Item ..\src-tauri\sidecar\python-backend.exe ..\src-tauri\target\release\python-backend.exe -Force
```

> 📌 这一步只影响**构建期** numba 的磁盘缓存位置，不改运行时行为；
> 用户在正常桌面环境启动应用时走默认缓存路径，不需要这个变量。
