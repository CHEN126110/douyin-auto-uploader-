## 1. 搜索词端点当前不可用（阻断「搜索词暴涨归因」）

证据：`D:\抖店\data\api_stability_results.json`

|---|---|---|---|---|
| `/compass_api/shop/mall/search_analysis/industry_words/doudian_rank_v3` | 3/3 | **0/3** | `{"10012": 3}` | **0** |
| `/compass_api/shop/mall/dd_search/search_analysis/weekly_report_summary` | 3/3 | **0/3** | `{"10012": 3}` | **0** |

- `lastMessage`：**当前视角与页面不匹配**
- 延迟正常（avg 117~124ms），HTTP 全 200 —— **看起来完全健康**

> 这是「假数据」的**完美样本**：传输层、HTTP 层全绿，业务层全败。
> 只看 HTTP 状态码的监控会把它标成可用。

**技术线索（未验证，需实测）**：这两个端点在清单里标注 `auth = headless_page`，
即需要**浏览器页面上下文**；而 `compass_api.js` 走的是纯 HTTP 直连（Path A）。
「视角不匹配」很可能源于此。仓库已具备浏览器内 fetch（Path B），
**改走 Path B 是否能通，必须实测验证，不可假定**。

**影响**：在这两个端点恢复之前，「搜索词为什么暴涨」缺乏数据源。
应先验证 Path B，若仍不通，则该需求需换数据源或降级为「基于自家商品表现 + 竞品/热销榜」的归因。

## 3. `_get()` 的错误处理漏洞

位置：`D:\抖店\scripts\compass\compass_api.js:49-80`

已实证的三个问题：

1. **错误对象被当数据用**：失败返回 `{ _error: '...' }`（truthy）。
   查证调用方：只有 `test_all_compass.js`、`_fetch_schemas.js`、`_probe_compass_apis.js`
   等测试/探针脚本检查 `_error`；业务脚本（如 `scripts/collect/probe_opportunities.js:52`）
   直接使用返回值。请求失败会被误读为「没有数据」。
2. **`return data.data || data`**：`data.data` 为 `{}` 或 `[]` 时（JS 中均为 truthy）照常返回，
   「真的没数据」与「异常空壳」无法区分。
3. **业务码检查不全**：只特判 `code` 与 `st === 10012`，
   其它非 0 业务码（含各类风控/鉴权码）可能漏网。

## 4. 归因的前提缺失：没有时间序列

- `compass_api.js` 中接口基本是**单日快照**（`begin_date = end_date`）；
  `getSearchRank()` 无日期参数。
- 仓库内 `data/` 下无历史快照库，仅有 API 参数与 schema。

**结论**：没有历史积累就无法判定「暴涨」。
必须先建立每日快照积累机制，且需要足够天数（建议 ≥14 天）才能启用突变检测。

## 5. 归因设计原则（防幻觉）

用户特别强调「避免得到的都是假的」。归因是 LLM 幻觉的重灾区——
给模型一堆数字问「为什么涨」，它必然给出一个听起来合理的解释，且多半是编的。

**职责边界必须写死**：

| 由确定性代码算出（可验证证据） | 由 LLM 负责 |
|---|---|
| 同期哪些相关词一起涨了 → 品类整体上涨/季节性 | 把证据串成人能读的解释 |
| 该词下热销商品有无换人 → 是否有商家投流 | 生成可读的行动建议 |
| 流量来源结构变化 → 是否算法倾斜 | —— |
| 日期是否撞节气/大促（本地日历） | —— |

**硬性要求**：
- 每个归因结论必须挂**可验证的证据链**；
- 明确区分「已验证事实」与「未验证假设」；
- 证据不足时必须输出「无法归因，仅观察到 X」，**不允许编造原因**；
- 不得复用 `D:\抖店\lib\attribution.js` 的 `confidenceOf`（只看指标方向一致性，
  会把噪音包装成 high 置信度，与防幻觉目标冲突）。

## 6. 建议的落地顺序（前两步不做完，后面都是白搭）

1. **确认目标店铺**并修复跨店铺串号（把罗盘链路与发布链路固定到同一 profile + 双向断言）。
2. **实测搜索词端点走 Path B 能否恢复**。不通则该需求换数据源或降级。
3. 加固 `_get()`：完整业务码判定、区分空数据与异常、错误绝不降级为空值。
4. 建每日快照库（存原始 body + sha256，不只存解析后的指标），积累 ≥14 天。
5. 在快照库之上做突变检测与归因；LLM 最后接入，且只做解释不做判定。

## 10. 一次真实的「假故障」（正好印证本文主题）

首次运行体检，14 个端点全部 `transport_error`，看起来像数据源全挂。
逐层排查后发现是**执行环境问题，与项目无关**：

```
PLAYWRIGHT_BROWSERS_PATH = C:\Users\CRB\Documents\HermesAgent\home\ms-playwright  ← 被运行框架劫持
实际浏览器               = C:\Users\CRB\AppData\Local\ms-playwright\chromium-1223
Playwright 1.62.1 期望   = chromium-1234（版本亦不匹配）
```

**教训**：如果体检工具只报「端点失败」而不区分 `transport_error` 与 `business_error`，
这次就会被误判成「罗盘数据源全部不可用」，进而做出完全错误的方案决策。
**故障分类的颗粒度本身就是数据可信度的一部分。**

## 11. 最重要的一课：防假工具自己产出了假报告

体检工具首版跑出的结果：**13/14 端点「✅ 有实质数据」**。看起来数据源很健康。

但每条返回都是 **49 字节**。抓出原始内容：

```json
{"st":100704,"msg":"服务器错误","data":null}
```

全是错误信封。真实状态是**登录态已失效**（身份断言同时报 `shopId: null`），所有请求都被拒。

### 双重失败，缺一不可

1. **`compass_api.js` 把错误信封当数据返回**（已知漏洞的实际发作）：
   ```js
   if (data.code && data.code !== 0) ...   // 该响应只有 st，没有 code → 跳过
   if (data.st && data.st === 10012) ...   // st 是 100704，不等于 10012 → 跳过
   return data.data || data;               // data 为 null → 返回整个错误信封
   ```
2. **体检工具的 `hasSubstance()` 只看「有没有字段」**：
   看到 `{st, msg, data}` 三个键、`msg` 非空，判定「有实质内容」。

### 修复

- `detectEnvelopeError()`：检查 `st`/`code`/`status_code`/`err_no`/`errNo` **全部**候选字段，
  任一非 0 即判 `business_error`；`data === null` 且带业务码 → `ok_but_empty`。
- 体积哨兵 `MIN_PLAUSIBLE_BYTES = 200`：实测错误信封 43~121 字节，真实 payload 数千字节。
- 修复后同一批数据：**13 个「可用」→ 0 个可用、13 个 `st=100704`**。

### 教训（直接适用于整个方案）

> **任何声称「保证数据可信」的组件，必须先证明自己不产假。**
>
> 这次的失败模式极具代表性：HTTP 200、延迟正常、字段齐全、非空字符串——
> 所有「表面健康」的信号全部满足，唯独业务码是错的。
> 若把这份报告当真去做优化，得到的每一条「市场洞察」都建立在错误信封之上。
>
> 具体到实现：**校验必须查业务码本身，而不是推断「看起来像不像有数据」**。
> 结构完整 ≠ 内容真实。

## 15. 底座加固完成：0/14 → 12/14，并修掉业务链路的真正漏洞

### 15.1 关键发现：此前只修了诊断链路，业务链路才是假数据入口

审计发现 `compass_api.js` 实际只被两个诊断脚本使用；
真正跑运营决策的是 `index.js → lib/doudian.js → lib/compass_pool.js`，
**那条链路上的同类缺陷一个都没修**。已查证并修复：

| 位置 | 缺陷 | 后果 |
|---|---|---|
| `lib/doudian.js` product_rank / product_analytics | 绕过 `_parseResult`，直接 `return ok(..., raw.data)` | `raw.success` 只代表 JSON 解析成功；`{"st":100704,...}` 被当成功数据返回。**且这两个正是上架优化最依赖的商品数据** |
| `lib/doudian.js` `_parseResult` | 业务码只查 `st` / `code` | `status_code` / `err_no` / `errNo` 类错误漏放行 |

修复：两处改走 `_parseResult`；业务码字段统一扩到
`['st','code','status_code','err_no','errNo']`（与 `compass_api.js` 的 `CODE_KEYS` 对齐）；
`compass_pool` 在解析后即做业务码判定，并带出 `codeField`/`codeValue` 供上层分类。
原文件均备份在 `archive/pre-session-fix-20260828/`。

> 教训：**修复的覆盖面必须由「谁在调用」决定，而不是由「哪个文件看起来是入口」决定。**
> `compass_api.js` 名字最像入口，实际只服务诊断脚本。

### 15.3 体积哨兵误报：把真数据判成了假数据

`MIN_PLAUSIBLE_BYTES = 200` 的哨兵把两个**真实响应**误判为不可信：

| 端点 | 字节 | 实际内容 |
|---|---|---|
| `getKeywordSearch` | 159B | `show_ucnt_incr: {value:151, out_period_ratio:-0.2705}` —— 曝光 151 人、环比 -27%，**真实数据** |
| `getCompetitorList` | 75B | `{selected_shop:[], total_limit:20}` —— **竞品确实未配置**，不是错误 |

根因是**体积哨兵越权**：`detectEnvelopeError` 已按业务码准确判定，
再让字节数覆盖它的结论就会误伤小而真实的响应。

> **误报与漏报同样有害**。漏报让假数据流入决策；
> 误报让人忽略真实数据，久而久之就不再信任告警。
> 判定权必须归于最可靠的依据（业务码），而不是启发式（字节数）。

## 16. 底座第二层完成：身份断言 + 快照库 + 解包器

### 16.1 身份断言已下沉到核心（安全闸门）

`compass_api.js` 的 `init()` 建立会话后立即断言店铺身份，双向实测通过：

| 用例 | 结果 |
|---|---|
| `COMPASS_EXPECT_SHOP_ID=155450371`（正确） | ✅ 放行，`getCurrentShopId()` 返回 155450371 |
| `COMPASS_EXPECT_SHOP_ID=177886360`（错误） | ✅ **抛异常中断**，并失效会话 |

未设置环境变量时只告警不拦截（显式配置才启用强校验），避免给既有脚本带来意外中断。

### 16.2 快照库（`lib/compass_snapshots.js` + `scripts/compass/daily_snapshot.js`）

- **SQLite 主库 + 原始 body 内容寻址（gzip）**。原文是证据，必须独立于 DB 存在。
- **唯一键是「统计口径」而非「抓取时刻」**：`D:日期` / `W:窗口` / `S:状态` / `U:未知`；
  口径优先从 payload 的 `extra.date_range` 提取，取不到才回落请求参数——
  服务端返回的口径才是数据真正代表的范围。
- **幂等实测**：同内容重抓 0 新增；内容变化则新增版本，**不覆盖**（回补数据不毁证据）。
- **失败也入库**（`status='error'`），否则「某天没数据」与「某天没抓」无法区分，
  曲线断裂会被误判成暴跌。

### 16.3 一个「假证据」缺陷（已修）

初版采集器的 `parsed` 来自业务函数、`raw` 却**另起一次 `_getRaw` 调用**，
两次请求参数不同，导致存进去的原文根本不是实际使用的那份数据
（实测出现 `status='ok'` 但原文是错误信封）。

修复：`compass_api` 记录 `lastRaw`，采集器取**同一次调用**的原文。

> 存证与数据必须同源。证据链对不上数据，本身就是一种假数据 —— 而且更危险，
> 因为它让人误以为「有据可查」。

### 16.4 解包器（`lib/compass_unwrap.js`）

平台返回的是**渲染用的表格结构**而非业务数据：
`{cell_type, children, value:{unit, value_str}}`，外层套 `xxx_children.children[]`，
指标里混着 24 小时图表点。实测商品列表 47522B，业务字段不足 8KB。

- 丢弃 `chart` / `axis_*`（对上架决策无用，占绝大部分体积）；
- **`unit=6` 一律解为 `null` 并标 `__missing`**，绝不当作 0；
- 提取 `index_values` 的 `value` / `last_value` / `out_period_ratio` ——
  **平台自带上期值与环比**，趋势是现成的。

> 初版解包器只认 `{cell_type, value}` 形态，把 `xxx_index_values` 整层丢掉，
> 结果 `pay_amt`、`product_show_ucnt`、`rank_num`、`refund_amt` **核心指标全丢**，
> 却"看起来解包成功"（体积从 47KB 降到 5KB，压缩比很漂亮）。
> **压缩比不是正确性指标**——丢掉全部指标也能得到很好的压缩比。

实测：47522B → 7368B（15.5%），19 个商品，字段含本期/上期/环比。

解包后的真实商品数据（店铺 155450371，2026-08-28）：

| 排名 | 商品 | 曝光 | 支付 | 退款 |
|---|---|---|---|---|
| 1 | 秋冬季可爱日系甜美碎花中筒袜女ins潮外穿蝴蝶结堆堆… | **2** | 0 | 0 |
| 2 | 春秋蝴蝶结袜子女中筒袜甜美日系小众款堆堆袜秋冬搭配… | **1** | 0 | 0 |
| 3 | 【杏仁榛果系列】秋冬新款直板中筒堆堆袜复古咖色系 | **2** | 0 | 0 |
| 4 | 换季清仓链接甜美花边袜子女秋冬款中筒袜韩系日常百搭… | **2** | 0 | 0 |

共 19 个商品，**排名第一的曝光是 2 次，全店支付 0 单**。

### 这意味着什么

1. **自家数据无法支撑任何转化率类结论**。曝光 2 次、支付 0 单，
   算出的任何「点击率」「转化率」都是统计噪音。
   此前调研提出的样本门槛（曝光 < 100 不参与排名）**全店商品无一达标**。
2. **问题不在转化，在曝光**。优化标题以「提高转化率」是无的放矢——
   商品根本没有被看到。真正要解决的是「为什么没有曝光」。
3. **高价值信息只能来自行业维度**，不能来自自家历史。
   而行业搜索词端点目前仍缺类目参数（`total=0`），**这条链路的优先级因此高于一切**。
4. 平台「诊断」接口返回的是广告推广文案
   （「投放精选商品，加速商品成交」），不是技术诊断，不可当作优化依据。

> **这是本轮最重要的发现**：在拿到真实数据之前，
> 整个方案默认「自家经营数据 + 行业数据 → AI 优化」；
> 真实数据表明自家数据这一侧目前近乎为零。
> 若不看数据就动手，会造出一套在噪音上做精密计算的系统。

## 18. 数据作用域三分法：区分「市场 / 店内统计量 / 店内状态量」

用户指出「这些数据可能有部分是店内的不是市场的，需要区分高价值数据」。
实证后确认这个区分成立，且**必须分成三类而非两类**——
简单的「店内 vs 市场」会误伤一批即使样本极少也有效的数据。

### A 类：市场数据（全平台样本，统计上可信）

| 来源 | 内容 | 实测状态 |
|---|---|---|
| `summary_core_index_v3` 的 `__benchmark` | **同行基准值** | ✅ 已取到 |
| `industry_words` 的行业字段 | `query`、`search_ucnt`、`search_ucnt_trend`、`query_tag` | ⚠️ 鉴权已通，缺类目参数（`total=0`） |
| `market_hot_sale` | 市场热销榜 | ❌ `st=11001` 平台限流 |

**已取到的同行基准（2026-08-28）**：

```
指标                        自家    同行基准
settlement_amt               0      6550
ad_costed_expense_ratio      -      0.0922   (9.22%)
overall_ad_costed_expense    -      0.1406   (14.06%)
```

> 同行广告费用占比 9~14%，而本店曝光个位数。
> 这是「曝光为什么只有 2」的一个**可验证解释**（同行靠付费流量），而非猜测。

### B 类：店内统计量（样本受限，当前是噪音）

`product_list` 的 `pay_amt` / `product_show_ucnt`、`flow/overview` 的流量指标等。

全店曝光个位数、支付 0 单，据此计算的任何比率（点击率、转化率）都是统计噪音。
**当前阶段不得进入 AI 提示词，也不得用于排序。**

### C 类：店内状态量（与样本量无关，始终有效）

| 数据 | 为什么有效 |
|---|---|
| `shop_show_product_top_rank` 本店在某词下的排名 | 是**位置**，不是统计量 |
| `rank_num` 商品排名 | 同上 |
| 商品是否被某搜索词收录 | 是**事实**，非概率 |
| 类目挂载、属性完备度 | 是**配置状态** |
| `prof_exp_score` 体验分 | 平台直接判定，非我方样本推算 |

> **这是三分法的关键价值**：C 类即使曝光为 0 也完全有效。
> 「你的商品没有出现在『中筒袜女』这个词的结果里」是一个事实，
> 不需要任何样本量支撑；而「你的转化率是 50%」在曝光 2 次时毫无意义。
> 只做「店内 vs 市场」二分会把 C 类一起废掉，而 C 类恰恰是当前最可用的诊断依据。

### 混合作用域端点必须拆开

`industry_words` 在**同一个响应里**混合两种作用域：

| 行业字段（A 类） | 店内字段（C 类） |
|---|---|
| `query`、`search_ucnt`、`search_ucnt_trend`、`query_tag` | `shop_product_show_ucnt_rate`、`shop_show_product_top_rank`、`shop_show_product_list`、`shop_product_diagnosis` |

消费时必须按作用域拆开标注，不能整体当成「市场数据」或「店内数据」。
**这是最容易出错的地方**：把店内的曝光占比当成行业数据用，
或反过来把行业搜索量误当自家成绩。

### 对 AI 输入的直接约束

| 类别 | 是否进提示词 | 用途 |
|---|---|---|
| A 市场 | ✅ 必须 | 判断依据：什么词有量、同行水位在哪 |
| B 店内统计量 | ❌ 禁止（样本不足时） | —— |
| C 店内状态量 | ✅ 必须 | 定位依据：我在哪、缺什么 |

> 判断「值不值得喂给 Agent」的标准不是「是不是我们的数据」，
> 而是**它在当前样本量下是否仍然成立**。

## 21. 关于平台推荐的可信度（用户提醒，已采纳为设计约束）

> 「不建议只看平台推荐的，因为通常不一定准确足够支持判断。」

**这个判断有直接证据支持**：同源的 `reach_data` 端点返回的所谓「诊断」，
实际内容是广告推广文案——「投放精选商品，加速商品成交，预估 ROI 不低于 80.0」。
**平台推荐带商业动机：它希望你投钱，不必然等于你该做的事。**

因此确立以下约束（已写入代码注释与采集器）：

| 原则 | 落地 |
|---|---|
| 平台结论只作**信号之一**，不作唯一依据 | `getRecommendOptimizedProduct` 的 JSDoc 显式声明 |
| 优先采集**原始数据**而非平台结论 | 补的 7 个端点中 6 个是原始指标；那 1 个结论型端点保留的理由是它**同时带回竞品对标原始数据** |
| 平台结论必须可**交叉验证** | 行业搜索排行 + 市场店铺排行 + 指标区间分布三路独立数据，可相互印证 |
| 作用域标注区分二者 | `data-contract.js` 中平台结论归混合作用域，需按字段拆分 |

> 这修正了我此前给出的方向建议（「以平台诊断为主，AI 只负责改写」）。
> 更准确的表述是：**以平台的原始数据为主，平台的结论与 AI 的结论同样需要被验证。**

## 22. 细节打磨：新端点的解包与作用域登记

补上端点只是「拿到字节」，能不能用还得看解包。实测发现新补的 7 个里有 4 个解不出或解错。

### 又三种没见过的结构

| 结构 | 端点 | 特征 |
|---|---|---|
| `base_info` + `metrics` | 行业搜索词排行 | 值可能是标量，**也可能是 `extra_value.{lower,upper}` 区间** |
| `compass_general_table_value` | 市场店铺排行 | `basic_meta` 声明列名，`data` 为行 |
| `range_list.{指标}[]` | 行业指标区间 | 区间在 `index_values.extra_value`，**`tag` 标出「本店所在区间」** |

**行业数据常以区间下发**（如「袜子行业月成交 7.5~10 亿」），
初版解包只取标量，把区间整个丢掉——等于丢掉全部信息。

### 一条极干净的定位信号

`index_range_list` 解出后：

```
档1       0 ~   25000  ← 本店在此档
档2   25000 ~   50000
档3   50000 ~   75000
```

**这属于 SHOP_STATE（状态量），不受样本量影响**——
本店曝光 2 次、成交 0，但「处于同行最低档」这个事实依然成立且可用。
这正是三分法相对「店内/市场」二分法的价值所在。

### 「有表头无数据」必须与「解包失败」区分

`market/shop_rank` 与 `channel_product_card_list` 解出 0 字段，
排查后确认是**本店确实没有排名/商品卡数据**（`data: []`，只有 `basic_meta` 列名），
不是解包器不认。

现改为显式标注 `__empty: true` + `__columns`，
避免「本店无数据」被误读成「解包失败」而去反复排查代码。

### 作用域登记

7 个新端点已登记进 `data-contract.js`：

| 端点 | 作用域 | 可否作判断依据 |
|---|---|---|
| `search_industry_rank` | MARKET | ✅ |
| `market_shop_rank` / `shop_benchmark_list` | MARKET | ✅ |
| `market_index_range` | **SHOP_STATE** | ✅ 档位不受样本量影响 |
| `search_shop_rank` / `channel_product_cards` | SHOP_STATE | ✅ |
| `recommend_optimized_product` | **混合，未登记** | ⚠️ 必须按字段拆分 |

新增字段规则：`benchmark_*` / `compare_*` / `__lower` / `__upper` → MARKET；
`isCurrentShop` / `tag` → SHOP_STATE。

> 平台推荐端点被刻意登记为 `scope: null`（混合），
> 使其**无法整包作为判断依据**，只能逐字段取用。
> 这是把「平台推荐不可尽信」这条约束**落进代码**，而不是停留在文档提醒。

自检增至 **50 项**，新增三条锁住：行业词区间不丢失、本店档位可识别、空表格与解包失败可区分。
