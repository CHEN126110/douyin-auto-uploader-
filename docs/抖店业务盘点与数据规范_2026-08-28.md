# `D:\抖店` 业务盘点与统一数据规范

## 一、这个项目到底在做什么

不是「罗盘抓取工具」，而是一条**完整的电商运营流水线**：

```
1688 找货  →  发布上架  →  经营诊断  →  订单售后  →  财务结算
   ↑                          ↑
抖音内容侧信号            网盘/文档素材
```

**145 个注册工具，12 个数据源前缀。**

| 域 | 工具数 | 干什么 |
|---|---|---|
| `store.*` | **71** | 抖店店铺全链路：商品(19)、财务(15)、售后(7)、订单(5)、物流、资质、规格、会员、通知、优惠券、运费、结算 |
| `diagnosis.*` | **41** | 经营诊断：罗盘(14)、抖音内容侧(14) |
| `pan` / `kdocs` | 11 | 网盘与在线文档素材 |
| `source.*` | 5 | 1688 / 巨量供给侧选品 |
| `im` | 3 | 客服消息（含 1 个写操作） |
| `auth` / `config` / `material` / `debug` | 10 | 登录、配置、图片处理、调试 |

**写操作 9 个**，全部已标记 `requiresApproval` 并受门禁拦截：
上架、下架、批量上架、建/改/删草稿、批量改价、发优惠券、发客服消息。

## 二、实际能拿到哪些数据（店铺 155450371 实测）

### 有数据的 7 类

| 数据 | 内容 | 作用域 |
|---|---|---|
| **商品列表** | 19 个商品：名称/ID/图/发布时间/曝光/支付/排名/退款，**含上期值与环比** | 混合 |
| **经营核心** | 14 项，**含 4 项同行基准** | 混合 |
| **货架分析** | 12 项：支付金额与人数、客单价、点击-成交转化率、新老客占比、UV 价值 | 店内统计量 |
| **体验分** | 10 项：差评率、投诉率、退货率、扣分 | 店内状态量 |
| **流量概览** | 6 项：GPM、支付金额、退款率、曝光 | 店内统计量 |
| **搜索周报** | 曝光人数 151、环比 −27.05% | 混合 |
| **类目树** | 完整层级（服装 → 1000003282 → 1000009114） | 参考数据 |

### 确认无数据的 3 类

店铺排名（本店无排名）、行业搜索词（缺类目参数，`total=0`）、竞品列表（未配置竞品）。

### 平台侧不可用的 2 类

`flow/source`（HTTP 500）、`market_hot_sale`（`st=11001` 限流）。

## 三、统一规范：`lib/data-contract.js`

### 为什么需要它

元数据原本已有 14 个字段、4 级风险分级（`riskLevel`），
但**完全没有记录数据的作用域**。于是同一个响应里，
「全平台搜索量」和「本店曝光占比」长得一模一样，谁也分不清哪个能拿来下结论。

实测背景让这件事变得紧迫：**19 个商品、排名第一的曝光 2 次、支付 0 单**。
这种样本下任何自家转化率都是噪音；而同行基准（结算额 6550、广告费用占比 9~14%）
来自全平台样本，才有统计意义。

### 作用域必须三分，不是两分

| 作用域 | 含义 | 能否作判断依据 |
|---|---|---|
| `MARKET` | 全平台/行业样本 | ✅ 可以 |
| `SHOP_METRIC` | 本店**统计量**（曝光、转化率、GMV） | ⚠️ 样本 ≥ 100 才可以 |
| `SHOP_STATE` | 本店**状态量**（排名、是否被收录、类目挂载、体验分） | ✅ **与样本量无关** |
| `REFERENCE` | 平台配置字典（类目树、运费模板） | ✅ 事实型 |
| `LOCAL` | 本地资源 | — |

> **关键在 `SHOP_STATE`**：「你的商品没出现在『中筒袜女』的结果里」是**事实**，
> 曝光为 0 也成立；而「你的转化率 50%」在曝光 2 次时毫无意义。
> 只做「店内 / 市场」二分会把这一整类连坐废掉，
> 而它恰恰是当前样本条件下最可用的诊断依据。

### 核心判据

```js
canDrivedecision(scope, { sampleSize, trust })
```

判断标准**不是「是不是我们的数据」，而是「它在当前样本量下是否仍然成立」**。

实测：

| 场景 | 结果 |
|---|---|
| 同行基准 6550 | ✅ 可作判断依据 |
| 本店曝光 2 次算转化率 | ❌ 样本量 2 < 100，属统计噪音 |
| 本店曝光 500 次算转化率 | ✅ 可作判断依据 |
| 本店在某词下的排名 | ✅ 状态量，不受样本量限制 |
| 可信度 suspect / rejected | ❌ 一律拒绝 |

### 混合作用域端点必须按字段拆开

`keyword_search`、`overview`、`product_rank` 在**同一个响应里**混着两种作用域：

| 字段 | 作用域 |
|---|---|
| `search_ucnt`、`query`、`industry_*` | MARKET |
| `*__benchmark`（同行基准） | MARKET |
| `shop_*`（本店曝光占比、最高排名） | SHOP_STATE |
| `pay_amt`、`refund_amt`、`*_rate` | SHOP_METRIC |

**对这些端点，未登记的字段返回 `null` 而不是回落端点默认值。**
「不知道」必须表达成「不知道」——推定作用域正是混合端点出错的方式，
而且这类错误不会报错，产出看起来完全正常。

## 四、规范是代码不是文档

全部约束已固化进 `npm run check`（**47 项，离线，任何环境都应全绿**）：

| 分组 | 锁住的不变量 |
|---|---|
| **数据契约** | 样本不足的店内统计量被拒；状态量不受样本限制；混合端点按字段拆分；未登记字段不得推定 |
| 解包器 | `unit=6` → null；真实 0 与「未知」可区分；benchmark 与环比不丢失 |
| 快照库 | 服务端口径优先于请求参数 |
| 写操作门禁 | 单一定义；未授权拦截；别名不可绕过 |
| 工具注册表 | 数量下限；写操作均标 `requiresApproval` |
| 高危接口 | 回环绑定；CORS 收紧；脚本接口默认禁用 |
| fxg 信封闸门 | 错误信封被拦截；正常数据不误伤 |
| 重试策略 | 限流/风控立即停止；瞬时故障正常重试 |
| 凭证保护 | 写入前校验登录态；覆盖前备份 |
| 店铺身份 | 无裸调 `compassPool.init()` |

## 五、盘点过程中修掉的问题

**解包器只认一种结构**。原实现照商品列表写，而平台有**四种**：

| 结构 | 特征 |
|---|---|
| 商品列表 | `cell_info` + `index_values` |
| 卡片型 | `compass_general_multi_index_card_value` + `basic_meta` |
| 指标数组 | `gmv_data[].index`，**`unit` 是字符串 `"price"` 而非数字 `3`** |
| 裸指标 | `{value:{unit,value}}`，**既无 `cell_type` 也无 `index_value` 包装** |

补齐后：货架分析 0 → **12 字段**，流量概览 1 → **6 字段**，搜索周报 0 → **2 字段**。

**中途制造过一次回归**：给 `module_data` 加分支时用了 if-else，
绕过了原本有效的路径，`summary` 从 14 字段掉到 0。
改成**取并集**才恢复——同样的坑（「只走其一会漏掉另一半」）
在 benchmark 那次已经踩过一回。
