# 采集协议化路线设计（2026-04-19）

## 目标

把当前 `1688 / 淘宝 / 天猫` 的链接采集，从“浏览器打开页面后混合 DOM 提取 + 文件下载 + 导入回填”的模式，逐步升级为一条独立、可审计、可分平台推进的协议化采集主线。

这里的“协议化”不是一句口号，而是要求：

- 平台识别明确
- 阶段边界明确
- 每个阶段有产物
- 先有证据，再有执行器
- 不靠继续堆 DOM 选择器来掩盖结构问题

## 当前真实现状

当前采集主入口在：

- [app.py](/E:/Script%20Project/Dyin/beiufen/2.0/tauri-app/python-sidecar/app.py): `/api/capture/start`

核心链路：

1. `start_capture()`
   - 校验 URL，只允许 `淘宝 / 天猫 / 1688`
2. `run_capture_task()`
   - 启动 `DrissionPage`
   - 访问平台首页建立浏览轨迹
   - 打开商品链接
   - 判断是否登录 / 是否触发拦截
   - 分平台提取商品信息
   - 下载主图 / SKU 图 / 详情图
   - 将结果写入 `capture_tasks`
3. `/api/capture/import`
   - 从采集结果读取 `download_path`
   - 找 SKU 文件夹
   - 回填 SKU 图片
   - 用采集结果中的价格去匹配本地 SKU 文件
   - 最终导入本地产品库

## 当前三平台的真实差异

### 1688

优势：

- 目前已经不是纯 DOM 采集
- 已有较强的平台上下文提取，直接读 `window.context.result.data`
- 已有独立函数：
  - `_extract_1688_context_snapshot()`
  - `_collect_1688_detail_images()`
  - `_build_1688_sku_info()`
  - `_extract_1688_parameters()`

结论：

- 1688 最适合优先协议化
- 它离“平台状态提取 -> 结构化结果”只差一步，不应该继续停留在“半 DOM 半协议”的状态

### 淘宝 / 天猫

现状：

- 入口仍统一走 `run_capture_task()`
- SKU、价格、图片仍大量依赖 DOM 选择器 + 页面执行脚本
- SKU 价格提取采用：
  - 先抓 DOM 默认价
  - 再点击 SKU 做二次价格修正

结论：

- 淘宝 / 天猫比 1688 更依赖页面结构
- 但其协议化并不是不可能，而是应拆成两层：
  1. 页面状态对象 / 初始化数据抓取
  2. 真实接口或页面内 JSON 数据复用

## 当前结构问题

当前采集主线有三个耦合点：

1. 采集与浏览器行为耦合
   - 平台访问、登录判断、滚动、DOM 提取都混在一个函数里
2. 采集与文件落地耦合
   - 下载图片后才能继续导入
3. 采集与导入回填耦合
   - `/api/capture/import` 需要再靠文件名、SKU 名称、价格映射去做二次对齐

这三个耦合会导致两个后果：

- 任何平台页面改版都会直接拖垮整条链
- 采集问题和导入问题会混在一起，难以复盘

## 采集协议化的阶段规划

建议新增独立模块：`tauri-app/python-sidecar/protocol_capture/`

阶段规划如下：

1. `route_url`
   - 统一识别 1688 / 淘宝 / 天猫
   - 统一规范化链接与商品 ID

2. `session`
   - 记录平台、浏览器、当前 URL、登录状态
   - 暂时不改变现有登录方式

3. `product_payload`
   - 1688：优先接管 `window.context`
   - 淘宝 / 天猫：优先找页面初始状态对象和接口响应

4. `sku_payload`
   - 分离 SKU 名称、规格图、价格
   - 不再把“点击 SKU 再改价”埋在大函数中

5. `asset_manifest`
   - 把主图、详情图、SKU 图先做成结构化清单
   - 下载器只是清单消费者，不再负责推断业务结构

6. `import_manifest`
   - 生成标准导入清单
   - 让导入逻辑消费结构化结果，而不是再次猜测

## 优先级

### 第一优先级

1688 协议化

理由：

- 现有上下文数据最完整
- 页面状态提取最明确
- 当前代码已经具备“半协议”雏形

### 第二优先级

淘宝 / 天猫的页面状态对象提取

目标：

- 先把价格、标题、SKU、主图、详情图的数据源从 DOM 选择器中剥离出来
- 暂时不直接承诺“完全绕过浏览器”

### 第三优先级

下载与导入解耦

目标：

- 采集阶段输出 `manifest`
- 下载器按 manifest 执行
- 导入器按 manifest 导入

## 与上传协议化的关系

两者要统一规划，但不能混在一个引擎里。

原因：

- 采集面向外部平台商品详情页
- 上传面向抖音发布后台
- 会话、数据结构、阶段定义都不同

因此应该保持：

- `protocol_publish/`：抖音发布协议化
- `protocol_capture/`：货源采集协议化

但两者共享原则：

- 先证据，后执行器
- 每阶段必须有产物
- 禁止隐式兜底
- 失败必须可复盘

这一轮不直接改掉现有采集流程，而是先做三件事：

1. 建立 `protocol_capture/` 目录骨架
2. 固化三平台与阶段规划
3. 给后续 1688 协议化接入留出正式位置

这样下一轮就可以直接开始：

- 再把淘宝 / 天猫的状态对象提取拆出来
