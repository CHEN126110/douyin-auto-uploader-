# 协议化上传流水线设计

创建日期：2026-04-19
更新时间：2026-04-19
当前角色：协议化上传早期架构设计参考文档

## 1. 目标

在现有 DOM 驱动上传流水线之外，新增一条明确独立的“协议化上传流水线”。

这条流水线的目标不是掩盖 DOM 流水线的问题，也不是做隐式兜底，而是作为一条可独立选择、可独立调试、可独立度量的上传引擎，重点提升：

- 价格库存填写稳定性
- SKU 结构处理速度
- 页面元素改版后的抗脆弱性
- 出错时的可追踪性

## 2. 当前流水线复盘

当前上传主流程位于：

- `tauri-app/python-sidecar/app.py::_execute_upload_flow`

主阶段顺序：

1. `open_publish_page`
2. `fill_title`
3. `upload_main_images`
4. `select_category`
5. `fill_category_attributes`
6. `upload_media_assets`
7. `configure_sku_entries`
8. `configure_sku_structure`
9. `fill_price_stock_and_delivery`
10. `submit_publish`

其中强依赖 DOM 的部分主要有：

- 页面登录态检查与发布页跳转
- 类目树选择
- 类目属性控件填写
- 主图/视频/白底图/详情图上传
- SKU 规格名、规格图、价格库存表格填写
- 提交发布与错误提示读取

## 3. 协议化可行性判断

### 3.1 不建议直接做“全协议版”

原因不是做不到，而是当前没有证据证明：

- 发布页所有草稿字段都有稳定公开 JSON 接口
- 媒体上传链路不依赖动态签名、STS、一次性 token 或页面态校验
- 最终“发布商品”提交接口可以脱离浏览器页面稳定复现

如果在这些关键点没挖清之前直接做“全协议版”，风险很高：

- 接口变更后会整条链路不可用
- 媒体上传阶段最容易卡在签名和回调确认
- 最终提交阶段可能存在页面上下文 token 依赖

### 3.2 适合先做“混合协议版”

最现实的路径是：

- 浏览器只负责登录态与少量页面上下文获取
- 商品字段、SKU、价格库存、部分类目属性改走协议
- 媒体上传和最终发布先保留浏览器确认，等接口挖清再继续协议化

这样做的收益最大，因为当前最慢、最脆弱的地方正是：

- SKU 结构与规格批量填写
- 价格库存虚拟表格滚动与逐行校验
- 页面改版后 XPath / class 失效

## 4. 分阶段协议化优先级

### P0：接口挖掘基础设施

现有基础已经具备，不需要从零开始：

- `mcp-server/cdp-tools.js`
  - `cdp_discover_targets`
  - `cdp_page_snapshot`
  - `cdp_fetch_json`
  - `cdp_network_capture`
- `mcp-server/core.js`
  - 已注册 CDP 类调试工具

这意味着当前项目已经能做：

- 在已登录 Chrome 页面对目标动作抓取 XHR / fetch
- 用页面 cookie 直接重放 GET / POST
- 记录 URL、方法、载荷、响应结构

### P1：价格库存协议化

这是第一优先级，因为收益最大，复杂度相对最低。

当前 DOM 版最脆弱之处：

- 价格库存区域是虚拟表格
- 行顺序与滚动窗口耦合
- 写入后还要做 DOM 回读校验

协议化目标：

- 直接找到价格库存批量保存接口
- 按 SKU 标识提交价格、库存
- 返回后只做接口级结果校验，不再依赖表格滚动

预期收益：

- 速度提升最明显
- 几乎完全消除“乱跳”“跳过三行”“从第一行重写”的问题

### P2：SKU 结构协议化

范围包括：

- 规格名
- 规格图
- 规格备注
- 规格组合结构

协议化目标：

- 找到 SKU schema / sku list / sku save 相关接口
- 直接按结构生成 SKU 数据

预期收益：

- 减少大量逐控件输入
- 降低弹窗、滚动、懒加载对流程的影响

### P3：类目属性协议化

重点不是全字段，而是先覆盖“高频且规则明确”的属性：

- 品牌
- 适用人群
- 适用性别
- 筒高
- 面料材质与材质占比

协议化目标：

- 找到属性 schema 接口
- 明确属性 ID、值 ID、枚举值与可选结构

### P4：媒体上传协议化

这是最复杂的一段，必须晚于 P1/P2/P3。

原因：

- 可能涉及上传凭证、临时 token、回调确认
- 主图、白底图、视频、详情图可能不是同一条上传链路
- 平台可能在上传完成后追加 OCR / AI / 规范校验

协议化目标：

1. 找上传初始化接口
2. 找文件上传目标地址与鉴权参数
3. 找上传完成确认接口
4. 找素材绑定到商品草稿的接口

### P5：最终发布协议化

这是最后一段。

要求必须先确认：

- 草稿数据可完整持久化
- 提交接口的 headers / token / nonce / version 可稳定取得
- 服务端错误信息可直接返回，不依赖页面弹窗

## 5. 推荐的产品形态

不要把协议逻辑偷偷塞进现有 DOM 流水线里。

推荐改成两条明确引擎：

- `DOM 上传引擎`
- `协议上传引擎（Beta）`

两条引擎都走同一份商品数据，但执行器不同。

这样做的好处：

- 行为边界清晰
- 出问题时容易定位是 DOM 侧还是协议侧
- 可以做同商品 A/B 对比，真实比较速度和稳定性

## 6. 建议的代码结构

建议新增目录：

- `tauri-app/python-sidecar/protocol_publish/`

建议模块：

- `models.py`
  - 上传草稿、SKU、媒体、属性的数据模型
- `session.py`
  - 从已登录浏览器获取 cookie / csrf / 页面上下文
- `client.py`
  - 协议请求封装，统一 headers、超时、日志
- `discovery.py`
  - 接口挖掘结果管理与接口元数据
- `stages/price_stock.py`
  - 价格库存协议执行器
- `stages/sku.py`
  - SKU 协议执行器
- `stages/attributes.py`
  - 类目属性协议执行器
- `stages/media.py`
  - 媒体协议执行器
- `stages/submit.py`
  - 提交发布协议执行器
- `engine.py`
  - 协议流水线编排入口

## 7. 接口挖掘方法

### 7.1 原则

不直接凭空猜接口。

必须用“真实页面动作 -> CDP 抓请求 -> 低频重放验证”的方式推进。

### 7.2 每个阶段的挖掘步骤

1. 打开已登录发布页
2. 只触发一个最小动作
3. 用 `cdp_network_capture` 记录该动作产生的 XHR / fetch
4. 从 URL、方法、载荷中筛选候选接口
5. 用 `cdp_fetch_json` 低频验证
6. 记录请求条件、依赖字段、返回结构、失败码

### 7.3 推荐最先挖的动作

1. 只改一行 SKU 价格
2. 只改一行 SKU 库存
3. 只新增一个规格值
4. 只修改一个类目属性
5. 只上传一张图片
6. 只点一次“发布商品”

## 8. 调试与审计要求

协议版必须天然可审计。

每一步都要记录：

- stage
- request url
- method
- request body 摘要
- response code
- response body 摘要
- elapsed_ms
- whether mutated draft

不要做隐式吞错。

如果某一步接口失败，就明确停在当前阶段，并把失败接口和摘要返回给前端。

## 9. 预期收益

### 稳定性收益

- 降低页面 class / 结构变化带来的失败率
- 减少浮层、引导、滚动、懒加载对主流程的干扰
- 价格库存不再依赖虚拟表格滚动

### 速度收益

- SKU 与价格库存将是最大收益点
- 类目属性次之
- 媒体上传是否提速取决于平台上传链路

## 10. 当前结论

当前项目不适合直接跳到“全协议发布”。

最合理的下一步是：

1. 先做一条独立的 `协议上传引擎（Beta）`
2. 第一阶段只覆盖 `价格库存 + SKU结构 + 类目属性`
3. 媒体上传与最终发布先继续保留浏览器版
4. 用真实抓包和低频重放逐步扩展协议覆盖面

这条路线符合实际，也最有机会先把稳定性和速度真正拉上来。
