# 拼多多发布路线研究计划（2026-10-10）

目标：把「**从登录到发布**」这条链路在拼多多商家后台（`mms.pinduoduo.com`）上摸清并逐步落地，
最终与抖店、淘宝一样成为本应用里一条可选的发布通道。

本文件是**计划**，不是结论。落地后的每一条事实都要按本仓约定的证据分级
（`verified` / `candidate` / `unknown` / `rejected`）记进新子项目的
`docs/05-证据日志.md` 与 `docs/06-阻塞项.md`。

---

## 一、边界与红线（与 `taobao-publisher/AGENTS.md` 同级，先立规矩）

1. **默认零写入**：上传图片、保存草稿、提交发布、改商品都默认禁用，必须由调用方显式传授权开关。
2. **不绕过任何安全机制**：不做登录绕过、验证码/滑块绕过、风控绕过、权限绕过，不做高频探测。
3. **不落敏感数据**：cookie / token / 手机号 / 店铺敏感信息 / 完整签名 URL / 未脱敏请求头一律不进仓库、
   不进日志；一切产物过脱敏守卫后再落 `captures/`。
4. **不用兜底掩盖映射错误**：字段没有实证就记 `unknown` 进阻塞项，**不许猜默认值让它跑通**。
   宁可明确失败，也不悄悄产出错误的发布结果。
5. **淘宝的结论不能搬**：拼多多与淘宝/抖店是三套互不相通的账号、协议与字段体系；
   只借架构（阶段划分、错误映射、安全门形态），结论与字段一律重新实证。
6. **禁止直接删除代码文件**（仓库级硬约束）；需要"删除"时移到
   `项目备份 禁止改动使用 只参考/recycle_bin/RECYCLE_<原因>_<日期>/` 并附 README。

## 三、阶段划分（每个阶段都有"做完的判据"）

### M0 环境与登录态（只读）
- 独立 Chrome profile（如 `.runtime/chrome-pdd-cdp`）+ 独立调试端口（**9335**，9333 抖店、9334 淘宝，不复用）。
- 走**真实登录**：账号密码 / 短信 / 扫码任选其一，登录态随 profile 持久化。
- 判据：关掉浏览器再启动，仍处于已登录状态；记录"登录态失效的触发条件"（时间、切网络、异地）。
- ⚠️ 已知坑（来自淘宝那套的教训）：Chrome 136+ 拒绝主 profile 开调试端口，必须用独立 user-data-dir。

### M1 发布页测绘（只读，产出证据表）
- 找到发布入口（类目选择 → 发布页）与它的 URL 形态；记录是否存在多步向导、是否有草稿态。
- 逐字段测绘：标题、类目属性、规格（**拼多多的规格是两级：规格名 + 规格值**，与淘宝的 SKU 表不同）、
  价格与库存、图片（主图/轮播/详情）、运费模板、发货时间、上架方式（立即上架/放入仓库）。
- 每个字段产出：选择器 / 读写方式 / 证据等级 / 反例（什么样会读错）。
- 判据：一张"字段 → 证据等级 → 复现命令"的表，`unknown` 项全部进阻塞项。

### M2 图片空间与上传（先只读，后协议化）
- 盘点图片空间：目录层级、文件列表、单图 URL 与 id 的来源（DOM 还是平台自己的响应）。
- **优先走"读平台自己的响应"**（淘宝那轮的教训：DOM 是虚拟列表，读不到 ≠ 不存在；
  用错判据会重复上传）。
- 上传：先只用**真实表单**路径；协议化（若有 upload.api）必须先取证再实现，且要过写授权门。
- 判据：能"按名字+内容身份"确认某张图在不在云端，且**读不到时拒绝重传**。

### M3 填写（`fill_only`，停在提交之前）
- 从本应用已有的商品资料 + 白底图产物出发填完整页；每步填完**回读校验**。
- 与抖店/淘宝共用：`src/` 的商品数据、白底图（`白底图/`、`SKU_1x1/`、`白底图.jpg`）、发布安全门。
- 判据：一次运行把页面填满并给出逐项回读证据，**不点提交、不保存**（除非显式要求）。

### M4 保存草稿
- 单独一步、单独授权；保存后回读确认（草稿列表里能看到）。

### M5 提交上架（可选，最后做）
- 只在显式解锁提交权限后才允许；需要有"提交前自检清单"（必填项、图片数、价格库存、类目）。
- 判据：能在**明确授权**下完成一次真实提交，且任务记录里写清"提交了什么、依据是什么"。

|---|---|---|

| 规格两级模型与现有 SKU 数据的映射 | `candidate` | M3 用真实商品试填，映射对不上就报缺口不猜 |

## 六、里程碑顺序与"什么时候可以停"

**M0 → M1 → M2 → M3** 是主干；**M4、M5** 各自独立，做不做取决于你是否要"真保存/真上架"。
每个里程碑结束都要能回答一句话：「这条链路现在到哪一步是 `verified`，哪一步还只是 `candidate`」。

## 七、已定的三件事（2026-10-10 确认）

1. **提交边界**：只做到「**填满不提交**」，即 **M0–M3**。M4（保存草稿）与 M5（真上架）
   本次不做，各自独立立项时再开；`fill_only` 路线与抖店/淘宝一致（`stop_before_submit=True`）。
2. **店铺范围**：**多店铺**。因此 M0 必须做两件事——
   - 读**店铺身份**（店铺 id / 名称 / 主体），且要与登录态绑定，参照 `src/shop_session.py` 的实测做法；
   - **按店铺隔离**：一个店铺一个 Chrome profile + 一个调试端口（9335 起，逐店 +1），
     任务与账本按店铺分区，绝不共用登录态或图片空间索引。
   已发布的店铺列表要以平台自己的响应为准，**不靠界面文字猜**。
3. **图源**：先按「沿用现有采集 + 白底图产物」推进（`白底图/`、`SKU_1x1/`、`白底图.jpg`）。
   若拼多多另有一套图，只需在 M3 换一个输入适配层，不影响 M0–M2 的结论。

### 多店铺带来的额外验收项

| 项 | 判据 |
|---|---|
| 身份读取 | 能列出当前 profile 下已登录的店铺，并给出**平台侧依据**（不是界面文字） |
| 隔离 | 切店后图片空间、草稿、任务记录互不串；账本按店铺分区 |
| 登录失效 | 单店失效不影响其它店；失效时的报错要指明是哪个店 |
