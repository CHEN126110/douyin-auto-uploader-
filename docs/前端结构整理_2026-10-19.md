### 约定（以后加代码按这个来）

1. **请求只走 `services/api.ts`**。组件 / composable 里不要 `import axios`、不要 `fetch`、不要写死 `127.0.0.1:5001`；
   要后端地址用 `BACKEND_URL`，要整理错误用 `apiErrorMessage / apiErrorStatus / apiErrorRejectedExplicitly`。
2. **设置页的表单状态不是全局状态**：`SettingsPanel` 创建三份模型（`usePricingSettings()` 等），通过 `model` prop 传给各 Tab，
   Tab 里用 `toRefs(props.model)` 就地编辑。要新增设置项：改对应 composable 的 `applySettings / buildPayload`，再改 Tab 模板。
   「高级集成」「关于」是只读页，数据自己持有，不参与保存。
3. **主页 composable 之间不靠全局变量**：依赖都从参数传入（`uploadBusy`、`formData`、`monitor`…），装配顺序写在
   `ProductManager.vue` 的 `<script>` 里。发布进行中所有会改数据的操作都要看 `uploadBusy` 让路。
4. **发布的安全顺序别动**（`usePublishFlow.ts` 开头的注释）：校验商品与账户 → 「直接发布」必须人工确认店铺 →
   存盘并拿到后端确认的版本号 → 才启动任务 → 交给 `useUploadTaskMonitor` 跟进。
5. `auto-imports.d.ts`、`components.d.ts` 是 unplugin 自动生成的；这次它因为新组件多了几行，是插件生成的，不是手改。

## 三、拆分的做法（为什么可以说「没变」）

- **模板和样式是机械搬迁的**：模板按行区间原样截取、样式按顶层规则块原样搬运（脚本生成，不是手抄），
  只有变量引用方式变了（`toRefs`）；原样保留的 6 条**拆分前就没被模板用到**的样式规则已标注 `[未使用]`，清理另做。
- **函数体逐字搬迁**：主页 composable 的函数体是按行号从原文件切出来的，只有两处改写：重复 5 次的 axios 错误整理换成
  `apiErrorMessage(error)`；淘宝启动失败分支里的两处 axios 判断换成 `apiErrorStatus / apiErrorRejectedExplicitly`。
- **DOM 结构不变**：Tab 组件和子区块都是多根节点（片段），不多包一层 `div`，所以 `.settings-section:last-child`
  等依赖兄弟关系的样式照常生效。
- **两个展示组件保留了原有的样式作用域**：`PricingResultsDialog` 的样式仍然是**非 scoped**（拆分前就是全局样式）。
  其中写在 `.pricing-results-dialog` / `.pricing-table` 里的 `:deep(...)` 在非 scoped 样式里浏览器不认，**拆分前就是无效规则**，
  原样保留（改成生效会改变外观），文件里有注释说明。

## 四、关于「16 处绕过 api.ts」

动手前 grep（`axios|fetch(|127.0.0.1:5001`）在 `api.ts` 之外命中约 20 行，**真正的 HTTP 请求只有 1 处**：

| 类别 | 处数 | 处理 |
|---|---|---|
| 真请求：`updater.ts` 里 `fetch(.../internal/update-readiness)`（连带自己再定义一份 `BACKEND_URL`） | 1 | 收进 `api.getUpdateReadiness()`（5 秒超时、不打印控制台错误，行为同前） |
| 手拼的后端图片地址：设置页水洗标预览 | 1 | `api.automationWashLabelPreviewUrl()` |
| 写死 `127.0.0.1:5001` 只用于界面展示 / 默认值（`defaultAppInfo.backend_url`、`backendUrl` 兜底） | 2 | 改用 `BACKEND_URL` |
| 组件里 `axios.isAxiosError(...)` 类型判断（`ProductManager` ×7、`ShopStatusBar` ×2、`SettingsPanel` ×1、`TaobaoPublishPanel` ×1） | 11 行 / 4 文件 | 收进 `apiErrorMessage / apiErrorStatus / apiErrorRejectedExplicitly`，组件不再 import axios |

另有几处直接读 `error.response.data.msg` 的写法（`SettingsPanel` 取模型列表 / 测试连接、`productStore`、`WhiteBgPanel`、`CaptureSection`）：
它们取 `msg` / `message` 的**优先级与统一函数不同**，换成统一函数会改变提示文字，所以没动，仍按原样。

`AppInfo` 类型原来在 `api.ts` 和 `SettingsPanel.vue` 里各写了一份，而且 `api.ts` 那份漏了 Rust `get_app_info` 实际返回的
`bundled_node_path / bundled_node_exists`；现在统一放在 `types/index.ts`。

### 有意的差异（只有这两处）

1. **设置页切换 Tab 时滚动位置一律回到顶部。** 5 个 Tab 共用同一个滚动容器。实测拆分前：从左往右切 Tab 总是从头开始；
   往左切则停在「被新内容高度截断」的位置（例如在「自动化」里往下滚，切到「价格」会停在价格页的底部）。
   拆分后各 Tab 内容不再在每次切换时被整体重渲染，如果不处理，滚动位置会一路保留，从长 Tab 滚下去、切到短 Tab 再切回来，
   新 Tab 会停在半截。所以 `SettingsPanel.vue` 里加了 `watch(activeTab) → 容器回顶`（`tabsBodyRef`，有注释）。
   效果：往右切与拆分前一致；往左切变成回顶（更合理，但严格说与拆分前不同）。
2. **自动更新前的「后台是否空闲」检查，网络层错误的英文原文略有不同**：原来用 `fetch`，现在走 axios。
   后端回非 2xx 时仍是同一句中文「无法确认后台任务状态，请稍后重新更新」；断网 / 超时时，界面里「更新失败：…」后面的
   技术原文由 `Failed to fetch` / `TimeoutError` 变成 `Network Error` / `timeout of 5000ms exceeded`。
   （这条路径需要 Tauri 的 `check()` 才能走到，浏览器里没法实测，靠代码对照。）

**这次修复带来的两点取舍（不是缺陷，但要知道）：**

1. 读不到店铺时，下拉里留着的是「上一次读到 / 保存的名单」，换过店铺的话可能是别家店的。页面会同时显示「读取运费模板失败：…」，且「已选模板在这家店里不存在」的警告只在读取成功时才会出现——和修复前一样。要彻底解决得按店铺分别缓存，这次没做。
2. 读取成功后刷新出来的新名单不再算「用户改动」，所以不会因此提示保存；它只在用户因为别的原因点保存时一并写回。名单只是兜底缓存，不影响发布时用的是哪个模板。

**对照中碰到、与修复无关的噪声（同一版本自己跑两遍也会出现）：** 「清空图片」按钮在清空后偶尔取到不同的文字颜色（渲染时序，A 与 A 也会不同）；页面可见时后台定时器会让 `GET /api/products`、上传 / 淘宝任务轮询的次数不同（页面加载触发的请求次数完全一致）。

**没重跑的：** 主页、发布流程、采集入口场景——这次只动了设置页的两个文件。真实平台与 Tauri 壳里的操作同样没验证。
