## 1. 最重要的一条：安装包差点被撑到三倍

### 事实

`tauri.conf.json:44` 的资源映射是：

```json
"resources": { "sidecar/*": "./", ... }
```

`sidecar/*` 是**整目录照单全收**。实测 `tauri-app/src-tauri/target/release/` 里同时存在
`python-backend.exe` 和 `python-backend.exe.bak`，证明采集阶段确实把整个目录复制了过去。

那个目录里当时躺着两个「备份」：

| 文件 | 大小 | 实测可压缩性 | 后果 |
|------|------|--------------|------|
| `python-backend.exe.bak`（2026-09-06） | 85.37 MB | zlib 98.6% / lzma 98.5% | +85 MB |
| `python-backend.exe.known-good-20260924`（2026-10-01 回滚备份） | 142.72 MB | zlib 98.7% / lzma 98.5% | +143 MB |

**关键点：PyInstaller onefile 产物内部已经压过一遍，NSIS 的 LZMA 对它几乎无效**——
所以这两个文件进安装包是**接近 1:1** 的，不是「压一压就小了」。

### 已做

1. `python-backend.exe.bak`（85.37 MB）按仓库约定回收到
   `项目备份 禁止改动使用 只参考/recycle_bin/RECYCLE_陈旧sidecar构建产物_2026-10-01/`（附 README）。
2. `build_sidecar.py` 新增 `prune_output_dir()` + `verify_output_dir()`：
   - 白名单之外的文件**搬走而不是删**——移到 `tauri-app/_sidecar_backups/`（回滚备份照样留着）；
   - `data/`、`build/` 属于可再生的运行/构建残留，直接删；
   - 收尾自检：`sidecar/` 里只要还有白名单外的文件，**构建直接报错**，不再「默默打进安装包」。
3. `python-backend.exe.known-good-20260924`（142.72 MB）已由新逻辑搬出打包目录。
4. 两个**经 SHA256 验证的纯重复副本**已删除（各有一份保留件在别处）：
   - `target/release/python-backend.exe.bak`（与 recycle_bin 里那份哈希一致）→ 回收 85.37 MB
   - `_sidecar_backups/...known-good-20260924.target-release-copy`（与保留件哈希一致）→ 回收 142.72 MB

### 为什么 `data/` 能删

打包运行时 `tauri-app/src-tauri/src/main.rs:153` 把 `DOUYIN_DATA_DIR` 指到
`%LOCALAPPDATA%\com.dyin.sock-publisher`，资源目录里那份 `data/` 永远读不到
（`src/runtime_paths.py:45-54`）。它只是有人在那个目录里手工跑过 exe 留下的。

## 2. sidecar exe 瘦身：已落地 4.64 MB，剩下一块 114.79 MB 的硬骨头

### 实测数据

用 `PyInstaller.archive.readers.CArchiveReader` 直接读 exe 内部归档：

| | 旧 exe（2026-09-24） | 新 exe（2026-10-01 重建） |
|---|---|---|
| 磁盘体积 | 142.72 MB | **138.08 MB** |
| 归档条目 | 630 | 584 |
| 解压后 | 354.99 MB | **345.45 MB** |
| `Pythonwin` | 2 条 / 6.50 MB | **0 条** |
| `win32ui` | 1 条 | **0 条** |

> 这次重建是**用改过的 `build_sidecar.py` 跑的**（`python-backend.spec` 21:19 重生成、
> exe 21:20 产出）。瘦身来源就是我加进 `EXCLUDED_MODULES` 的 `Pythonwin` / `win32ui`。

### 本轮对 `build_sidecar.py` 的改动

1. **删掉 `HIDDEN_IMPORTS` 里 14 个标准库名字**（`dataclasses`/`typing`/`pathlib`/`json`/
   `logging`/`threading`/`queue`/`uuid`/`hashlib`/`base64`/`traceback`/`shutil`/`tempfile`/
   `subprocess`）。只要被 import 就一定会被收集，写在那儿没有任何作用，只会误导后来人。
2. **补 7 个排除项**，每个都有证据：
   - `PySide6` / `shiboken6`：**预防性**。两份 `requirements.txt` 都装着 PySide6，而
     `app.py:140` 是用 `importlib` 动态 import `src.gui` 的，静态分析看不见它 → 今天没进包；
     哪天有人加一个静态 import，exe 会凭空涨几百 MB。钉死。
   - `Pythonwin` / `win32ui`：pywin32 的 MFC GUI 壳，全仓只用 `win32api`/`win32con`
     （`src/gui.py:8-9`）。实测已生效，省 4.64 MB。
   - `cv2` / `pandas` / `pytest` / `_pytest`：全仓零引用，防依赖的可选 import 带进来。

### 剩下的 114.79 MB：`llvmlite`（**未实施，需要你决策**）

新 exe 解压后占用前几名：

| 包 | 解压体积 | 是否真的需要 |
|---|---|---|
| **`llvmlite`** | **114.79 MB** | ❌ 只有 `rembg.bg → pymatting → numba` 这条链要 |
| `scipy`（含 `scipy.libs`） | 88.00 MB | ✅ `src/whitebg/*` 用 `scipy.ndimage` |
| `onnxruntime` | 35.12 MB | ✅ matte + CLIP 推理 |
| `numpy`（含 `.libs`） | 26.07 MB | ✅ |
| `PIL` | 12.80 MB | ✅ |
| `skimage` | 9.81 MB | ❌ 只有 `rembg.bg` 的 `post_process()` 要 |

**为什么不能简单地 `--exclude-module numba`：**

- `rembg/bg.py:24-28` 在**模块顶层**就 `from pymatting...` / `from skimage.morphology import ...`，
  而 `rembg/__init__.py` 又 `from .bg import remove`；
- `pymatting` 的 `util/boxfilter.py:3`、`foreground/estimate_foreground_ml.py:2` 等 10 处
  都是顶层 `from numba import njit`；
- 所以 `--exclude-module numba` 会让 `import pymatting` 直接失败 → `import rembg` 失败 →
  **白底图整条链断掉**。

而生产代码其实**从不走这条路径**：`src/whitebg/matte.py:40` 调的是
`remove(work, session=session, only_mask=True, post_process_mask=False)`，
`alpha_matting` 默认 False（不用 pymatting），`post_process_mask=False`（不用 skimage）。

**要拿到这 114.79 MB，只有一条路**：改 `src/whitebg/matte.py`，让它不经 `rembg.bg`
（`rembg/session_factory.py` + `rembg/sessions/base.py` 只需要 onnxruntime），
然后 `--exclude-module pymatting,skimage,numba,llvmlite`。

- 收益：解压后 −124.60 MB，exe 预计再降 **30~45 MB**（DLL 可压缩率约 2.5:1）
- 代价：动的是 `src/whitebg/`——AGENTS.md 明确要求「改 matte 模型后必须重跑 22 张确认转正没退化」
- **我没有做**，因为这是行为改动，而且本沙箱跑不了白底图（见 §6）

## 3. 冷启动性能：每次启动要写 355 MB

### 问题

PyInstaller `--onefile` 的语义是：**每次进程启动，先把 345.45 MB / 584 个条目解压到
`%TEMP%\_MEIxxxxxx`，再开始执行 Python**。这不是「启动慢一点」，是每次冷启动都产生
一份几百 MB 的磁盘写入。

### 实测对照（本沙箱能测到的部分）

| 场景 | 耗时 |
|------|------|
| `python -c pass`（基线） | 49.5 ms |
| **非 frozen：`SIDECAR_MODE=1 python app.py` 起到 Flask 监听** | **0.85 s** |
| frozen onefile exe 冷启动 | **测不到**（见 §6） |

也就是说：**Python 侧本身只要 0.85 秒**，剩下的全部是 onefile 解压开销。

### 已做的两处真实优化

1. **`src/utils.py:15` 的 `flask_jwt_extended` 改成函数内导入**
   - 它整条依赖链只服务 `update_payload()`（`src/utils.py:2069`），而该函数**全仓零调用**。
   - 实测 `import flask_jwt_extended` 单独就要 **329 ms**。
   - 结果：`import src.utils` 从 **673 ms 降到 443.7 ms（−230 ms）**，且行为完全不变。
   - 剩下的 443 ms 几乎全是 `from DrissionPage import ...`（378 ms），那个**没动**——
     utils 里大量函数直接用 `ChromiumPage`/`ChromiumOptions`，改成延迟导入要动十几处，风险不划算。
2. **`src/ops_engine.py:5288` 的 `get_ops_ledger()` 加按路径缓存**
   - 原来每次调用都 `OpsLedger()`，构造里跑 `initialize_schema()`
     （`ops_engine.py:4690-4834`：8 条 `CREATE TABLE IF NOT EXISTS` + 2 次 `PRAGMA table_info` 迁移检查 + 一次连接开关）。
   - `app.py` 里有 **37 个调用点**，其中若干路由（如 1415/1426、1455/1471、1649/1655）**一次请求连着调两次**。
   - 实测：**1.42 ms/次 → 0.35 ms/次（4.0×）**，同一路径返回同一实例。
     `OpsLedger` 不持有连接（`_connection()` 每次开关），所以复用实例是安全的；
     缓存键是账本绝对路径，测试传自定义路径不会串味。
   - 坦白说：**绝对收益只有约 2 ms/请求**，真正省掉的是每个 `/api/ops/*` 请求白跑的两遍建表。

### 建议的下一步（未实施）

把 `build_sidecar.py` 的 `--onefile` 换成 `--onedir`：
启动变成直接加载、不再解压，代价是安装目录里多一个文件夹，NSIS 侧体积基本不变
（本来就压不动 exe）。需要同步改 `src-tauri/src/main.rs:178-182` 的
`sidecar_candidates`（加 `<resource>/sidecar/python-backend/python-backend.exe`）。
**这一项需要真机跑 `tauri build` + 冒烟验证**，本沙箱做不了。

## 4. 代码可维护性与运行期性能

### 4.1 `app.py`（14020 行）：先纠正一个判断

我最初以为 14020 行里一定堆着死代码。**AST 全量分析结果是：0 个未被引用的顶层函数。**
349 个顶层定义、111 个路由，全部活着。所以「轻量化」在这里不成立，能做的是**去重与去通配**。

#### 已做

**① 消灭 `from src.utils import *`（`app.py:198`）**

通配导入的两个实际代价：静态分析看不到真实依赖（少一个 hiddenimport 就得等打包后运行才炸）；
改名/删符号时失效引用不会被任何工具发现。

- 用 AST 算出「app.py 真正 Load 到、且 src.utils 提供」的 **50 个名字**，写成显式括号导入；
- 自动化验证：50 个名字 `src.utils` 全部提供；**全文件无悬空引用**；
- 顺带删掉 3 个真·未使用导入：`OperatingCostInput`、`calculate_operating_profit`、`timedelta`。

**② 收敛 2 处逐字重复的实现**

| 重复位置 | 处理 |
|---|---|
| `_import_capture_product_record`（单品导入）与 `import_capture_result`（店铺批量导入）里的「SKU 图 → 采集结果匹配」逻辑，约 25 行 × 2，逐字相同 | 抽成 `_index_captured_skus()` + `_resolve_captured_sku_match()` |
| `get_settings()` 与 `reset_settings()` 里的设置字段拍平，约 21 行 × 2 | 抽成 `_settings_to_payload()` |

> 注意一个**刻意保留的差异**：`get_settings` 之后还会过 `enforce_no_external_ai_settings`
> 并屏蔽 `model_configs[].api_key`，`reset_settings` 没有。我只收敛「拍平」这一步，
> 没有顺手改净化差异（那会是行为变更）。**但这条差异本身是个安全缺口**，见 §7。

#### 不能做的事（重要约束）

`tests/` 里有 11 个文件是**把 `app.py` 当纯文本读、用 `.split("def xxx")` 断言源码结构**的
（`test_sidecar_upload_safety.py`、`test_upload_brand_safety.py`、`test_publish_stability_fixes.py` 等）。

所以**「把 app.py 拆成多个模块」这条路在当前测试体系下走不通**——一拆，
所有靠 `source.split("def ...")` 定位的断言立刻失效。要拆必须先重写这批测试。
考虑到它们是发布安全门（preflight / 上传 / 无品牌）的唯一回归网，我没有动。

**本轮顺带修了一处因此失效的断言**：`test_publish_stability_fixes.py:205`
原本靠 `line.startswith('from src.utils import _wait_until')` 定位导入行，
通配导入改掉后自然失配。已改成**解析 AST 判断**——不变量（下划线名字必须在显式导入清单里）
没变，还额外钉住了「不许再用通配导入」。

### 4.2 `src/ops_engine.py`（5289 行）

- **`build_product_record_mappings()` 的 O(n·m·L²)**（`ops_engine.py:1216`）：
  内层循环对**同一条 record 标题**反复调 `_match_text()`（逐字符循环），
  外面再套 `SequenceMatcher.ratio()`（O(L²)）。
  已改成「归一化提到循环外」：复杂度降到 O(n·m·L)，**打分逻辑逐字未变**
  （新增 `_similarity_of_normalized()`，`_title_similarity()` 保留为薄封装）。
- **拆分可行性**：AST 扫描 `global`/`nonlocal` = **0 处**，模块级只有 5 个只读常量，
  外部依赖只有 2 个叶子模块（无循环导入）。真正的阻塞是 7 个「跨 3 个以上逻辑域」的助手
  （`_money` 被 9 个域用），且定义位置散落在各段中间。子代理给了按风险从低到高的 9 步拆分顺序，
  **本轮未执行**（收益是长期可维护性，风险是回归，应该独立排期）。

## 7. 发现但**没有动**的问题（交给你决定）

按严重程度排：

1. **`reset_settings` 回传 `api_key` 明文**（`app.py` `reset_settings` → `_settings_to_payload`）。
   `get_settings` 会屏蔽它，`reset_settings` 不会。前端 `api.ts` 的 `resetSettings` 封装**当前无调用方**，
   所以还没实际暴露。改它是行为变更，我没动。
2. **`src/trending_keywords_scraper.py:447` 用 `.seconds` 当缓存年龄**。
   `timedelta.seconds` 只有 0–86399，超过 1 天就会回绕 → **超过 1 天的缓存可能被当成新鲜的**，
   一直返回旧关键词。同文件 `:530` 已经是正确的 `.total_seconds()`。这是**正确性 bug**，但属行为变更。
3. **`src/chrome_installer_gui.py` 打包后必然 ImportError**：它 `import PySide2`
   （`chrome_installer_gui.py:12-16`），而 `build_sidecar.py` 的 `EXCLUDED_MODULES` 排除 `PySide2`。
   它既不在 hiddenimports 里、也没有任何调用方，只是因为整个 `src/` 目录被 `--add-data` 打进包才存在。
4. **17 个全仓零引用符号**，包括 `src/utils.py:4299 _wait_for_sku_upload_settled`（95 行等待逻辑从未被调用）、
   `src/utils.py:2038-2076` 整块 v1.0「淘宝商品信息采集系统」遗留（`is_valid_phone_number` 的正则里还留着
   mojibake 尾巴 `r'^1[3-9]\d{9}dollar'`）、`ops_engine.py:1469 _float_value`。
   另外 `people_goods_scene.py` / `title_engine.py` / `category_attr_suggester.py` 三个模块生产侧零引用
   （只在 tests 里），但看起来是「打算接但没接上」的离线标题生成链路——**建议走 recycle_bin，不要直接删**。
5. **`git diff` 被行尾支配**：`app.py` 全文件 CRLF，而索引里是 LF，
   导致 `git diff --stat` 显示 26964 行改动，加 `--ignore-cr-at-eol` 后只剩 1464 行。
   **这意味着现在任何一次代码审查都不可读**。加一个 `.gitattributes`（`* text=auto eol=lf`）
   + 一次 renormalize 提交能根治，但那是个大提交，建议单独排期。
6. **前端 4 处常驻轮询**（`App.vue:116` 30s、`ProductManager.vue:745` 15s、
   `CaptureSection.vue` 已降到 30s、`ShopStatusBar.vue:208` 15s），
   空闲态合计约 15 次/分钟。我只改了最贵的那处（原来 5s），其余按「文档已定方案」留给后续。
7. **`.trae/documents/前端性能优化方案.md` 与实际不符**：文档的「改动 2（动态间隔轮询）」
   实际只做了一半（固定间隔从 5s 提到 15s/30s，没有动态调度）。建议同步文档。
