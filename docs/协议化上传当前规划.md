# 协议化上传当前规划

创建日期：2026-04-27
更新时间：2026-05-07

本文是协议化上传研究与后续实现的稳定入口。后续不再把“抓到接口”直接等同于“正在做协议自动化”，而是统一按本文约定的定位、阶段和里程碑推进。

## 当前定位

当前项目**还没有进入完整协议自动化执行阶段**。

更准确的定位是：

- 正式上传主路径仍是 DOM 自动化流水线。
- `protocol_publish` 当前主要承担：
  - 协议证据收集
  - 字段与 envelope 审计
  - dry-run 预检
  - 受控 replay 与风控边界研究
- 这些能力属于“协议自动化前置研究层”，不是“完整协议上传引擎”。

现有 DOM 自动化流水线仍是正式上传主路径。协议化能力必须以独立实验模块推进，不能直接替换正式上传按钮。

## 什么叫有价值进度

后续每一轮工作必须至少满足下面一条，否则不值得继续投入：

- 缩小一个关键不确定性。
- 排除一条错误方向或错误假设。
- 把某个字段或阶段从“候选推断”推进到“已实证”。
- 为后续“阶段性协议执行器”补齐真实输入、真实输出或真实校验规则。
- 明确某条接口链不是必经链，减少后续误判。

不再把以下行为视为默认有价值进度：

- 只重复点击已有预览看是否发请求。
- 在已知高风控入口上继续堆低价值变体。
- 把候选接口默认写成必经链。
- 继续扩大证据堆积，但不收口成阶段结论或执行边界。

## 当前阶段判断

当前研究已经证明：

- `addWithSchema` / `editWithSchema` 是页内**所有业务写入的统一入口**。不存在独立
  的价格库存、SKU 结构或类目属性的协议写入端点。
- `batchupload`、`34智能裁剪`、`视频一键生成`、`IsWhiteBackgroundPic` 是独立于
  `addWithSchema` 的媒体链协议调用。
- 对至少一个成功样本，完整发布链表现为：
  - `batchupload`（媒体上传）
  - AI 任务/白底检测
  - `addWithSchema`（最终提交，承载所有业务字段）
- `saveMaterial`、`submitWhiteImg` 在该成功样本中未被观察到，当前不应预设为必经链。
- `editWithSchema` 编辑态 replay 已明确更适合做风控边界研究，不适合作为当前协议落地
  主突破口。

2026-05-04 关键修正：

- 先前 P1/P2/P3 的"独立阶段执行器 + 独立 API 调用"假设已被证伪。正确的协议自动化
  架构应该是"**body 构造器模型**"：各阶段负责构造 `addWithSchema` body 的正确子结构，
  最终由单一 `addWithSchema` 调用完成写入。
- 这意味着协议自动化的价值不在于"找到一堆小接口分别调"，而在于"**能从本地商品数据
  稳定构造一份与真实请求体一致的 body，且在每个字段上都能解释来源和校验规则**"。

## 重新排序后的阶段路线

### P0：保留研究基础层

目标：持续保留并精炼现有研究资产，而不是继续扩散。

保留内容：

- CDP probe / capture / blocked capture
- 字段证据矩阵
- dry-run 与本地预检
- replay 工具与风控边界实验

完成判据：

- 文档口径一致。
- 每条新证据都能回写到 blocker 和矩阵。
- 不把研究结论误写成正式能力。

### P1：价格库存协议数据构造器（已修正）

2026-05-04 最新研究结论：**价格库存没有独立 API 入口**。

证据链：

- Webpack 模块 `51313` 已确认页内所有写入只走 `addWithSchema` / `editWithSchema`，不存
  在 `saveSku` / `savePrice` / `batchSaveSku` 等独立端点。
- 历史探针 `price_stock_probe_save_draft_20260420.json` 与
  `price_stock_probe_roundtrip_20260420.json` 均证实：在价格库存 tab 点击"保存草稿"，
  请求体仍是完整 `editWithSchema`，`sku_detail[].price` 与 `sku_detail[].stock_info`
  嵌在 `schema.model` 中一同发送。
- 真实成功上传 deep capture 样本中，`addWithSchema` 同样携带完整 `sku_detail`（含
  `price` 与 `stock_info`），没有其它独立价格库存请求。

这意味着先前 P1 的"独立阶段执行器 + 独立 API 调用"假设不成立。价格库存的协议化路径应
修正为：**构造正确的 `sku_detail` 价格库存值，作为最终 `addWithSchema` body 的一部分**。

修正后的目标：

- 明确 `sku_detail[].price` 的格式、精度、校验规则。
- 明确 `stock_info` 真实字段（当前已确认 `stock_num`；`stock_inc_num` 等仍为候选）。
- 把本地商品价格库存数据稳定映射成 `sku_detail` 片段，供最终提交阶段使用。
- 不再要求"独立 API 调用 + 独立结果校验"。

完成判据：

- 本地商品价格 / 库存能稳定映射为 `sku_detail` 行中的正确值。
- 在真实 `addWithSchema` deep capture 样本中，该映射结果与实际请求体一致。
- 不涉及通过网络发送协议请求。

仓库里现有 `stages/price_stock_runtime.py` 的"协议写入"分支仍属旧研究路径，受
`DYIN_PRICE_STOCK_ENABLE_SAVE_DRAFT_PROBE` 门禁保护，不能视为已完成执行器。

### P2：SKU 结构协议数据构造器

目标：

- 明确 `spec_detail`、`spec_values`、`sku_detail`、`spec_detail_ids`、SKU 组合 ID
  的真实规则。
- 搞清规格轴、规格值、SKU 行之间的协议关系。
- 构造正确的 `spec_detail` 与 `sku_detail` 片段，作为最终 `addWithSchema` body 的
  一部分。

注：与 P1 相同，SKU 结构也没有独立写入 API。`spec_detail` 与 `sku_detail` 同样是
`addWithSchema` body 的子结构，不是独立接口。

完成判据：

- `spec_detail/sku_detail` 不再只是形状级证据，而是能支撑真实 body 构造。
- SKU 组合 ID、规格值 ID 规则至少对目标类目闭环。
- 不涉及通过网络发送协议请求。

### P3：高频类目属性协议数据构造器

目标：

- 优先覆盖高频且规则明确的属性，而不是一次性追所有属性。
- 首批优先：
  - 品牌
  - 适用性别
  - 筒高
  - 面料材质

注：`category_properties` 同样是 `addWithSchema` body 的子结构，不是独立写入接口。
但属性映射本身不依赖网络调用，可以在本地完成从 schema 到值的映射闭环。

完成判据：

- 字段映射来自实时 schema，而不是硬编码。
- 至少一个目标类目上可稳定解释 `category_properties` 中这几个字段的值来源与结构。
- 不涉及通过网络发送协议请求。

### P4：媒体链映射收口

目标：

- 媒体阶段继续研究，但不再占据当前主目标。
- 重点搞清：
  - `main_image_three_to_four`
  - `white_background_pic`
  - `main_pic_video`
  - `description`
  - `qualification`

当前优先问题：

- `main_pic_video.resource_id` 与 AI 视频任务结果的精确映射。
- `submitWhiteImg` 与 `saveMaterial` 的真实触发条件，而不是假设它们必经。
- `description` 和 `qualification` 的最终可接受结构。

完成判据：

- 至少能回答“这个字段从哪来、通过哪条链进入提交、服务端接受条件是什么”。

### P5：最终提交协议化评估

目标：

- 在前述数据构造器均已产出正确的 body 子结构后，评估是否进入 `addWithSchema` 真实
  写入执行。

当前已知：`addWithSchema` 是唯一写入入口，它承载了所有业务数据（属性、SKU、
价格库存、媒体 URL、资质、详情等）。因此"最终提交"不是一个独立阶段，而是所有
body 构造器的汇聚点。

进入前提：

- `spec_detail` / `sku_detail` / `category_properties` 的值来源可解释且与真实
  deep capture 样本一致。
- 媒体字段（`pic`、`main_image_three_to_four`、`white_background_pic`、
  `main_pic_video`）的来源链已明确。
- 关键 blocker 明显减少。
- 不再依赖"猜 body 再试"的方式推进。

## 明确停止的方向

以下方向暂停作为主目标：

- 把 `editWithSchema` 当成主要落地入口继续硬撞。
- 把 `saveMaterial` / `submitWhiteImg` 预设成全局必经链。
- 为了追最终提交而长期忽视更适合先协议化的 `价格库存 / SKU / 高频属性`。
- 用大量新证据继续扩写文档，但不沉淀成阶段执行器目标。

## 当前边界

必须继续保留的边界：

- 研究阶段不能改正式主流水线。
- 未闭环协议不能接正式上传按钮。
- dry-run 不能当真实提交能力。
- 不绕过登录、验证码、风控、平台权限或审核规则。
- 不保存 cookie、token、手机号、店铺敏感信息或完整签名 URL。

## 下一轮只做什么

下一轮只允许从下面三项里选**一个**高价值目标：

1. 对齐 `sku_detail` 中价格/库存值与真实 `addWithSchema` deep capture 样本，明确格式、
   精度以及 `stock_info` 真实字段。
2. 对齐 `spec_detail/sku_detail` 中规格值 ID 与 SKU 组合 ID 与真实 deep capture 样本。
3. 明确 `main_pic_video.resource_id` 的真实来源链。

当前已经确认的事实：

- 价格库存、SKU 结构、类目属性都没有独立写入 API。所有写入统一走
  `addWithSchema` / `editWithSchema`。
- 因此协议自动化的正确路径不是"为每个阶段找独立接口"，而是"正确构造
  `addWithSchema` body 的每个子结构"。
- 只有媒体上传 (`batchupload`) 和 AI 任务链（智能裁剪、视频生成、白底检测）是
  独立于 `addWithSchema` 的协议调用。

## 当前最大缺口

从"协议自动化研究"走向"可构造完整 `addWithSchema` body"，当前最大缺口是：

- `spec_detail` 中规格值 ID 与 `sku_detail` 中 SKU 组合 ID —— 由平台在规格填写阶段生成，无法离线构造。这是 body 构造器模型唯一的硬阻断点，其余字段均可本地构造
- `stock_info` 真实字段全貌（当前仅确认 `stock_num` 出现在请求体中；其他候选字段未见使用）
- `category_properties` 中仍有部分属性未覆盖；`241`(厚薄) 已支持基于 schema `optionMatches.keyword` 的精确标题命中推断，但只对标题中出现且能唯一命中的值生效，不能外推出 `厚款/常规款` 的通用规则
- 媒体字段 (`pic`/`main_image_three_to_four`/`white_background_pic`/`main_pic_video`) 的值来源链 —— 来自 batchupload + AI 任务，URL 可离线构造但资源 ID 不可
- `description` 的 HTML 格式模板

已排除的 blocker：
- `qualification` 在此成功样本中为空 `{}`，说明此类目非必填
- `sku_detail` 格式（stock_info 嵌套、sku_status、confirm_no_barcode）已对齐
- `delivery_delay_day/reduce_type/reference_price_enable/short_product_name` 已可由真实 capture 自动提取并注入 dry-run，不再属于“完全缺失字段”
