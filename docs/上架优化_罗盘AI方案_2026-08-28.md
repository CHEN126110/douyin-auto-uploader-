# 上架数据优化：罗盘信号 + DeepSeek + Harness（需求具体化）

> 状态：**方案待确认**，尚未实现任何代码。
> 本文把「加入 DeepSeek + Agent + Harness 优化上架产品数据」这一模糊需求具体化为可执行方案。

## 1. 一句话目标

**用电商罗盘的真实市场信号（而非凭空想象）驱动上架商品的标题与类目属性优化，
由 DeepSeek 生成候选，经自动质量门筛选后，以「建议 + 依据」的形式交给人工逐条确认。**

现有标题优化是「基于人货场画像想出来的」，没有真实市场数据支撑；
罗盘握有真实信号（什么词有流量、竞品在卖什么、什么排名高），两边未打通。
**本方案要接的就是这条数据链路，并为 LLM 输出加上自动质量门。**

## 4. 数据契约（`D:\抖店` → 本项目）

导出文件：`compass_insights.json`（放到约定目录，本项目只读）。

```jsonc
{
  "schema_version": 1,
  "exported_at": "2026-08-28T20:00:00+08:00",
  "shop": "new_shop",
  "category": "服饰内衣 > 袜子 > 中筒袜",
  "search_terms": [                      // getSearchRank / getKeywordSearch
    { "word": "中筒袜女", "search_index": 12345, "competition": 0.42, "trend": "up" }
  ],
  "hot_products": [                      // getMarketHotSaleRank
    { "title": "...", "price": 19.9, "sales": 5000, "shop_type": "旗舰店" }
  ],
  "competitors": [                       // getCompetitorList
    { "title": "...", "price": 15.9, "main_attrs": { "面料材质": "棉" } }
  ],
  "own_products": [                      // getProductRank（自家表现）
    { "product_id": "...", "title": "...", "impressions": 0, "ctr": 0, "cvr": 0 }
  ],
  "shelves": { }                         // getShelvesAnalysis（可选）
}
```

**时效性要求**：本项目读取时校验 `exported_at`，超过 N 天（建议 7 天）在 UI 上标注「数据可能过期」，
但不阻断使用（避免因数据陈旧完全用不了）。

## 5. 模块设计（本项目侧新增）

| 模块 | 职责 |
|---|---|
| `src/compass_insights.py` | 读取 + schema 校验 + 时效判断；文件缺失/损坏时安全降级为「无罗盘信号」，不影响现有发布流程 |
| `src/listing_optimizer.py` | 优化引擎：罗盘信号 + 商品当前数据 → 构造 prompt → DeepSeek → 候选 |
| `src/optimizer_harness.py` | **质量门**（见下节） |
| `/api/optimize/listing`（sidecar） | 入参商品 id，返回「建议 + 依据 + 质量门结果」 |
| 前端建议面板 | 展示建议、依据（命中了哪个词/搜索量多少）、逐条采纳 |

## 6. Harness = 自动质量门（本方案的关键）

不是「让 LLM 自由发挥然后人工肉眼看」，而是**每条候选都必须先过机器验收**，不合格的不呈现：

| 检查项 | 实现 | 不通过后果 |
|---|---|---|
| 无品牌合规 | 复用 `audit_no_brand_title_text` | **直接丢弃**（合规硬约束） |
| 极限词 | 现有禁用词表 | 直接丢弃 |
| 标题长度 | 平台上限 | 直接丢弃 |
| 信号覆盖度 | 命中高搜索量词的数量/权重 | 用于**排序**，低分靠后 |
| 与原标题的差异度 | 避免「改了等于没改」 | 过低则丢弃 |
| 类目属性合法性 | 属性值必须在平台选项内（可复用材质采集缓存的思路） | 直接丢弃 |

Harness 的评估结果需**可回溯**（记录每条候选的得分与丢弃原因），便于判断是 prompt 问题还是数据问题。

## 7. AI 政策调整（精确、最小改动）

用户已确认放开经营数据。**但不应粗暴地把 `ops_engine.AI_POLICY` 整体改掉**——
那是运营决策（日计划/复盘/利润阶梯）的约束，与上架优化是两个场景。

建议做法：

- `ops_engine.AI_POLICY` **保持不变**：运营决策继续只用本地规则（既有测试与约束不受影响）。
- 新增独立的 `LISTING_AI_POLICY`，显式声明：上架优化场景允许使用罗盘数据 + DeepSeek，
  并列明允许出境的数据类别。
- `/api/ops/ai-policy` 同时暴露两个政策，保持透明可审计。

## 8. 分阶段实施

| 阶段 | 内容 | 可验证产出 |
|---|---|---|
| P0 | 数据契约落地：`D:\抖店` 侧导出器 + 本项目 `compass_insights.py` 读取 | 能读到真实罗盘信号并在日志打印摘要 |
| P1 | Harness 先行（**故意先于 LLM**） | 用现有标题跑一遍，验证质量门能正确拦截违规标题 |
| P2 | `listing_optimizer` 接入 DeepSeek，产出标题候选 | 对单个商品产出通过质量门的候选 + 依据 |
| P3 | 前端建议面板 + 逐条采纳 | 人工确认后写入待上传数据 |
| P4 | 扩展到类目/属性/卖点 | |

> **为什么 Harness 先于 LLM**：先有验收标准，才能判断 LLM 输出是否真的更好；
> 否则只能靠肉眼感觉，无法回归、无法迭代 prompt。

## 9. 验收标准

- 罗盘数据文件缺失时，现有发布流程**完全不受影响**（降级为无信号，不报错、不阻断）。
- 每条建议都能展示**具体依据**（命中词 + 搜索量），而不是「AI 觉得更好」。
- 违反无品牌/极限词的候选**不可能出现在 UI 上**（被 Harness 拦掉，并有记录）。
- 人工不确认则不改动任何待上传数据。
