# 协议化上传多类目适配规划

创建日期：2026-04-22
更新时间：2026-04-27
当前角色：协议化上传多类目适配与协议证据优先级参考文档

## 目标

协议化上传不能只适配袜子类目。未来上传来源包括淘宝、天猫、1688 和本地文件结构，发布目标仍然是抖店商品创建页。

核心目标：

- 用户选择或识别类目后，实时读取平台真实 schema。
- 类目属性、规格轴、SKU 表列、运费模板、上下架配置都来自接口，不写死在本地。
- 上传前先生成 dry-run 校验报告，缺字段就阻塞并给出明确原因，不用兜底代码掩盖。
- 正式上传仍保留现有 DOM 流水线，协议化阶段成熟后再逐步替换。

## 本轮实证结论

新增只读工具：`cdp_fxg_category_matrix_probe`。

新增设置页运行时选项工具：`cdp_fxg_runtime_options_probe`。

2026-04-27 补充结论：

- 当前下一步不再扩大 DOM 流水线改动，也不优先做设置页大改。
- 当前优先级是补协议接口证据：`addWithSchema` 最终提交体、`spec_detail/sku_detail`、价格库存、图片上传、详情图、资质/合格证。
- 所有写接口证据只能走本地截停，不能让保存、提交、素材送审请求真正到平台服务端。
- dry-run 已开始输出完整 `proposed_submit_model` 和字段验证报告，但 `submit_enabled` 仍必须保持 `false`。

测试类目：

- `服装 > 内衣裤袜 > 袜子 > 长筒袜`
- `服装 > 内衣裤袜 > 袜子 > 短袜`
- `3C数码及配件 > 手机及配件 > 手机保护套/壳`

已确认差异：

| 类目 | 必填类目属性 | 规格轴 |
| --- | --- | --- |
| 长筒袜 | 品牌、适用性别、筒高、面料材质 | 颜色分类、码数、筒高长度 |
| 短袜 | 品牌、筒高、适用人群、适用性别、面料材质 | 颜色分类、码数、筒高长度、规格 |
| 手机壳 | 品牌、型号、生产厂家 | 颜色分类、适应机型 |

风险结论：

- 类目属性差异是常态，不能硬编码 `筒高`、`面料材质`、`品牌`。
- 规格轴名称和数量会变化，不能固定为 `颜色分类 + 码数`。
- SKU 表列目前测试中 key 基本一致，但仍应按 `price`、`stock_info` 等列 key 处理，不能按列序号。

## 运行时配置读取实证

`cdp_fxg_runtime_options_probe` 已在真实登录页面中验证，可以从同一套平台运行时读取以下配置能力：

- 当前命中类目和候选类目。
- 必填类目属性、属性可选值、材质含量模板。
- 规格轴和 SKU 表列。
- 真实运费模板列表和当前值。
- 发布控制字段：配送方式、上下架、销售渠道、商品类型、预售类型。

已确认长筒袜类目中可读取：

- 上下架字段 `start_sale_type`：包含“上架”和“下架”。
- 商品类型字段 `product_type`：包含“普通商品”和“虚拟商品”。
- 预售字段 `presell_type`：包含“现货”和“现货预售混合”。
- 配送方式字段 `pickup_method`：可读到平台返回的配送选项。

结论：设置页后续可以从真实接口渲染“类目属性默认值、运费模板、上下架策略”等配置，不需要继续在前端或 Python 中写死袜子类目的默认值。

运行时配置多类目矩阵已验证：

| 类目关键词 | 命中类目 | 必填属性 | 规格轴 | 运费模板 | 上下架 | 预售/发货模式 |
| --- | --- | --- | --- | --- | --- | --- |
| 长筒袜 | 服装 > 内衣裤袜 > 袜子 > 长筒袜 | 品牌、适用性别、筒高、面料材质 | 颜色分类、码数、筒高长度 | 可读取 | 可读取 | 现货、现货预售混合 |
| 短袜 | 服装 > 内衣裤袜 > 袜子 > 短袜 | 品牌、筒高、适用人群、适用性别、面料材质 | 颜色分类、码数、筒高长度、规格 | 可读取 | 可读取 | 现货、现货预售混合 |
| 手机壳 | 3C数码及配件 > 手机及配件 > 手机保护套/壳 | 品牌、型号、生产厂家 | 颜色分类、适应机型 | 可读取 | 可读取 | 现货、预售、现货预售混合 |

差异结论：发布控制字段不只是类目属性有差异，预售/发货模式的选项也会随类目变化；设置页必须按当前类目 schema 渲染，而不是保存一组全局固定枚举。

## 接口能力分层

### 1. 类目与 schema

已验证：

- `GET /product/tproduct/searchCategoryN?key=<关键词>&search_type=1`
- `POST /product/tproduct/getSchema`

用途：

- 设置页类目搜索。
- 上传前类目确认。
- 动态生成类目属性表单。
- 动态生成规格轴和 SKU 校验规则。

### 2. 运费模板

已验证：

- `POST /product/tproduct/refetchSchema?action=freight_template_options_load`

用途：

- 设置页读取真实运费模板。
- 上传前精确匹配模板名到 `freight_id`。
- 未精确命中时阻塞，不自动选择默认模板。

### 3. 素材上传

当前状态：

- `/product/img/batchupload` 已有请求字段和返回形状证据，但仍需要和完整 `addWithSchema` 模型交叉验证。
- `/product/tproduct/saveMaterial`、`/product/tproduct/materialDetail`、`/product/tproduct/spuImgUpload` 仍是候选链路。
- 白底图字段形状已确认是 `array<{ url: string }>`，但 `submitWhiteImg.action_list` 和审核闭环仍未确认。
- 详情图最终写入 `description` 的序列化形态仍未确认。
- 资质图/合格证不能硬编码到 `qualification`，必须先抓到当前类目真实资质子项请求体。

用途：

- 主图、3:4 主图、白底图、详情图、资质图。
- 主图视频和素材库保存。

阻塞：

- 需要用 `CAPTURE_PROFILE=media-preflight` 或 `submit-preflight` 在本地截停真实页面动作产生的请求体。
- 需要确认图片 URL、素材 ID、详情页 `description`、白底图审核结果与最终提交模型的关系。

### 4. 提交

已确认：

- `/product/tproduct/addWithSchema?check_status=<状态>`
- `/product/tproduct/editWithSchema?check_status=<状态>`
- 前端提交 wrapper 的 envelope 合并顺序已定位。
- 媒体字段、`qualification`、`description`、`spec_detail/sku_detail` 的提交 schema 形状已有部分证据。

阻塞：

- 缺少本地截停到的完整 `addWithSchema` 请求体。
- 缺少 `spec_detail/sku_detail` 中规格值 ID、SKU 组合 ID、价格库存字段的真实样例。
- 缺少详情图、白底图、合格证/资质在最终请求体中的真实落点。

## 当前证据工具链

- `cdp_fxg_protocol_capture` / `npm run capture:fxg-protocol`：抓取匹配请求并去敏；使用 profile 时默认本地截停。
- `CAPTURE_PROFILE=submit-preflight`：覆盖最终提交、SKU/价格库存、图片、详情、资质相关优先证据链。
- `CAPTURE_PROFILE=submit-only`：只截停 `addWithSchema/editWithSchema`。
- `CAPTURE_PROFILE=media-preflight`：截停图片、素材、白底图、详情图相关请求。
- `evidenceSummary`：抓包输出中按 `final_submit`、`sku_price_stock`、`image_upload`、`detail_page`、`qualification` 汇总证据。
- `proposed_submit_model`：dry-run 输出的完整拟提交模型。
- `field_verification_report`：dry-run 输出的已验证、缺失、不能提交字段清单。

当前约束：这些工具只证明请求体结构和字段来源，不代表协议发布已可用。

## 产品配置规划

设置页后续不应写死这些内容：

- 默认类目：通过类目搜索和 schema 选择。
- 运费模板：通过运费模板接口读取。
- 上下架策略：从 schema 中读取 `start_sale_type` / `sale_channel_type` 等字段能力后再配置。
- 类目属性默认值：按每个类目 schema 存储映射，不跨类目复用。
- SKU 规格轴：按 schema 的 `spec_detail` 生成，不固定袜子规格。

建议的配置数据结构：

```json
{
  "category_leaf_id": "<platform_category_leaf_id>",
  "category_path": "<platform_category_path>",
  "freight_template": {
    "name": "<用户选择的真实运费模板名>",
    "freight_id": "<运行时读取并精确匹配的模板 ID>"
  },
  "category_property_defaults": {
    "<筒高属性ID>": "长筒袜",
    "<面料材质属性ID>": [
      { "name": "棉", "percent": 75 },
      { "name": "氨纶", "percent": 25 }
    ]
  },
  "spec_axis_mapping": {
    "颜色分类": "source_sku_name",
    "码数": "default_size"
  }
}
```

这个结构只能作为规划，不代表所有类目都适用。真正上传前仍必须用实时 schema 校验。

## 当前硬编码治理清单

这些点不应再继续扩大使用范围，后续需要按接口能力逐步替换：

- `tauri-app/src/components/SettingsPanel.vue`：自动化设置中存在本地默认运费模板、材质选项和材质比例。
- `tauri-app/src/types/index.ts`：类目选项仍是袜子类目的本地枚举。
- `tauri-app/python-sidecar/app.py`：运行时配置读取仍有本地默认运费模板和材质比例。
- `src/enhanced_category_selector.py`、`src/utils.py`：类目选择和袜子筒高推断仍依赖袜子字典。
- `mcp-server/core.js`：仍存在本地袜子类目辅助映射。
- `tauri-app/python-sidecar/protocol_publish/stages/basic_runtime.py`：DOM 阶段仍含袜子类目字段默认值。
- `tauri-app/python-sidecar/protocol_publish/stages/price_stock_runtime.py`：运费和上架状态仍是 DOM 阶段固定操作逻辑。
- `tauri-app/python-sidecar/app.py`：智能定价/成本配置仍使用“默认袜子模板”作为存储键和默认模板。

治理原则：先补齐协议证据和 dry-run 字段解释，再把硬编码替换为用户显式选择和实时 schema 校验结果；不要通过新增兜底逻辑掩盖字段缺失。

## 开发顺序

1. 继续补接口证据：优先抓 `addWithSchema`、SKU、价格库存、图片上传、详情图、资质/合格证请求体；只做本地截停。
2. 完善 dry-run：输入已采集商品，输出完整 `proposed_submit_model`，明确哪些字段已验证、哪些缺失、哪些不能提交。
3. 做协议化 SKU/价格库存模块：先协议化收益最大、DOM 最慢且最容易乱跳的部分。
4. 做图片与详情页协议化上传：仅在图片上传协议和详情 `description` 结构稳定后推进。
5. 做完整协议发布实验线：必须加开关，默认仍走 DOM 稳定线，协议线只作为实验模式。
6. 设置页平台配置读取放在接口证据稳定之后推进，避免在字段协议仍不清楚时扩大配置面。

## 禁止事项

- 禁止把袜子类目的 `筒高`、`面料材质` 逻辑复用到其他类目。
- 禁止按固定规格轴生成 SKU。
- 禁止按表格列序号写价格库存。
- 禁止模板名未命中时自动选择第一个运费模板。
- 禁止在没有 dry-run 报告的情况下启用协议提交。
- 禁止商品记录类目与当前 schema 不一致时继续生成协议候选模型。
