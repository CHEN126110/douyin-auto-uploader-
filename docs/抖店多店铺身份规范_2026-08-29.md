# 多店铺身份规范（2026-08-29）

## 起因

接线完成后发现：旧路径默认 `default_shop = new_shop`，而目标店铺
「起了个球球」的 profile cookie 停在 2026-08-14。**两条链路可能在查不同的店。**

技术决策：**不直接改 `default_shop`**。翻配置是在猜，而猜错的后果正是
「拿到别的店铺的真实数据」——不报错，每个数字都对，只是属于另一家店。
先查清事实再说。

## 查清的事实

| 事实 | 依据 |
|---|---|
| `new_shop` profile 实际登录的是 **155450371（起了个球球）** | cookie `ecom_gray_shop_id` |
| `shop-resolver.js` 的手工表却声明 `new_shop → 177886360` | `SHOP_ID_MAP` |
| 三个 profile 的 `cookie_cache.json` **shopId 全是 155450371** | 逐个读文件确认 |

第三条是根因：`sync_compass.js`、`grab_compass_cookie.js`、`fxg_bridge.js`
都写死了 `['login_capture', 'new_shop', '起了个球球']`，一次登录写三份。
**profile 与登录态从根上就没有对应关系**，「按 profile 区分店铺」不成立。

> 幸好没有盲目改配置——`new_shop` 恰好就是目标店，改了反而会错。

## 核心原则

> **profile 的名字不等于它登录的店铺。**
> 声明的映射只是意图，实测的 cookie 才是事实。冲突时以事实为准。

## 三层身份体系

| 层 | 文件 | 职责 |
|---|---|---|
| 路由 | `lib/shop-resolver.js` | shopId → profile。**实测记录优先**，手工 `SHOP_ID_MAP` 降级为尚未观测时的兜底 |
| 事实 | `lib/shop_registry.js`（新增） | 从 cookie 实测的「profile → 店铺 id」，落盘 `shop_profiles/registry.json`，自动检出与手工表的漂移 |
| 闸门 | `dispatcher` / `compass_api` | 取数后校验，不符即拒绝并**丢弃已取到的数据** |

## 读写两级闸门

| | 读不到店铺身份 | 身份不符 |
|---|---|---|
| 只读 | 放行，但 `_meta.shopIdNote` 标注「未经身份校验」 | 拒绝 |
| **写** | **拒绝** | 拒绝 |

写操作（`launch` / `delist` / `edit_draft` 等）更严的理由：
读错店只是结论被污染，**写错店是真的改了另一家店的商品，不可逆**。

确需跳过时设 `DOUDIAN_SKIP_SHOP_GATE=1`，但要有明确理由。

## 加一个新店铺

```bash
node scripts/auth/login_agent.js doudian <profile名>   # 1. 登录
node scripts/compass/shops.js verify <profile名>       # 2. 实测并记入注册表
node scripts/compass/shops.js                          # 3. 查看记录与漂移
```

**不需要手工编辑任何映射表。** 第 3 步发现漂移会以退出码 1 结束，可用于 CI 拦截。

## 修掉的串店路径

| 位置 | 问题 | 后果 |
|---|---|---|
| `compass_api.init()` | 不接受 profile 参数，固定用 `chrome_profile/`；`if (initialized) return` | 第二次带不同 profile 的调用**直接复用旧会话** |
| `compass_tools` | 只用布尔 `inited` | 同上 |
| `compass_cookie` | 单份 cookie + 5 分钟 TTL，无店铺分槽 | 先查 A 店再查 B 店，5 分钟内命中缓存 → 返回 **A 店的真实数据**，`success:true` |
| `_callFxgPool` | 写操作零身份校验 | 上架/下架可能发到错误店铺 |
| 三个登录脚本 | cookie 扇出到写死的三个 profile | profile 与店铺脱钩（根因） |
| `compass_pool` | 缺 `refreshPage` / `_page` 代理 | 一处 TypeError 被吞后落到跨店兜底；另一处 `undefined.goto` 同步抛错，`.catch()` 接不住 |

## 过程中我自己造的两个回归

**其一**：把 `init()` 改成支持 profile 后，忘了 `_getRaw()` 等 4 个内部调用点
不传参。`init(undefined)` 会把 target 算成 `chrome_profile`，
**每次取数都把刚绑定好的店铺会话关掉重开**。
已把无参语义改为「沿用当前会话」（`activeProfile || PROFILE`）。

**其二**：合并鉴权码表时取了单边集合，漏掉 `compass_cookie` 独有的 `st=100704`，
导致整条 `compass_pool` 通道全线「服务器错误」——该码原本靠刷新会话重试恢复。

> **合并两份配置时默认取并集；取单边必须逐项说明丢弃的理由。**

## 修复暴露的既有缺口

`init()` 真正开始按 profile 走之后，身份读取反而失败了——
因为 `shop_profiles/*` 的浏览器目录里**没有活的罗盘会话**，
只有根目录 `chrome_profile` 一直有。之前 `init()` 忽略参数，
所以一直误打误撞用对了。

已补：按 profile 从 `cookie_cache.json` 注入 cookie（与 `compass_pool` 的做法对齐）。

## 测试写错三次

`assertWriteShop` 的验证中，我用 `new Function` 取巧测试，
而函数体里的 `require` 不在作用域内，两次取值都抛错被 catch 成 null，
**看起来像闸门误拦了合法写操作**。改为正常导出后测，三种情形全部判对。

加上本会话早先的两次「表头当数据」，**同一类错误犯了三次**：
断言写错和代码写错，红灯长得一模一样。现已全部固化为自检用例。

## 自检

从 73 增至 **78 项**，新增多店铺相关断言：
漂移可检出、身份不符必拒、读不到不拦但留痕、`init` 接受 profile、
换 profile 重建会话、结果带 shopId、写闸门三情形、cookie 缓存按店铺校验、
登录 cookie 不得扇出。

## 验证结果

46 个接线工具：**31 有业务数据 / 2 仅图表 / 0 解包盲区 / 13 确无数据 / 0 失败**，
全部标注 `shopId = 155450371`。

## 已知限制

`COMPASS_EXPECT_SHOP_ID` 是**进程级全局**，同进程并发查两个店时会误报。
需要并发多店时改用 `args.expectShopId` 逐次指定，不要设这个环境变量。

## 尚未处理

  与调用方要哪个店无关
