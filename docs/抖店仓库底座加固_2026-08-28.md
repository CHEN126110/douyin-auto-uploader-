## 1. 审批门禁是空实现（最严重）

`lib/approval-gate.js` 里有**两组同名函数**：

```js
// 39-52 行：真实实现，返回 dry_run + riskLevel L4
function dryRunResponse(toolId, args = {}) { ... }

// 55-60 行：空壳。函数提升使其覆盖上面的实现
function checkApproval() { return { ok: true }; }                    // 恒放行
function dryRunResponse() { return { success:true, status:'ok' }; }  // 预览变"成功"
```

后果：全仓 14 处 `if (!gate.ok)` **恒真放行**，12 个写操作
（上架/下架/删草稿/批量改价/发券/发消息）无任何门禁；
被覆盖的 `dryRunResponse` 还会返回"成功"，让调用方**误以为在预览、其实拿到成功信号**。

修复：删除重复定义，恢复真实实现。放行条件为
`args.execute === true` / `args.approved === true` / `DOUDIAN_ALLOW_WRITES=1`，
未满足时返回 `{ok:false, error:<dry-run>}`，与既有调用方契约一致。

实测：只读放行、写操作拦截（status=dry_run, risk=L4）、
别名 `store.product.draft.create` 同样拦截（不能成为绕过通道）。

## 2. browser_pool 安全漏洞

```js
page.evaluate(new Function('page', script))   // 执行请求体里的任意 JS
```

在**已登录店铺的浏览器**中执行任意脚本，配合 `Access-Control-Allow-Origin: '*'`
与默认监听所有网卡，意味着：局域网内任何设备、以及用户浏览的**任何网页**，
都能通过 `fetch('http://localhost:17871/page/...')` 控制店铺账号。

修复三层：
- `server.listen(PORT, '127.0.0.1')` —— 阻断局域网；
- CORS 由 `*` 收紧为本机来源；
- 脚本执行接口**默认禁用**，需显式设置 `BROWSER_POOL_TOKEN` 并携带 `x-pool-token`。

查证无本地调用方，修复不影响现有流程。

## 10. fxg 信封校验：在统一出口 `ok()` 一处覆盖 125 个返回点

### 为什么不用改 60 处

最初判断需要逐个改 60 个 `JSON.parse` 点。查证后发现更好的入口：

- `ok(toolId, data, opts)` 被调用 **125 次**，而直接写 `success: true` 只有 3 处
  —— 它是**统一的成功出口**；
- 它**已经在做同类检查**（`detectEmptyMetrics` 识别罗盘 `unit:6` 空值，
  自动标注「无数据 ≠ 0」）。加信封检测属于风格一致的扩展，不是新增机制。

### 判据必须保守（并已用真实数据验证）

只有当对象同时满足以下条件才判为错误信封，避免误伤恰好含 `code` 字段的合法数据：

1. 存在 `st`/`code`/`status_code`/`err_no`/`errNo` 之一且**非 0**；
2. **且** 带 `msg`/`message`，或 `data` 为 null，或字段数 ≤ 5。

验证结果：

| 用例 | 期望 | 实测 |
|---|---|---|
| 11 份真实快照数据 | 全部放行 | ✅ 零误伤 |
| `{st:10008,msg:'登录已失效'}` | 拦截 | ✅ |
| `{st:100704,msg:'服务器错误',data:null}` | 拦截 | ✅ |
| `{code:10012,msg:'视角不匹配'}` | 拦截 | ✅ |
| 商品数组 / `{st:0,...}` / `{code:0,...}` / `[]` / `null` | 放行 | ✅ 全部放行 |

命中时转为 `fail(toolId, 'UPSTREAM_BUSINESS_ERROR', ...)`，
并把业务码传给既有的 `_getFriendly` 错误映射，复用已有的用户友好文案。
提供 `opts.skipEnvelopeCheck` 供确需回传原始信封的场景显式豁免。

**修复前**：登录失效返回 `{st:10008}` → `success:true` + "0 products"，
Agent 据此得出「店里没有商品」。**这是整个仓库最大的假数据源**，
且恰好发生在 Agent 最常读的 `store.product` / `store.order` 上。

## 13. 重试风暴与凭证摧毁（已修）

### 13.1 `lib/retry.js`：风控时反而加速请求

两个缺陷叠加：

```js
// 缺陷一：不可重试时只是「不 sleep」，没有 break
if (attempt < maxTries && shouldRetry(e)) { ...sleep... }
// → 循环继续，零延迟连打满 maxTries 次

// 缺陷二：默认判据把除 404 外所有含 HTTP 的错误都当可重试
err.message?.includes('HTTP') && !err.message?.includes('404')
// → 403/429（风控与限流）也进入重试
```

合起来的效果：**被限流时以最高频率连续重打**，正好加速触发封禁。

修复后实测：

| 错误 | 调用次数 | 说明 |
|---|---|---|
| `HTTP 429` 限流 | **1** | 立即停止，不再火上浇油 |
| `HTTP 403` 风控 | **1** | 立即停止 |
| `HTTP 404` | 1 | 重试不会让它变对 |
| `ETIMEDOUT` | 3 | 瞬时故障，正常重试 |
| `HTTP 503` | 3 | 服务端错误，正常重试 |
| `HTTP 408` | 3 | 请求超时，正常重试 |

### 13.2 `refresh_login.js`：登录失败也覆盖可用凭证

原实现提取 cookie 后**无任何校验**就写入四个文件（`cookie.txt`、`cookie_netscape.txt`、
两个 `.doudian_cookies*.json`）。登录超时同样走到这里——
**本来可用的凭证被一次性摧毁，且四个文件同时被毁，无从回滚。**

修复：写入前校验 `sid_guard`/`sessionid` 存在且 cookie 长度合理，
不通过则拒绝写入并退出（现有凭证保持不变）；通过则先备份带时间戳的副本再覆盖。

## 14. 自检自身的严重缺陷：异步断言永远不会变红

加入 retry 的 4 条断言后自检显示「38 通过 / 0 失败」，但**这些断言其实没有被验证**：

```js
function it(name, fn) {
  try { fn(); pass++; console.log('✅'); }   // async fn 返回 Promise，不会抛
  catch (e) { fail++; }                       // 永远进不来
}
```

async 断言的异常逃逸成 unhandled rejection，计数器照样 +1。
**测试永远绿，也就永远发现不了问题——比没有测试更危险，因为它提供虚假的安全感。**

修复：`it()` 收集 Promise 到 `pending`，收尾用 `Promise.all(pending)` 统一等待后再统计。

**验证方式**：注入一条必失败的异步断言 → 报 `失败 1`；移除后 → 回到 `失败 0`。
不做这一步就无法确认「能报红」这件事本身。

> 这与第 8 节是同一类问题的两种形态：
> 一次是断言取错字段导致**误报**，一次是断言根本没执行导致**漏报**。
> **测试的可信度必须被单独验证，不能因为它是「测试」就默认可信。**

## 15. 本轮踩到三次的同一个坑：转义污染

用 Python 脚本改写 JS 时，`\b` 被写成**退格控制字符**、`\n` 被写成**真换行**：

| 现象 | 后果 |
|---|---|
| `/\b([45]\d{2})\b/` → 正则里嵌入 `^H` 控制字符 | 正则看起来完全正常，却永远匹配不上 |
| `split('\n')` → 字符串被真换行截断 | 语法错误（这个反而是好事，会立刻暴露） |

**第一种最危险**：语法合法、逻辑看似正确、只是永远不成立。
若当时只跑了「限流不重试」那一半用例，就会误以为改对了。

规避：正则改用 `[^0-9]` 等不含反斜杠转义的等价写法；
字符串换行用 `chr(92) + 'n'` 显式拼接。

## 8. 本轮的方法论教训

- **两次误判源于取错字段**：注册表标识字段是 `toolId` 而非 `id`，
  取 `t.id || t.name` 会落到人类可读名（"Create Draft"），正则匹配不上，
  从而误报"工具缺失"。**断言写错和代码写错，表现完全一样。**
- 因此自检里的每条断言都必须先人工确认过判据本身，
  否则"测试变红"可能只是测试错了，反而消耗信任。
