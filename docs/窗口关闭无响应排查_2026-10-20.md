# 窗口关闭无响应排查（2026-10-20）

> 状态：**旧实例事故——机制已查清并复现，触发原因没查到**，已加「再次出现时自动留现场」的证据采集；
> **另外发现并修复了一个独立缺陷**（外部工具把 `WM_CLOSE` 发给 tao 的内部窗口，应用会永远退不出去）。
> 代码：`tauri-app/src-tauri/src/ui_watchdog.rs`（新）、`event_target_guard.rs`（新）、`main.rs`（接线）；验证脚本：`lab/shell_close_probe/`。

## 一句话结论

1. **旧实例事故（pid 51740）**：UI 线程当时停在 tao 某个事件回调里的**嵌套消息循环**中。tao 在回调重入时把新事件放进缓冲区、等外层回调返回才派发，
   所以关闭请求（`WM_CLOSE`）被收下了，却到不了 Tauri 的 `on_window_event`——日志里没有 `window close requested`；嵌套循环仍在分发窗口消息，
   窗口照常应答 `WM_NULL`，所以 `Process.Responding=True`、线程是「空闲等待」。实验里用一个永不返回的 `GetMessage` 循环复现了全部特征，
   并且释放它的同一毫秒，被缓冲的关闭请求立刻被处理。**触发原因（谁把 UI 线程停进了回调）没查到**，事后无法还原。
2. **「请求发给了错误的窗口」不是这次事故的原因**：已向当时的会话核实——四次请求的 `hwnd` 都是 `Tauri Window`（真主窗口），Tao 事件窗口在第一次请求后仍然存在。
3. **独立缺陷（已修）**：进程里有两个可见的无 owner 顶层窗口——真主窗口 `Tauri Window` 和 tao 的内部窗口 `Tao Thread Event Target`。
   主窗口一最小化，`Process.MainWindowHandle` / `CloseMainWindow()` 就指向内部窗口；`WM_CLOSE` 发给它会把它销毁，从此**应用再也退不出去**
   （主窗口照常能关、清理照常执行，但 tao 的事件循环永远不结束，留下一个没有窗口的残留进程）。现在给它挂了子类过程，收到 `WM_CLOSE` 只记日志不处理。
4. **新构建不是必现**：同一份 `main.rs`（本次改动之前，自 10-18 21:04 起没改过）的新构建，在隔离实例里三种关闭请求全部正常；真实新实例（pid 9000，09:25 启动）
   09:30:56 也记录了 `window close requested` 并正常退出。
5. **做了什么**：①`ui_watchdog`（只写日志，下次再出现时自动留现场：窗口状态 + 最近事件 + UI 线程调用栈）；②`event_target_guard`（修第 3 条）；
   ③发布配置保留符号，调用栈里才有函数名。没有改任何关闭 / 清理逻辑，没有加兜底或强杀。

## 1. 现象与已有证据

来源：重启应用的会话（`api`）的实测，旧实例 pid 51740，exe 为 10-18 21:21 构建，10-19 22:08 启动，10-20 09:10~09:25 测试关闭：

- 四次关闭请求，**hwnd 全部来自 `Process.MainWindowHandle`，值始终是 2233954（`Tauri Window`，可见、最小化）**：
  ① pwsh 7 里 `CloseMainWindow()`；② `PostMessage(WM_CLOSE)`；③ `SendMessageTimeout(WM_SYSCOMMAND, SC_CLOSE)`（返回 1，`hung=False`）；④ `SW_RESTORE` 后再发 `SC_CLOSE`（对同一个句柄，`IsIconic` 由 True 变 False）。
  全部「成功」，`Process.Responding=True`，进程不退出。
- `EnumWindows`（按 pid 过滤，在第 1 次之后、第 2~4 次之前）：`Tauri Window` 2233954（可见、最小化）→ `Tao Thread Event Target` 7669424（可见、未最小化、无标题）→ `MSCTFIME UI` → `Default IME`。第 1 次之后内部窗口还在。
- `tauri-runtime.log` 里**没有** `window close requested`（`on_window_event` 的 `CloseRequested` 分支第一件事就是写这行）。
- 窗口线程 `Wait/UserRequest`；没有原生对话框；先让后端 `POST /internal/terminate` 退出也没让壳处理排队的关闭请求。
- 同一份 `main.rs` 的新实例 09:30:56 被关闭时，日志完整：`window close requested` → `sidecar stopped` → `shutdown_existing_backend succeeded` → `run event exit requested` → `run event exit received`。

## 2. 关闭事件在源码里怎么走（版本以 `Cargo.lock` 为准：tao 0.34.5 / tauri-runtime-wry 2.9.3 / tauri 2.9.5 / wry 0.53.5）

```text
WM_CLOSE
 └ tao  platform_impl/windows/event_loop.rs  public_window_callback → WM_CLOSE → send_event(CloseRequested)
     └ runner.rs  EventLoopRunner::send_event
          ├ should_buffer()==true  →  事件进 event_buffer，等外层回调返回后 dispatch_buffered_events   ←←← 旧实例卡在这里
          └ 否则 call_event_handler → tauri-runtime-wry handle_event_loop
                └ on_close_requested（lib.rs:4224）
                     ├ tauri manager/window.rs on_window_event（向 JS 发 tauri://close-requested）
                     └ 我们的 on_window_event：println! → 写 "window close requested" → cleanup_python_process
```

关键条件在 `runner.rs:143`：`should_buffer()` 就是「事件处理器此刻是否已被取走」，也就是「当前正处在一次事件回调里」。tao 自己在 `event_loop.rs:2364` 的注释里承认
「*a nested win32 event loop is triggered inside of the `event_handler` callback*」会走缓冲分支。

所以：**只要 UI 线程停在某个回调里的嵌套消息循环中**，之后所有窗口事件（包括 `CloseRequested`）都被缓冲；窗口过程仍在被嵌套循环调用，窗口因此「有响应」。

依赖里能在回调中产生嵌套消息循环的东西（逐个读过）：

| 位置 | 说明 |
|---|---|
| `webview2-com` `wait_with_pump`（`lib.rs:60`，`GetMessageA` 循环） | wry 在**创建 WebView 环境 / 控制器**（`webview2/mod.rs:360, 410`）和读 **cookies**（`:1648`）时用；本应用运行期不新建窗口 / WebView、不读 cookies |
| `tauri-runtime-wry` `dialog/windows.rs`（`TaskDialog`） | 仅在找不到 WebView2 运行时时弹，事故时进程里没有对话框窗口 |
| WebView2 的同步 COM 调用卡在浏览器进程 | 没有证据，也无法从源码排除 |
| 我们的代码 | `setup`（Ready 回调内）和 `RunEvent` 回调里只有有时限的阻塞（reqwest 800 ms、端口探测、PowerShell 清理），没有任何消息泵 |

## 4. 独立缺陷：内部事件窗口可被外部关闭 → 应用退不出去（已修）

- **原因（现象已复现，机制据源码推断）**：tao 的事件循环要回到「空闲」状态，靠它的内部窗口收 `WM_PAINT`（`event_loop.rs:2359` 一带）；`run_return` 里的退出判断是
  `if ControlFlow::ExitWithCode && !runner.handling_events() { break }`（`event_loop.rs:276`）。内部窗口一旦被销毁，状态永远停在「处理事件中」，循环就永远不结束。
  实测现象：之后关真窗口，`run event exit requested received` 之后再也没有 `run event exit received`，窗口全没了、进程还活着。
- **谁会触发**：任何按 `EnumWindows` 顺序挑窗口、然后发 `WM_CLOSE` 的东西——实测的是 .NET 的 `CloseMainWindow()`（主窗口最小化时）。
  这是 AI 会话里最常见的「优雅关闭」写法，所以风险不小；表现为「关不掉」，之后启动器还会说「当前工作区应用已在运行，不重复启动」。
- **修法**（`event_target_guard.rs`）：`setup` 里（UI 线程）找到该窗口，挂一个子类过程，`WM_CLOSE` 只记一行日志、返回 0，其它消息交给 tao 原来的处理。
  真窗口完全不受影响；找不到窗口（tao 升级后改了类名）时会在日志里写 `guard NOT installed`，`probe_wrong_window.ps1` 也会失败。
- **验证**：实验 9 → 10。回归：空闲 53 秒后 `WM_CLOSE`、最小化后 `SC_CLOSE`、还原后 `CloseMainWindow`、带后端的完整链路与强杀，全部正常。
- **不是什么**：它**不能**解释 pid 51740 那次事故（当时的 hwnd 是真主窗口）；也**不会**让「最小化时 `CloseMainWindow()`」能关掉应用——请求被忽略了。要可靠地关应用，
  请按类名 `Tauri Window` 找窗口再发 `WM_CLOSE`（`lab/shell_close_probe/Probe-Lib.ps1` 的 `Find-MainWindow` / `Send-PostClose`），或先还原窗口。

## 5. 新增：`ui_watchdog`（只收集证据）

接线（`main.rs`）：`setup` 里 `window.show()` 之后启动；`.run` 回调对每个 `RunEvent` 记一条面包屑；`ExitRequested` / `Exit` 时 `stop()`（退出清理本来就会阻塞 UI 线程数秒）。

行为：

1. **面包屑**：最近 40 条 `RunEvent` / `WindowEvent`（连续重复的合并计数，如 `MainEventsCleared x262`）。
2. **心跳**：每 15 秒用 `run_on_main_thread` 往 UI 线程投一个空任务；20 秒没执行 → 判定停摆。监测线程自己被挂起（系统睡眠）超过 8 秒时丢弃这次心跳，不误报。
3. **现场**（同一次停摆最多完整记 3 次，之后每 10 分钟一行 `still stalled`；恢复时记 `RECOVERED`）：
   - 主窗口是否应答 `WM_NULL`、`IsHungAppWindow`、是否最小化 / 可见 / 前台；
   - 本进程全部顶层窗口（用来发现是否有残留的对话框）；
   - 最近事件（新→旧）；
   - **UI 线程调用栈**（`模块!符号+偏移`，Rust 符号已还原）。取栈时挂起 UI 线程的时间只限 `SuspendThread → GetThreadContext → ResumeThread` 三个系统调用，其间不分配内存、不拿锁。

不做的事：不重试、不强杀、不改变任何流程。

### 怎么读 STALL 报告

| 栈顶附近 | 含义 | `WM_NULL` 应答 |
|---|---|---|
| `GetMessage*` / `PeekMessage*`，下面是 `handle_user_message` / `handle_event_loop` / `send_event` | 回调里的嵌套消息循环——**就是 2026-10-20 那种**；看 `GetMessage` 上面一帧是谁调的 | true |
| `NtWaitForMultipleObjects` ← `combase!` / `CoWaitForMultipleHandles` | 同步 COM 调用在等对端（看上一帧是哪个 COM 接口） | 通常 true |
| `RtlSleepConditionVariableSRW` / `WaitOnAddress` / `NtWaitForAlertByThreadId` | 互斥锁 / 条件变量死锁（不是消息泵） | false，`IsHungAppWindow=true` |
| `NtReadFile` / `NtWriteFile` / `NtDeviceIoControlFile` | 同步 I/O（例如 `println!` 写到没人读的管道） | false |

> 只有第 1 行是实验 5 实测过的；其余几行是按 Windows 通用行为整理的对照，没有逐项复现。

### 符号（调用栈里的函数名）

- **进程内解析**：dbghelp 直接读 exe 旁边的同名 `.pdb`（`target\release` 里本来就在）。必须是**同一次构建**的 pdb，否则自家的帧会退化成 `模块+偏移`。系统 DLL 的帧用导出表就能给出名字（`win32u!NtUserGetMessage`），不需要符号服务器（监测代码刻意用空的符号搜索路径，不联网）。
- **发布配置要保留符号**：`Cargo.toml` 的 `[profile.release]` 原来是 `strip = true`，实测 `.pdb` 只有 3.3 MB / 约 1900 个符号，**没有任何 Rust 函数名**（`tao::…::send_event`、`tauri_runtime_wry::handle_user_message` 都查不到），停摆调用栈里自家的帧就只剩地址，事后也无法还原。
  现改为 `debug = "line-tables-only"` + `strip = "none"`：`.pdb` 变成 24 MB / 约 1.2 万个符号，**exe 体积不变**（7.52 MB），构建多约 15 秒；`.pdb` 不进安装包。顺带让 `panic.log` 的回溯也带上函数名和行号。
- 用「LTO + 保留符号」的发布配置重跑实验 5，调用栈里已经是 `tao::…::EventLoopRunner::send_event`、`tauri_runtime_wry::handle_user_message`、`douyin_sock_publisher::main` 这样的可读名字。
- **安装包（NSIS）形态没有 pdb**：那种环境下自家的帧是 `douyin-sock-publisher+0x偏移`。要还原，需要同一次构建的 pdb——所以每次正式构建后请把 exe 和 pdb 一起归档（本次的在 `tauri-app/_sidecar_backups/shell-close-probe-20261020/`）；启动行里记录的 exe 大小 / 修改时间用来对应构建。

### 开销与风险

- 常驻：一个监测线程（每秒醒一次）+ 每 15 秒一个投递到 UI 线程的空任务；面包屑每个事件一次短暂的互斥锁。
- 只在停摆时才会挂起 UI 线程（微秒级）并调用 dbghelp；dbghelp 只由监测线程使用。若停摆期间恰好发生 panic，`panic.log` 的回溯也会用 dbghelp，两者理论上可能互相干扰，属极小概率。
- 单元测试 7 条（纯逻辑，不需要窗口）：判定的时间线、系统睡眠、面包屑合并 / 容量、Rust 符号还原。已做 11 种故意改坏（阈值、重复间隔、心跳间隔、睡眠分支、恢复提示、合并 / 容量、哈希、转义等），测试全部变红。
  跑法：本次是用一个只 `#[path]` 引入 `ui_watchdog.rs`（加上 `windows` 依赖）的独立小 crate 跑的；没有在 `src-tauri` 里直接 `cargo test`（那会编译整个壳）。
- `event_target_guard` 没有单元测试（纯 Win32 子类化），回归靠 `probe_wrong_window.ps1`。

## 6. 下次再出现「关不掉」时怎么办

1. **先确认请求发给了对的窗口**：按类名 `Tauri Window` 取窗口（不要用 `MainWindowHandle` / `CloseMainWindow()`，也别在刚启动的几秒里用 `taskkill`）。日志里出现 `[event-target-guard] ignored WM_CLOSE` 就说明刚才选错了窗口。
2. **别急着强杀**——但即使已经强杀也没关系，日志是自动落盘的：`%LOCALAPPDATA%\com.dyin.sock-publisher\logs\tauri-runtime.log`（从 Claude 会话启动的应用在 Claude 包的虚拟存储里，路径看法见 CLAUDE.md「重启桌面应用的实操要点」）。
3. 搜 `[ui-watchdog] STALL`：看「窗口应答 / 顶层窗口 / 最近事件 / 调用栈」，对照上面的表判断是哪一类。
4. 把 STALL 那一段连同启动行（`[ui-watchdog] started: ... exe=... size=... modified_unix=...`）一起保存；要还原函数名时用同一次构建的 `.pdb`（见上节）。
5. 强杀壳之后后端会在约 1.5 秒内自己退出（实测），不需要再手工杀 `python-backend.exe`；自动化浏览器（Chrome）是否残留没有验证。

- 自动化浏览器（DrissionPage 起的 Chrome）在强杀壳后是否残留，没有测。
- 关闭处理本身的两个**独立**隐患（这次没改，均与旧实例事故无关，因为旧实例根本没走到处理函数）：
  - `cleanup_python_process` 在 UI 线程里同步做清理，且 `force_kill_known_backend_processes` 调 PowerShell/WMI **没有超时**；WMI 卡住时，窗口会在「已记录 `window close requested`」之后一直卡在清理里；
  - `cleanup_python_process` 会按端口 5001 终止**任何**后端，而不只是自己启动的那个——同时开两个实例时，关一个会杀掉另一个的后端。
