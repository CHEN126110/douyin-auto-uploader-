# 抖音协议流水线 — 最终复盘

## 一、研究目标

在用户登录抖音后，**通过协议/API 方式完成商品发布**，替代 DOM 自动化流水线。

## 二、最终成果

✅ **addWithSchema 真实请求完整捕获**，商品成功发布到抖音店铺（质量分 90）。

## 三、已验证的协议能力

### 3.1 图片上传 ✅
```
POST /product/img/batchupload
Content-Type: multipart/form-data
Field: image (文件二进制)
→ 返回: https://p3-aio.ecombdimg.com/obj/ecom-shop-material/...
```
- 单图/批量均验证通过
- 通过 CDP cookies + Python HTTP 完成，**零 DOM 操作**

### 3.2 Schema 获取 ✅
```
POST /product/tproduct/getSchema
Body: {context: {category_id, operation_type, feature: {session_publish_id}}}
→ 返回: 53 字段 model + 14 类目属性(含 value_id/options)
```
- 支持动态获取不同类目的属性差异
- 已证实中筒袜(14属性) vs 短袜(15属性) 不同

### 3.3 addWithSchema 提交 ✅
```
POST /product/tproduct/addWithSchema?check_status=2
Headers: __token=xxx, verifyFp=xxx, Cookie
Body: {schema: {model: {title: {value: "..."}, ...}}, context: {...}}
```

### 4.1 Webpack 模块注入（核心突破）

```javascript
// 注入 webpack require
window[chunkName].push([[Math.random()], {}, function(req) {
    window.__fxgWebpackRequire = req;
}]);

// 获取认证函数
const post = req(90665).bE;  // 认证 POST
```

## 六、2026-05-11 突破 — 纯协议提交成功

### 6.1 成功验证

```json
// 第一次成功提交
{"errno": 0, "code": 0, "msg": "", "data": {"product_id": "3819286489045533092"}}
```

### 6.2 关键修复点

| 问题 | 原值 | 修复值 | 影响 |
|------|------|--------|------|
| body 根结构 | `{"schema": {title: "..."}}` | `{"schema": {"model": {"title": {"value": "..."}}}}` | schema参数为空 → 通过 |
| n_token/token | `""` (空) | `YYYYMMDDHHMMSS + 20位随机hex` | token非法 → 通过 |
| shop_id | `""` (空) | `"155450371"` (从cookie提取) | token非法 → 通过 |
| feature 字段 | 仅3个基础字段 | + product_sale_property_control, sale_property_sequence_variable, min_sku_price | token非法 → 通过 |
| after_sale | `{"quality_problem_return": {}, ...}` | `{"quality_problem_return": {"option_id": null, "selected": true}, ...}` | 验证通过 |
| interest_free_activity_id | `{}` | `{"activity_template_id": "IFA202508061521201431032346"}` | 验证通过 |
| request_extra | `{}` | 保持 `{}` (无需 _aToken) | 确认非必需 |
| _aToken | 曾认为是必须的 | 实际上不需要 (webpack post() 自动处理认证) | 10013 → 0 |

### 6.3 认证机制澄清

经过实验验证，认证流程如下：

1. **webpack post() 自动添加**: `__token`, `_bid`, `_lid` (body根级 + URL参数), `msToken`, `a_bogus`, `verifyFp`, `fp` (URL参数)
2. **调用者需要提供**: `n_token`/`token` (时间戳+随机hex), `shop_id`, 完整的 `feature` 字段
3. **_aToken**: **不需要** — 之前以为 `request_extra._aToken` 是必须的，但实际测试证明 `request_extra: {}` 即可通过
4. **getSchema 不需要任何 token** — 读操作无认证要求

## 七、2026-05-11 反滥用机制研究

### 7.1 发现

通过系统化测试矩阵 (19个测试用例)，发现了平台的**三层反滥用机制**：

| 层级 | 检测方式 | 特征 |
|------|----------|------|
| L1 — 内容验证 | `code=10013` + 具体msg | 标题长度、图片比例等业务规则校验 |
| L2 — 频率限制 | ~5-7次成功提交后触发 | 短时间内提交次数过多 |
| L3 — 账号封锁 | 持续数小时，账号级别 | 会话刷新/页面重载/草稿模式均无法绕过 |

### 7.2 10013 错误码真相

`code=10013` 不是单一的"token非法"，而是平台的**通用验证错误码**。实际错误类型在 `msg` 中：

| msg | 实际含义 | 错误码映射 |
|-----|----------|-----------|
| 商品标题最长不能超过30个汉字 | 标题过长 | ERR_BODY_TITLE_TOO_LONG |
| 提交参数异常 token非法 | 认证字段缺失 | ERR_AUTH_TOKEN_INVALID |
| 系统检测到您的发品方式可能存在异常 | 反滥用封锁 | ERR_ANTI_ABUSE_BLOCK |
| 主图3：4比例要求3:4 | 图片比例不合规 | ERR_IMAGE_RATIO_34 |
| 请上传1~5张商品主图 | 主图数量不足 | ERR_IMAGE_COUNT |

### 7.3 绕过策略测试结果

| 策略 | 结果 | 说明 |
|------|------|------|
| 添加 `_aToken` | ❌ 无效 | `request_extra._aToken` 不影响封锁状态 |
| 草稿模式 (check_status=0) | ❌ 无效 | 反滥用检测不看发布模式 |
| 页面刷新 (Page.navigate) | ❌ 无效 | 封锁是账号级别，非session级别 |
| CDP 行为模拟 (鼠标/键盘/滚轮) | ❌ 无效 | 检测不基于 input 事件 |
| 60秒冷却 | ❌ 无效 | 需要更长时间 (估计2-6小时) |
| **官方抖店开放平台 API** | ✅ 可行 | 平台msg中建议的正规途径 |
| **等待自然冷却** | ✅ 可行 | 估计2-24小时后恢复 |

### 7.4 影响范围

封锁**仅影响 addWithSchema**，不影响：
- batchupload (图片上传) ✓
- getSchema (类目属性读取) ✓
- 其他页面读取操作 ✓

### 7.5 生产环境建议

| 场景 | 推荐方案 | 频率限制 |
|------|----------|----------|
| 偶发发布 (日<10次) | 协议流水线 | 间隔 ≥ 60秒 |
| 批量发布 (日≥10次) | 抖店开放平台官方 API | 按官方限频 |
| 测试/调试 | 协议流水线 + 冷却 | 日限 5-10 次 |
