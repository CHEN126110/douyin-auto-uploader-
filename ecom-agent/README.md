# 电商 Agent（ecom-agent）

> 主项目 `2.1` 的本质是**发布工具**——它解决「怎么把商品传上去」。
> 本子项目要解决的是上游那个更贵的问题：**传什么上去，为什么是它**。
>
> 目标：**店铺盈利**。不是「多发几个商品」。

## 一句话

把「找到真实存在、竞争又小的需求」这件靠经验的事，变成一条有证据、可复盘、
能自我验证的流水线。

## 用户提出的底层逻辑

> 「需求决定了购买。就好比一个产品你很自信地说他上架就可以大卖，
> 你怎么知道他可以卖？因为你知道其中的**真实需求是存在的**，而且**市场竞争小**。
> 有了市场和需求机会，就可以去选品，选品之后设计素材、然后上架运营。」

这句话里有两个判据和一条链路，本项目就是把它们变成代码：

| 用户的话 | 专业表述 | 本项目怎么算 |
|---|---|---|
| 真实需求是存在的 | 需求真实性 / 需求质量 | 成交增速与曝光增速的**背离方向** |
| 市场竞争小 | 供给集中度 / 竞争强度 | 同类目店铺的成交分布集中度 |
| 有机会就去选品 | 机会到货盘的转化 | 机会卡 → 选品条件 → 1688 候选 |
| 上架运营 | 执行与回流 | 发布 + **回来验证当初的假设** |

## 为什么「成交增速 vs 曝光增速」是关键

实测数据（袜子，2026-08-29）：

```
成交额环比  +22.62%
曝光人数环比 +16.39%
```

**成交涨得比曝光快。** 这说明进来的人更愿意买了，不是单纯人变多了。

反过来如果曝光暴涨而成交没跟上，那多半是蹭到了热点或平台给了流量扶持——
看起来热闹，实际需求没变。这两种情况在「搜索量涨了」这个表象下长得一模一样，
但对是否值得进场是**完全相反**的结论。

这就是用户说的「你怎么知道他可以卖」的可计算版本。

## 与现有资产的关系

| 仓库 | 角色 |
|---|---|
| `D:\抖店` | **数据层**。73 个罗盘工具，每条数据带作用域与可信度定性 |
| `2.1`（主项目） | **执行层**。DOM 发布流水线、1688 采集、定价、标题 |
| `2.1/src/ops_engine.py` | **运营规则**。选品评估、利润阶梯、日复盘（纯本地规则） |
| 本项目 | **决策层**。把数据变成「该做什么」，并记录假设以便回头验证 |

本项目**不重复造**上面任何一层的能力，只做编排与判断。

## 三条不可让步的原则

1. **平台的结论只是假设。** 用户明确说过「不建议只看平台推荐的，因为通常不一定
   准确足够支持判断」。平台给的诊断、推荐、优化建议一律标记为待验证，
   必须用原始指标独立复核。
2. **只给建议，人工确认。** 不做无人值守的写操作。
3. **算不出来就说算不出来。** 行业数据大量以区间下发，不是精确值。
   宁可给「无法判定」，也不给一个看起来精确的假分数。

**N7 冻结假设、N12 裁决假设**——没有这一对，系统就只是个单向流水线，
永远不知道自己判断得对不对。

## 开发方式：先证明能做，再动手做

> 「确保项目是可实现的，而不是出现了问题再去修改，这是猜和摸瞎。」

**每个 DAG 节点依赖的前提，都要先在 [可行性验证表](docs/可行性验证表.md) 里
有一行、跑通探针、状态为可行，才允许开始实现。**

```bash
node probe/feasibility.js    # 能力存不存在（一次性）
node probe/stability.js      # 能不能稳定依赖（要长期跑）
node probe/stability.js --report   # 看累积趋势
```

当前：可行性 **✅ 7 / ⛔ 3 / ❌ 0**；稳定性 4 轮观测**可用率 100%、结构无漂移**。

两者问的是不同问题：可行性是「现在能不能」，稳定性是「能不能一直能」。
后者**必须长期重复跑**，单次结果说明不了问题。

⛔ 的三条不是"待修 bug"，是**设计前提不成立**，必须改设计：

| 前提 | 实测 | 设计怎么改 |
|---|---|---|
| 能回溯历史周窗口 | 只服务当前周，回溯一律拒 | 纵向归因在攒够 4 周前返回「不知道」，不猜；立刻开始按周攒快照 |
| 能拿到类目在售商品数 | 只有店铺维度 | 删掉供需比，改用「进入门槛 + 头部形状」 |
| 工具名与内容一致 | `video_after_watch` 实为热点榜 | 加别名或在 description 写明 |

这份表本身也是踩出来的——项目在有它之前撞过三次墙，
全是做到一半才发现的，而三条都是一个探针就能提前知道的事。

## 已经验证的核心结论

**一、需求真实性判据成立。** 比较成交增速与曝光增速的方向，
能把「真需求」和「虚流量」分开。日抛袜子表面增速最高（+66%），
背离却最负，是这批里最不该进的。

**二、但单看词内背离会误导，必须扣掉类目基准。**
篮球袜 +26.7% 看起来很好，扣掉类目基准（+25.2%）后只高 1.5pp——
根本不突出。不扣基准就会把「大盘在涨」误读成「这个词有机会」。

**三、内容侧归因能做。** 热点榜 50 条里 11 条是秋季换季主题，
指向类目普涨的成因。且本店在 331 个热点中关联商品数**全为 0**。

**四、纵向归因做不了。** 罗盘只服务当前周，回溯一律「参数校验失败」，
本地只攒了 1 个周窗口。**区分不了趋势与季节性**——
这直接决定篮球袜的机会是值得建 SKU 还是两周后就没了。
在攒够 4 周之前，这个问题的答案是「不知道」，不猜。

## 稳定性观测查出的真问题

**多字节字符在 HTTP 分块边界被截断。** 表现是「同一查询返回不同结果」，
看起来像平台数据不稳定；真相是 `d += c` 逐块拼字符串，
跨块的 UTF-8 字符两半各自解码成了乱码（「帮人**修**表」→「帮人**??**表」）。

会静默损坏商品标题、搜索词这类文本，且只在部分响应里出现。
已改为先拼 Buffer 再整体解码，并加自检断言。

**这个 bug 只有做稳定性观测才会暴露**——功能测试永远是「有数据、能解析」。
