# 机会度量模型设计（抖店袜子类目 / 罗盘数据条件下）

---

## 0. 前置：三项字段语义校验（不做这个，后面全部无效）

模型的全部结论都压在 `__ratio` 这一个字段的语义上。翻 `D:\抖店\lib\compass_unwrap.js` 后发现三个必须先证实的事，**在校验通过前，模型只能输出 `INSUFFICIENT`，不能出分**。

### 0.1 `__ratio` 的来源歧义（真实缺陷，不是假设）

`compass_unwrap.js:248` 的取值逻辑是：

```
const ratio = m.out_period_ratio || m.last_period_change;
```

`out_period_ratio` 是**环比率**（无量纲），`last_period_change` 是**环比绝对变化量**（有量纲，单位同母指标）。两者被写进**同一个 key** `name + '__ratio'`。也就是说 `pay_amt__ratio = 0.2262` 有两种可能：

- 来自 `out_period_ratio` → 成交额环比 +22.62%（用户的读法）
- 来自 `last_period_change` → 成交额环比增加了 0.2262 元 —— 在 7.5 亿量级下这个读数荒谬，可自证排除

**判别方法（可机读，不靠人记）**：`compass_unwrap.js:17` 已有 `UNIT_MAP`，`4: 'ratio'`。改造 unwrap，在写 `__ratio` 的同时落 `__ratio_src`（`out_period_ratio` / `last_period_change`）与 `__ratio_unit`（原始 unit 码）。**判据：`__ratio_src === 'out_period_ratio'` 且 `__ratio_unit === 4` 才允许当增长率用**；否则该行的增长率字段整条丢弃（不是补 0，不是猜）。

### 0.2 `__ratio` 的量纲标定（0.2262 = 22.62% 还是 0.2262%）

用**本店精确值**做标定，这是唯一不需要外部信息的自校准：本店数据 `is_self=1` 时 `value` 与 `last_value` 都是精确值（`data-contract.js` 的 PRECISION 注释已实测确认 5/5）。取任一本店指标，独立算 `(value − last_value) / last_value`，与同节点的 `out_period_ratio` 比对：

- 比值 ≈ 1 → ratio 是小数制，`0.2262 = 22.62%`
- 比值 ≈ 100 → ratio 是百分数制，`0.2262 = 0.2262%`

至少在 3 个不同指标上一致才认定。不一致 → 标定失败 → 全模型停在 `INSUFFICIENT`。

### 0.3 `__ratio` 的周期口径（环比谁对谁）

`date_type=21` 之类的参数决定了「上期」是昨天、上周还是上月。同一个词的 22.62% 在日环比和月环比下是完全不同的两件事（日环比 22.62% 是巨震，月环比 22.62% 是温和增长）。**必须把请求参数里的日期口径与 ratio 一起持久化**，`compass_snapshots.deriveStatKey(params, parsed)` 已经在按参数派生 `stat_key`，把周期口径纳进 `stat_key` 即可。跨口径的 ratio **禁止放进同一个序列比较**。

### 0.4 顺带发现的登记不一致（会导致 fail-closed 误伤）

`compass_tools.js` 的 CATALOG 里 `market.index_range` 登记 `scope: 'market'`，而 `data-contract.js:130` 的 `SOURCE_SCOPES['compass.market_index_range']` 登记为 `SCOPE.SHOP_STATE`；且键名是下划线 `compass.market_shop_rank` / `compass.market_index_range`，而 dispatcher 的 toolId 是点号 `compass.market.shop_rank` / `compass.market.index_range`。**键名对不上 → `fieldScope` 走 `by:'unknown'` → `canDriveDecision=false`**，本模型的两个供给侧主数据源会被契约整体挡在门外。这是本模型落地的前置阻塞项，必须先统一键名并确定 index_range 的作用域归属（我的判断：档位边界与各档店铺数属 MARKET，`isCurrentShop`/`tag` 属 SHOP_STATE，是典型的**混合作用域端点**，应加进 `MIXED_SCOPE_TOOLS` 按字段拆）。

## 1. 这个概念的专业叫法

用户描述的「真实需求存在 + 市场竞争小」，在电商运营与战略分析里不是一个词，而是**三个层次的概念叠起来**。按精确度从高到低：

### 1.1 最贴切的正式框架：机会缺口分析 / 供需失衡

| 中文 | 英文 | 出处与含义 |
|---|---|---|
| **机会缺口分析** | **Opportunity Gap Analysis** | 通用叫法：需求强度高但供给满足度低的位置 |
| **机会算法 / 机会分** | **Opportunity Algorithm / Opportunity Score** | Anthony Ulwick 的 ODI（Outcome-Driven Innovation）方法论。原式 `Opportunity = Importance + max(0, Importance − Satisfaction)`。**这就是用户直觉的正式形式**：需求重要性高、被满足程度低 = 机会 |
| **供需比** | **Demand-Supply Ratio (D/S Ratio)** | 跨境电商（Jungle Scout / Helium 10）标准指标：`月搜索量 / 在售竞品数`。国内生意参谋对应「搜索人气 / 在线商品数」，包装成「**蓝海指数**」 |
| **市场吸引力—竞争地位矩阵** | **GE-McKinsey Matrix** | 纵轴 Market Attractiveness（需求侧），横轴 Competitive Strength/Intensity（供给侧），九宫格定档。**本设计第 4 节直接采用这个形态**，因为它天然容纳「不精确输入」 |
| **同业竞争强度** | **Rivalry / Competitive Intensity**（波特五力之一） | 供给侧那一半的正式名 |

### 1.2 该领域通常怎么量化（以及我们**做不到**哪部分）

行业标准做法与本项目数据条件的对照：

| 行业标准量化项 | 标准算法 | 我们能不能算 |
|---|---|---|
| 需求规模 | 月搜索量 / 月成交额 | ✅ 能，但**只有区间**（`pay_amt__lower/__upper`） |
| 需求增速 | 搜索量同比/环比 | ✅ 能（`__ratio`，需先过第 0 节校验） |
| 需求真实性 | 搜索→成交转化效率 | ⚠️ 只能算**增速的相对关系**，不能算绝对转化率（见 2.2 口径警告） |
| **供给数量（在售商品数 / 竞品数）** | 类目在售 SKU 总数 | ❌ **拿不到**。这是本模型最大的数据缺口，D/S Ratio 的分母缺失，**任何声称算出了「供需比」的输出都是编的** |
| 供给集中度 | CRn / HHI | ⚠️ 只能**近似**（第 3 节），且在电商长尾下 HHI 判档基本无效 |
| 进入门槛 | 挤进前 N 名所需 GMV | ✅ **能，且这才是对小商家真正可操作的替代指标** |
| 广告竞价强度（CPC/竞价热度） | 关键词出价 | ❌ 拿不到（需千川数据） |

**结论先行**：在现有数据下，**不应该输出「供需比 / 蓝海指数」这类需要供给侧计数的指标**——分母不存在。应该把供给侧重构成「**进入门槛（要做到多少 GMV 才能进入可见区间）**」+「**头部形状（钱是集中在少数店还是摊在长尾）**」两个可算量。这是对用户硬约束 #4「明知不可用的东西不要让它看起来可用」的直接落实。

## 2. 需求真实性（Demand Authenticity）

### 2.1 观察到的现象是什么

```
pay_amt__ratio          = 0.2262   成交额环比 +22.62%
search_show_ucnt__ratio = 0.1639   搜索曝光环比 +16.39%
```

- 差值 `Δ = 22.62 − 16.39 = +6.23 pp`
- 效率比 `E = (1 + 0.2262) / (1 + 0.1639) = 1.0535` → **单位搜索曝光的成交产出环比 +5.35%**

### 2.2 关键的口径警告（必须先说，否则会误用）

用几何均值把区间转成可比值（`rangeToComparable`）：`pay_amt ≈ √(7.5e8 × 1e9) = 8.66 亿`，`search_show_ucnt ≈ √(7.5e5 × 1e6) = 86.6 万`。相除得到「每个搜索曝光人贡献 1000 元」——**这个数荒谬**，说明这两个字段**不在同一条漏斗上**（`pay_amt` 很可能是该词关联的全行业成交，`search_show_ucnt` 只是搜索场的曝光人数；抖音成交大头在内容推荐场，不经搜索）。

所以：**绝对值层面的 `pay_amt / search_show_ucnt` 无意义，禁止计算和展示。**

但**增速比 E 仍然有效**，理由是一个可写下来的恒等式：

```
ln(1+G) − ln(1+S) = Δln(pay_amt) − Δln(search_show_ucnt) = Δln(pay_amt / search_show_ucnt)
```

设两指标之间存在口径常数 `k`（`pay_amt = k · 真实漏斗量`），只要 **k 在相邻两期不变**，`k` 在做差时被完全消去。即：**比值的绝对水平不可解释，比值的变化率可解释。**

这个前提的失效条件必须被检测：平台改统计口径 / 改归因窗口 / 改样本范围时 k 发生阶跃。检测方法——用 `compass_snapshots.series(shopId, 'search.industry_rank', 90)` 取历史，对 `E` 序列做**阶跃检测**（相邻期 `|ln E_t − ln E_{t-1}|` 超过历史 MAD 的 5 倍且随后维持在新水平）。命中 → 该期及前一期的 E 标记 `CALIBRATION_BREAK`，不参与判定。

### 2.3 Δ > 0 到底说明了什么

在成交额的近似分解下：

```
GMV ≈ 曝光人数 × 点击率 × 转化率 × 客单价
```

`GMV 增速 > 曝光增速` 等价于 `(CTR × CVR × AOV) 的乘积在上升`，即「**同样多的人看，买得更多、或买得更贵**」。这在方向上支持「需求深化」，因为它不是靠流量堆出来的增长。

但 **+6.23pp 单独一条不足以定性**，它至少与四种成因兼容：

| 成因 | 也能产生 Δ>0 吗 | 为什么 |
|---|---|---|
| 真实需求深化 | ✅ | 购买意图占比上升 |
| 蹭热点虚假流量 | ❌ 通常 Δ<0 | 围观型搜索拉高曝光、不成交 |
| 季节性 | ✅ | 旺季来临时意图强度与客单同时上升（袜子换季买厚款，单价更高） |
| 平台流量扶持 | ❌ 通常 Δ<0 | 灌进来的泛流量摊薄转化 |
| **供给侧/内容场推动**（达人带货、爆款视频） | ✅ **且是抖音最常见的一种** | 成交发生在推荐场，根本不经搜索，于是 GMV 涨而搜索曝光不涨 |

**所以 Δ>0 有效地排除了「虚假流量」和「平台泛扶持」两类，但完全无法区分「真实需求深化」与「季节性」与「内容场爆款推动」。** 这三者对行动的含义完全不同（前者值得建 SKU 长期做，中者是窗口期，后者跟本店无关且不可复制），必须靠下面的判据继续拆。

### 2.4 需求真实性判据组（DAT，Demand Authenticity Tests）

设计原则：**这是一组证伪清单，不是加权评分。** 五条判据各自独立返回 `PASS / FAIL / INSUFFICIENT` 三态，**不允许把 INSUFFICIENT 折算成中间分**——那正是「兜底掩盖真实问题」。

---

**DAT-1｜变现效率不劣化（必要条件）**

- 字段：`pay_amt__ratio`（记 G）、`search_show_ucnt__ratio`（记 S），来自 `compass.search.industry_rank` 同一行
- 公式：`E = (1+G)/(1+S)`
- 判定：`E ≥ 1.00` → PASS；`0.97 ≤ E < 1.00` → 弱 PASS（标注）；`E < 0.97` → FAIL
- 数据缺失降级：任一 `__ratio_missing = true`（`unit=6`，平台未就绪）→ **INSUFFICIENT**，不用 0 代替；`__ratio_src ≠ out_period_ratio` → 整条判据作废
- 本例：E = 1.0535 → **PASS**

---

**DAT-2｜超额增长为正（去大盘，必要条件）**

这是整套模型里最有价值的一招：`industry_rank` 返回的是**整张榜**，因此可以算横截面统计量，把「大盘共同因子」减掉——等价于金融里从收益里剥离 beta、只看 alpha。平台扶持和季节共振都是**共同因子**，会让全榜同向移动；真实的单一需求深化是**特异的**。

- 字段：全榜每行的 `pay_amt__ratio`、`search_show_ucnt__ratio`
- 公式（用中位数与 MAD，因为榜单是厚尾分布，均值和标准差会被头部带偏）：
  ```
  excess_G = G_word − median(G_全榜)
  excess_S = S_word − median(S_全榜)
  z_G      = excess_G / (1.4826 × MAD(G_全榜))
  ```
- 判定：`z_G ≥ 1.0` → PASS（特异性增长）；`|z_G| < 1.0` → **NOT_SPECIFIC**（该词只是跟着大盘动，不构成"这个词的机会"）；`z_G ≤ −1.0` → FAIL
- 有效行数不足降级：参与统计的行数 < 20 → **INSUFFICIENT**（MAD 在小样本下不稳）
- ⚠️ 对「袜子」这个 rank=1 的大词，它自己就占了大盘的很大权重，`median` 会被它污染 → 计算榜内中位数时**剔除待测词本身**（leave-one-out）

---

**DAT-3｜持续性（必要条件）**

- 数据源：`compass_snapshots.series(shopId, endpoint, 90)` → 逐期 `stat_key` + `body_sha256`，再 `readRaw(statKey, sha)` 取回原始 body 重新解包
- 公式：连续 k 期内 `G_t > 0` 的期数占比，以及**回撤** `retrace = max(0, (G_peak − G_last)/G_peak)`
- 判定：`k ≥ 3` 且 `G_t > 0` 的期数 ≥ ⌈2k/3⌉ 且 `retrace < 0.5` → PASS；单期尖峰后 `retrace > 0.7` → FAIL（典型热点形态）
- 降级：**可用期数 < 3 → INSUFFICIENT，且这是当前的真实状态**。历史快照要靠时间积累，无法即刻补齐。冷启动期的诚实输出是「持续性未知」，不是「假定持续」
- ⚠️ 跨期比较前必须校验 `stat_key` 的日期口径一致（第 0.3 节）

---

**DAT-4｜广度扩散（加分条件，非必要）**

真需求会在**词族**里扩散（"袜子"涨 → "中筒袜""防臭袜""纯棉袜"一起涨）；单点异动更可能是事件。

- 字段：全榜的 `word` 列表 + 各自 `pay_amt__ratio`
- 构造词族：以待测词为种子做子串/共现匹配（"袜"→ 所有含"袜"的词），得族内词集合 F，`|F| ≥ 5` 才启用
- 公式：`breadth = |{ w ∈ F : G_w > 0 }| / |F|`
- 判定：`breadth ≥ 0.6` → PASS（扩散）；`breadth ≤ 0.3` → 单点异动（记 `ISOLATED_SPIKE`，不是 FAIL，是分型证据）
- 降级：`|F| < 5` → INSUFFICIENT
- ⚠️ 词族匹配是**字符串启发式，不是语义**，会漏掉"棉袜/船袜"之外的表达（如"隐形""地板袜"）。必须把匹配规则明示给用户，允许人工补词，且标注 `breadth` 为**下界**

---

**DAT-5｜非事件驱动（排除性条件）**

- 数据源：`compass.market.hotspot`（抖音热点榜；注意 `data-contract.js` 已实测标注 `diagnosis.compass.video_after_watch` 工具名不副实、打的其实也是 hotspot 端点，两者不要重复计入当作两份独立证据）
- 判定：近 7 日热点榜中存在与待测词/其关联实体的强匹配 → 标 `HYPE_SUSPECT`，需要**延后 2 期复评**才允许出机会分
- 降级：hotspot 返回 `__chart_only` / `__unparsed` / 空 → INSUFFICIENT，**此时不能判"无热点"**（没查到 ≠ 不存在）

---

### 2.5 汇总规则（明确禁止加权求和）

```
必要条件 = { DAT-1, DAT-2, DAT-3 }

任一必要条件 FAIL                        → 需求真实性 = 不成立
任一必要条件 INSUFFICIENT                → 需求真实性 = 待验证（禁止出机会分）
三条必要条件全 PASS 且 DAT-5 未命中      → 需求真实性 = 成立（强）
三条必要条件全 PASS 但 DAT-5 命中        → 需求真实性 = 成立（弱，热点存疑，延后复评）
```

`DAT-4` 只影响下一节的**成因分型**，不参与成立与否的判定。

### 2.6 四种成因的判别矩阵（可直接落地）

| 成因 | `E=(1+G)/(1+S)` | `z_G`（去大盘） | 榜内曝光中位数 | 形态（≥3 期） | `breadth` |
|---|---|---|---|---|---|
| **真实需求深化** | ≥ 1.03 | ≥ 1.0 | 无要求 | 持续，回撤<50% | ≥ 0.6 |
| **蹭热点虚假流量** | < 0.97 | ≥ 1.0（曝光特异高） | 无要求 | 尖峰，次期回撤>70% | ≤ 0.3 |
| **季节性** | ≈ 1（0.97~1.03） | < 1.0（**不特异**） | 同向大幅 | 有日历规律 | ≥ 0.6（**全族共振**） |
| **平台流量扶持** | < 1.0 | < 1.0（**不特异**） | **中位数 S 显著>0 而中位数 G≈0** | 阶跃后走平 | 高（全榜普涨） |
| **内容场/达人推动**（抖音特有） | **≫ 1.1** | ≥ 1.0 | 无要求 | 陡升，取决于投放 | ≤ 0.3（**单点**） |

判别的核心分水岭有两条：
1. **`z_G` 分开"特异 vs 大盘"** → 大盘的两种（季节、平台扶持）与特异的三种（深化、热点、内容场）先分开
2. **`E` 分开"效率提升 vs 效率摊薄"** → 深化/内容场（E>1）与热点/扶持（E<1）分开
3. 剩下「深化 vs 内容场」由 `breadth` 分开：需求深化是**面**（词族共振），内容场爆款是**点**

### 2.7 把这套判据用在用户手上这条真实数据上（诚实结论）

现有的**单条记录**只够跑 DAT-1：

- DAT-1：E = 1.0535 → **PASS**
- DAT-2：需要全榜才能算 `median(G)`。用户提供的是单行 → **INSUFFICIENT**
- DAT-3：需要 ≥3 期快照 → **INSUFFICIENT**
- DAT-4：需要全榜词族 → **INSUFFICIENT**
- DAT-5：未查 hotspot → **INSUFFICIENT**

**汇总判定：需求真实性 = 待验证，禁止出机会分。**

现在能诚实说出口的只有一句：「袜子这个词的成交增速快于搜索曝光增速 6.23pp，方向上不像是被泛流量灌出来的增长。但这一条不能区分真实需求深化、换季、还是某个达人的爆款视频——而这三者对'该不该压货'的答案完全相反。」

另外，`rank=1` 这件事本身是个**减分项而不是加分项**：见 5.6，行业第一大词是无数子需求的加总，它的增长在因果上不可解释，也几乎不可能满足"竞争小"。**真正的机会在长尾，不在 rank 1。**

## 3. 竞争强度

### 3.1 先说一个必须避开的陷阱

`compass.market.shop_rank` 给的是 **top-N 行 + total（榜单总店铺数）**。`total` 是**店铺家数**，不是市场总成交额。

> **绝对禁止**：`CR_n = Σ(top-n 的 pay_amt) / Σ(返回行的 pay_amt)`。
> 这个式子的分母只覆盖 top-N，当 n→N 时结果恒等于 1，会稳定产出「这个市场极度集中」的假结论，而且**不报错、输出看起来完全正常**——正是 `data-contract.js` 开头警告的那类错误。

市场总额 `S_total` **不在返回里**，必须显式承认它是**估计量**，并且估计方法与误差方向要一起输出。

### 3.2 主路径：`index_range` 的分组界（无模型假设，优先级最高）

`compass.market.index_range` 返回的是**档位分布 + 本店所在档**，本质是一张**覆盖全体店铺的直方图**——比只有头部的 `shop_rank` 更适合算集中度，因为它不需要外推。

设第 g 档区间为 `[a_g, b_g]`，档内店铺数 `n_g`（`Σn_g = total`）。

**总额区间（严格界，非估计）：**
```
S_lo = Σ n_g · a_g          S_hi = Σ n_g · b_g
```

**HHI 下界（组内尽可能均等 → 最分散）：**
```
每家取组内几何均值 m_g = √(a_g·b_g)
HHI_lo = Σ n_g · (m_g / S_hi)²      ← 分母取 S_hi 使结果最小
```

**HHI 上界（组内尽可能不均 → 最集中）：**
在「每家的值必须落在 `[a_g, b_g]` 内」的约束下，HHI 在**端点解**取极值：档内让尽可能多的店铺取 `b_g`、其余取 `a_g`。
```
HHI_hi = Σ_g [ k_g·(b_g/S_lo)² + (n_g−k_g)·(a_g/S_lo)² ] ，k_g = n_g（取满上限）
```

**输出规则：`HHI ∈ [HHI_lo, HHI_hi]`。若该区间跨越了判档阈值 → 输出「无法判定集中度」，不取中点。**

- 降级：任一档缺 `n_g` 或档位边界，或最高档是**开区间**（`b_g = ∞`，电商直方图的常态）→ `S_hi = ∞`、`HHI_hi` 不可算 → **只输出 `HHI_lo` 并明确标注"仅下界，真实集中度不低于此"**。这是唯一诚实的做法
- ⚠️ `isCurrentShop` / `tag` 字段属 SHOP_STATE，**不得进入集中度计算**（会把本店信息混进市场结论，违反 `data-contract` 契约）

### 3.3 备用路径：`shop_rank` 的幂律外推（有模型假设，作交叉验证）

电商店铺 GMV 分布通常近似 Zipf / 幂律。用 top-N 拟合斜率，再外推到 `total` 家。

- 字段：`pay_amt`（或 `pay_amt__lower/__upper` 经 `rangeToComparable` 取 `mid`）、排名 `r = 1..N`、`total = N_total`
- 拟合：`ln v_r = ln C − α · ln r`，对 `(ln r, ln v_r)` 做 OLS，得 `α` 与 `R²`
- 广义调和数：`H_n(α) = Σ_{r=1}^{n} r^{−α}`
- 推导结果（闭式）：
  ```
  S_total ≈ C · H_{N_total}(α)
  CR_n    ≈ H_n(α) / H_{N_total}(α)
  HHI     ≈ H_{N_total}(2α) / [H_{N_total}(α)]²
  ```

**误差分析（有方向，且方向对我们有利）：**

真实的长尾通常比幂律**衰减更快**（有限尾），因此外推出的 `S_total` **偏大** → `CR_n` 与 `HHI` 被**系统性低估** → 结论偏向「市场更分散、竞争更激烈」。这是**保守方向的偏差**：不会让用户误以为一个红海市场很好进。这个方向性必须写进输出。

**误差量化（可自检，不靠猜）：** 用 top-⌈N/2⌉ 拟合，预测 rank `⌈N/2⌉+1 .. N`，报 hold-out MAPE。

- `R² ≥ 0.95` 且 `MAPE ≤ 15%` → 外推可用
- `R² ∈ [0.90, 0.95)` 或 `MAPE ∈ (15%, 25%]` → 仅作为 3.2 的交叉验证，不单独出结论
- `R² < 0.90` 或 `MAPE > 25%` → **拒绝外推**，竞争强度回落到 3.2；若 3.2 也不可用 → 竞争强度 = `UNKNOWN` → 机会分拒绝合成

**区间值对 α 的影响（一个好消息）：**
如果平台的区间是**按固定比例分箱**（各行 `upper/lower` 比值近似恒定），那么所有点在 log 空间被**平移同一常数**，`ln C` 变、**`α` 完全不变**。也就是说：**区间只影响规模估计，不影响形状/集中度估计。** 落地前必须实测检查 `upper/lower` 比值的离散度（变异系数 < 0.1 视为恒定）。

若比值不恒定，`α` 的严格界由极端组合给出：
- `α_max`（最集中）：高排名取 `upper`、低排名取 `lower`
- `α_min`（最分散）：高排名取 `lower`、低排名取 `upper`

用「袜子」那行的宽度做个量级感受：`spread = 1e9/7.5e8 = 1.333`，log 空间宽度 `ln(1.333) = 0.288`；若 N=20，`ln r` 跨度 `= ln 20 = 3.00`，噪声/信号 ≈ 0.096 → **α 的不确定性在 ±0.1 量级，可接受**。

### 3.4 但是：HHI 在电商长尾里基本没有判档价值（重要的负面结论）

代入实际量级看一下。取 `N_total = 1000`：

| α | `HHI`（万分制） | `CR_10` |
|---|---|---|
| 0.8 | ≈ 55 | ≈ 25% |
| 1.0 | ≈ 294 | ≈ 39% |
| 1.2 | ≈ 405 | ≈ 51% |

两点结论：

1. **HHI 对 α 极度敏感**：α 从 0.8 到 1.2（一个完全正常的估计不确定范围），HHI 变化 **7 倍**。所以**永远不要报单个 HHI 数字**，只报区间；区间宽到跨档时报「无法判定」。
2. **HHI 绝对判档失效**：反垄断口径的 `<1500 分散 / 1500~2500 中度 / >2500 高度集中` 在这里全部落在「分散」，袜子类目几乎不可能例外。**用 HHI 判"竞争小不小"在电商长尾类目里是无效的指标**——它永远告诉你"分散"，不提供信息量。

HHI 的**唯一有效用法是相对比较**：同一时点跨类目 / 跨词横向比排序，或同一类目跨期比趋势（α 变大 = 头部在集中 = 窗口在关闭）。**禁止用绝对阈值判档。**

### 3.5 真正该用的供给侧指标：进入门槛与可撼动性

对一个非专业运营的小商家，「HHI 是 294」毫无操作含义；「要挤进能被看见的位置需要月成交 X 万」有操作含义。

**M-1｜进入门槛（Entry Threshold）**
- 字段：`compass.market.shop_rank` 第 k 名的 `pay_amt`（区间→`rangeToComparable().mid`，同时保留 `lower/upper`）
- 定义：`Threshold(k) = pay_amt(rank=k)`，取 k = 目标位次（如 total 的 20% 分位）
- 输出：**区间**，如「进前 20% 需月成交 A~B 万」
- 降级：`spread > 4`（`rangeToComparable().reliable === false`）→ 只输出数量级（「十万级」），不输出数字

**M-2｜头部斜率 α（钱是集中在头部还是摊在长尾）**
- α 越小 = 越平摊 = 新进入者越可能吃到；α 越大 = 赢家通吃
- 这是比 HHI 更直接、且**不需要知道 `S_total`** 的量（α 只依赖形状，规模常数 C 与它正交）——**这是全模型里最稳健的供给侧指标**

**M-3｜行业级流量效率（进入的效率门槛）**
- 字段：`compass.market.shop_rank` 的 `pay_ucnt`、`product_show_ucnt`、`pay_amt`
- `行业曝光成交率 = Σ pay_ucnt / Σ product_show_ucnt`（仅用返回行，**必须标注为"头部店铺的"而非"全行业的"**，头部效率通常高于长尾 → 这是一个偏乐观的基准，要说明）
- `行业客单价 AOV = Σ pay_amt / Σ pay_ucnt`（区间 → 结果也是区间）
- 用途：若 AOV 区间显著高于本店能供的价格带，说明「这个市场的钱在高价段」，规模大不代表机会属于你
- 降级：缺 `pay_ucnt` 列 → AOV 不可算 → 输出 `UNKNOWN`，**不用类目均价之类的假设值顶替**

**M-4｜本店可达性（仅展示，不入分）**
`compass.market.index_range` 的 `isCurrentShop` / `tag` 直接给出本店档位，与 M-1 一起可算「还差几档」。但按 `data-contract` 契约，SHOP_STATE 不驱动决策 → **只作为展示层旁注，明确标注「不参与机会分计算」**。

### 3.6 竞争强度输出形态

**输出三档 + 限制因子，不输出小数。** 数据精度不支持两位小数的「竞争指数 0.63」，那是虚假精确。

```
竞争强度 ∈ { 低 / 中 / 高 / UNKNOWN }
判档依据（三选二一致才定档，否则 UNKNOWN）：
  α 的相对分位（在本类目全部词/全部快照中的分位）
  HHI 区间的相对分位（禁用绝对阈值）
  进入门槛相对本店当前 GMV 的倍数（仅当本店 GMV 样本量 ≥100，否则该项弃用）
同时输出「限制因子」：门槛型 / 头部垄断型 / 高客单型 / 未知
```

## 4. 机会分合成

### 4.1 为什么不能是一个数

三条独立的理由：

1. **输入是区间**（`pay_amt__lower/__upper`），区间经过非线性运算后宽度会放大
2. **有些输入是 `UNKNOWN` 而不是"中间值"**——把 UNKNOWN 折算成 0.5 分再加权，正是「兜底掩盖真实问题」
3. **加权求和会掩盖单项否决**：需求真实性 FAIL 的市场，无论竞争多小都不是机会；加权分会给它一个"还行"的中等分

### 4.2 输出形态：门控 + 九宫格 + 定档概率

**第一关（门控，二值）—— 需求真实性门**

```
DAT 汇总 = 不成立            → 输出 D 档「无机会」，流程结束
DAT 汇总 = 待验证/INSUFFICIENT → 输出 REFUSE「数据不足，拒绝给分」+ 缺什么、怎么补
DAT 汇总 = 成立              → 进入第二关
```

**第二关（定档）—— GE-McKinsey 九宫格**

- 纵轴 **需求强度**：由 `pay_amt` 的区间量级分位（规模）× `excess_G`（去大盘增速）合成，**分三档：高/中/低**
- 横轴 **竞争强度**：第 3.6 节输出，**三档：低/中/高**
- 九宫格定档：`A（强机会：需求高×竞争低）/ B / C / D`

**第三关（可执行性，只标注不入分）**：本店档位差、供应链、运费模板可行性——契约不允许 SHOP_STATE 驱动决策，且运费模板按用户硬约束 #5 不能写死。

**第四关（不确定性传播）—— 定档概率**

不做正态假设的蒙特卡洛，而是做**端点枚举**（确定性、可复现、可审计）：

- 每个区间字段取 `{lower, mid, upper}` 三值
- 若参与合成的区间字段有 m 个（实际 m ≤ 4），枚举 `3^m ≤ 81` 种组合，全跑一遍定档
- 输出**格分布**，如 `{ B: 0.72, C: 0.28 }`

**定档规则：**
```
最高格概率 ≥ 0.60  → 定该档，附「另有 X% 落在 Y 档」
最高格概率 < 0.60  → 输出「跨档，不定档」+ 候选档 + 是哪个输入的宽度导致跨档
```

最后一句很重要：它把「不确定」变成**可行动的**——告诉用户"是 `pay_amt` 的区间太宽（7.5亿~10亿）导致定不了档，多抓 3 期快照能收窄"。

**第五关（置信等级）**，与档位**分开输出**、不合并：

| 置信 | 条件（全满足） |
|---|---|
| **高** | DAT 五条全 PASS；快照期数 ≥ 6；所有区间 `reliable=true`（spread ≤ 4）；竞争强度走 3.2 主路径且档位闭合；定档概率 ≥ 0.8 |
| **中** | DAT 必要三条 PASS；快照期数 ≥ 3；竞争强度可定档；定档概率 ≥ 0.6 |
| **低** | 满足门控但上述任一不满足，且未触发拒绝条件 |

### 4.3 拒绝给分的硬条件（任一命中即 REFUSE）

这是本设计对用户硬约束 #1/#3/#4 的集中落实。**REFUSE 是一个正常输出，不是错误。**

| # | 条件 | 检测字段 |
|---|---|---|
| R1 | `__ratio` 语义未通过第 0 节校验 | `__ratio_src` / `__ratio_unit` 缺失或不符 |
| R2 | 增长率未就绪 | `__ratio_missing === true`（`unit=6`） |
| R3 | 解包失败或平台空数据 | `__chart_only` / `__unparsed` / `platform_empty` |
| R4 | 数据不可驱动决策 | `_meta.canDriveDecision === false` |
| R5 | 输入含平台结论型数据 | 工具 `advisory === true`（如 `product.recommend_optimized`、`search.batch_tool`、`diagnosis`、`search_diagnosis`）——按硬约束 #1 一律判 SUSPECT 拒绝 |
| R6 | 店内统计量样本不足 | `scope === shop_metric` 且 `sampleSize < 100` |
| R7 | 区间过宽 | `rangeToComparable().reliable === false`（spread > 4）**且**该字段参与定档 |
| R8 | 无趋势 | 可用快照期数 < 2（连环比都没有第二个点交叉验证） |
| R9 | 竞争强度不可估 | 3.2 分组界不可算 **且** 3.3 拟合 `R² < 0.90` |
| R10 | 定档跨度过大 | 定档概率最高格 < 0.60 → 降级为「跨档，不定档」（这是软拒绝：给候选档，不给单一结论） |
| R11 | 身份不符 | `shop_registry` 校验失败（profile 名 ≠ 实测 cookie 的 shopId）→ 全部数据作废 |

**REFUSE 的输出必须包含**：命中了哪条、缺哪个字段、**要补什么才能出分**（如"再抓 2 期 industry_rank"）。拒绝而不说怎么解锁，等于把问题丢回给用户。

### 4.4 存证与可复现（必需）

阈值会随标定而改，历史结论必须能追溯。每个机会分输出必须落：**输入快照的 `body_sha256` 列表**（`compass_snapshots` 已经是内容寻址 + gzip，直接复用）+ **模型版本号** + **阈值集版本号** + **命中的判据与拒绝条件**。没有这个，三个月后没人能解释"当时为什么判了 B 档"。

## 5. 归因：一个词为什么突然暴涨

### 5.1 Step 0 — 触发（什么叫"暴涨"）

不用固定阈值，用**榜内稳健 z**（榜单是厚尾，均值/标准差会被头部带偏）：

```
z_G = (G_word − median(G_全榜, leave-one-out)) / (1.4826 × MAD(G_全榜))
触发条件：z_G ≥ 2.0
```
- 降级：有效行数 < 20 → 不触发归因（MAD 不稳），输出「样本不足以判断异常」

### 5.2 Step 1 — 增长分解：量 vs 效（零假设，直接可算）

```
ln(1+G) = ln(1+S) + ln(E)
流量贡献占比 = ln(1+S) / ln(1+G)
效率贡献占比 = ln(E)   / ln(1+G)
```

本例：`ln(1.2262)=0.2039`，`ln(1.1639)=0.1518`，`ln(1.0535)=0.0521`
→ **流量贡献 74.4%，效率贡献 25.6%**。

这是第一层归因，**不需要任何假设**，且已经能回答一半问题：这次增长主要是「更多人来了」而不是「买得更狠了」。

- 降级：`G ≤ 0` 或 `S ≤ −1` → 对数不可算 → 改用线性近似并标注；`__ratio_missing` → 整步 INSUFFICIENT

### 5.3 Step 2 — 共同因子剥离（先判"是不是这个词的事"）

```
特异增长 excess_G = G_word − median(G_全榜)
大盘增长 base_G   = median(G_全榜)
特异占比 = excess_G / G_word
```
**若 `|z_G| < 1.0`（特异占比低）→ 归因结论直接是：「这不是这个词的故事，是大盘/平台层面的移动」**，流程转向大盘归因（季节 or 平台扶持，见 5.4 的 D/E 两型），**不再对该词做单独解释**。

这一步能淘汰掉大量误判，成本极低，应该放在最前面。

### 5.4 Step 3 — 成因分型（仅在特异性显著时执行）

每一型给出**可检验的印记（signature）**，而不是感觉：

| 型 | 印记（全部可算） | 用到的数据 |
|---|---|---|
| **A 热点/事件** | hotspot 榜时间对齐（热点出现日领先 0~3 天）+ `E < 1`（泛流量摊薄）+ 单期尖峰、次期回撤 >70% + `breadth ≤ 0.3` | `compass.market.hotspot` + 快照序列 |
| **B 季节/日历** | 特异性不显著 + 词族共振 `breadth ≥ 0.6` + `E ≈ 1` + 与去年同期同向 | 全榜 + 历史序列（**首年无同比 → 只能给"疑似"**） |
| **C 内容场/达人推动**（抖音特有） | `G ≫ 0` 而 `S ≈ 0 或 <0`（成交涨、搜索不涨）+ `E ≫ 1.1` + `breadth ≤ 0.3` | `industry_rank` 两个 ratio + 词族 |
| **D 价格驱动** | `pay_ucnt` 大涨而 `AOV = pay_amt/pay_ucnt` 下降 | 需要 `pay_ucnt` 列，**搜索词榜通常没有 → 多数情况不可分辨** |
| **E 平台流量扶持/算法改版** | **榜内 `median(S) ≫ 0` 而 `median(G) ≈ 0`**（全榜曝光普涨、成交不涨）+ 阶跃形态 | 全榜横截面 |

**判别顺序**：先 Step 2 分「特异 / 大盘」，大盘侧只在 B/E 中选（用 `median(S)` vs `median(G)` 的背离方向区分）；特异侧在 A/C/D 中选（用 `E` 与 `S` 的方向区分：`S↑E↓`→A，`S平E↑`→C，需 `pay_ucnt` 才能到 D）。

### 5.5 Step 4 — 交叉验证与置信

**规则：至少 2 个相互独立的印记指向同一型，才允许输出结论。** 否则输出「候选成因清单 + 无法排他」。

注意独立性检查：`E` 与 `S` 不独立（`E` 由 `G,S` 构成），不能算两个证据。真正独立的证据源是：① `industry_rank` 的比率关系、② 快照时间序列的形态、③ hotspot 榜的外部事件、④ 词族横截面。

### 5.6 Step 5 — 明确承认"归因不了"的条件

| # | 条件 | 为什么必须承认 |
|---|---|---|
| U1 | 可用期数 < 3 | 看不到形态，尖峰与持续增长无法区分 |
| U2 | `z_G < 1.0`（特异性不显著） | 信噪比不足，任何"原因"都是过度解读 |
| U3 | 缺 `pay_ucnt` / 点击类字段 | 量价拆不开，D 型永远不可分辨（**这是常态，不是异常**） |
| U4 | 多型印记同时命中且互斥 | 例如换季窗口内恰好出现热点，二者叠加不可分离 |
| U5 | **待测词是宽泛大词**（`rank ≤ 3` 或占大盘份额过高） | **聚合掩盖**：「袜子」的增长是成百上千个子需求的加总，任何单一"原因"都是错的。**必须下钻到长尾词才谈得上因果**。对 rank=1 的"袜子"做归因是无意义的 |
| U6 | 检测到 `CALIBRATION_BREAK`（2.2 节口径阶跃） | 增长可能是统计口径变了，不是市场变了 |

### 5.7 归因的真正价值：它决定行动是否可复制

用户说"这个价值很高"是对的，但价值不在于知道原因本身，而在于**不同的原因对应完全不同的行动**。归因输出必须**带上行动映射**，否则用户拿到"这是热点驱动"不知道该干什么：

| 成因 | 是否可持续 | 行动含义 |
|---|---|---|
| A 热点/事件 | 否，天级 | **不压货、不建 SKU**。若已有现货可短期跟标题；等 2 期回落确认后再评估 |
| B 季节 | 是，但有窗口 | 按日历提前备货，**窗口结束前清库存**；利润阶梯按窗口长度倒推 |
| C 内容场/达人推动 | 取决于别人，与本店无关 | **最容易误判成机会**。需求可能只属于那个达人的粉丝。除非能自己做内容，否则不跟 |
| D 价格驱动 | 否，是价格战 | 检查是否会击穿本店利润底线；`smart_pricing_engine` 的下限不得为此让步 |
| E 平台扶持 | 窗口期 | **抢曝光但不扩产能**。扶持撤走时流量会一起走 |
| 真实需求深化 | 是 | **这才是值得建 SKU、进 `ops_engine` 选品评估的那一类** |

### 5.8 输出结构（固定格式，便于人工确认）

按硬约束 #2「AI 只给建议，人工确认」，归因结论必须是**可反驳的**，因此固定五段：

```
成因假设：      C 型（内容场推动），置信 中
支持证据：      ① E=1.21 远超榜内中位数  ② breadth=0.17 单点  （2 个独立源）
反证 / 未排除：  未查 hotspot（DAT-5 INSUFFICIENT），A 型未能排除
推翻它需要什么： hotspot 榜近 7 日无匹配 → 排除 A；再 2 期 G 维持 → 排除 A
建议动作：      不压货，观察 2 期；期间不做 SKU 投入
```

## 6. 阈值的诚实性声明与标定路径

**本文给出的所有数字阈值（`E≥1.03`、`z≥1.0/2.0`、`breadth 0.6/0.3`、`R²≥0.90`、`MAPE≤25%`、`spread≤4`、定档概率 `0.60`、快照期数 `3/6`）是先验起点，不是实证标定值。**

除了两个有外部依据的：
- `spread ≤ 4` 来自 `data-contract.rangeToComparable` 的既有 `reliable` 判据（沿用，不另起）
- `sampleSize ≥ 100` 来自 `data-contract.MIN_SAMPLE_FOR_METRIC`（沿用）

**首轮使用规则：只用相对排序，不用绝对阈值。** 即：把候选词/候选类目按 `E`、`z_G`、`α` 排序取头部，而不是拿 `E ≥ 1.03` 卡线——排序对阈值不敏感，卡线对阈值极敏感。

**标定路径**：积累 ≥8 期快照后，用本店实际发布结果回标——把「判为 A/B 档的词」与「实际上架后 30 天的成交」做对照，用 ROC 反推每个阈值。在此之前，**模型输出里必须带一行「阈值未标定，仅供相对排序」**。

## 7. 与现有资产的接口约束

- 机会度量模型是**选品的前置**，输出（词 + 档位 + 置信 + 成因 + 反证）喂给 `src/ops_engine.py` 的选品评估，**不改变 `ops_engine` 的 `AI_POLICY`**：本模型全部是本地规则计算，不调外部 AI、不调抖店官方 API
- 所有市场数据经 `lib/dispatcher.js` → `data-contract.describe()`，`canDriveDecision === false` 的数据**在模型入口就丢弃**，不进入任何公式（而不是"进来了再降权"）
- 所有写操作（上架、改价、改标题）走 `lib/approval-gate.js`，本模型**只产出建议，不触发任何写**
- 本模型**不读写运费模板**，也不对运费做任何假设——按硬约束 #5，运费模板是店铺相关配置，只能作为可执行性旁注由人工填入
