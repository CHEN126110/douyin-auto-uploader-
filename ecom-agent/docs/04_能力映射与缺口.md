### 1.4 利润测算

先说事实：**两个仓库目前零互相引用** —— 全仓 grep `D:/抖店` / `Desktop/2.1` 在对方代码里均无命中。这是全新设计，没有历史包袱。

### 3.1 文件交换的具体形态

**交换目录**：`D:\抖店\data\exchange\`（放在生产者本地盘，避免跨盘写权限与中文路径转义问题）
```
exchange/
  opportunity/<YYYY-MM-DD>/industry_rank.json      D:\抖店 写，2.1 读
  shop_metrics/<YYYY-MM-DD>.json                   D:\抖店 写，2.1 读
  inbox/publish_result_<record_id>.json            2.1   写，D:\抖店 读
```

**内容契约**：每个文件必带信封，直接沿用 `dispatcher.call` 的返回结构，**不做二次加工**：
```json
{ "contract_version": 1, "tool_id": "...", "shop_id": "...", "stat_key": "W:2026-08-20_2026-08-26",
  "produced_at": "...", "status": "ok|empty|error",
  "_meta": { "scope": "...", "canDriveDecision": true, "gateReason": null, "rows": 20 },
  "data": { ... } }
```

**规则**（每条都有对应的既有实践支撑）：
1. **写入原子化**：先写 `*.tmp` 再 `rename`（NTFS 同盘 rename 原子）。绝不允许读到半截 JSON。
2. **失败也必须写文件**（`status:"error"`）。这条直接抄 `lib/compass_snapshots.js:12` 的原则："失败也入库，否则『某天没数据』与『某天没抓』无法区分，曲线断裂会被误判成暴跌。" 文件交换里同样成立：没有 error 文件，2.1 会把"抓失败"读成"今天还没生产"。
3. **消费方必须校验 `shop_id`**，与自己要操作的店铺不一致就中断退出。这正是 1.6 指出的 `2.1` 侧缺失的那道闸，文件交换是补它的最佳时机。
4. **消费方只信 `_meta.canDriveDecision`**，为 false 的数据一律不进决策路径（理由见下条局限 3）。
5. 并发：单写者 + 单读者，用 `<name>.lock` **目录锁**（`mkdir` 是原子的）即可。不要用 flock —— Node 与 Python 语义不一致。
6. 编码：两侧统一 `pathlib.Path` + 显式 `encoding='utf-8'`。

### 3.2 局限（必须写清，不能假装它够用）

1. **没有请求-响应。** 文件交换是单向投递。「选品节点想临时查这个词现在的数据」做不到，只能降级用昨天的快照。DAG 里凡是需要即时问询的边都会被迫变成"读上一批"。
2. **失败反馈有延迟。** compass 会话 cookie 过期（`lib/compass_cookie.js`）后，2.1 要等读到 error 文件才知道；靠规则 2 缓解，但缓解不掉时间窗。
3. **口径无人守。** `_meta.scope / canDriveDecision` 是 `D:\抖店` 运行时算的，写进文件就是死值。2.1 读到时**不会重新过 `canDrivedecision`** —— Python 侧根本没有这套契约代码。要么在 2.1 重写一份（必然漂移），要么只信文件里的布尔值。建议后者，并用 `contract_version` 卡版本：版本不匹配直接拒绝，不做兼容转换。
4. **跨盘符 + 中文路径。** `D:\抖店` 含中文；`2.1` 的 sidecar 打包成 `python-backend.exe` 后（`python-backend.spec`），在非 UTF-8 codepage 下路径处理有风险。`app.py` 已用 `_SafeConsoleStream` 包 stdout，但文件路径层没有统一约定。
5. **不含调度。** 谁触发 `daily_snapshot.js`？`D:\抖店\package.json:14` 只有 `npm run snapshot`，没有定时器。文件交换本身解决不了这个。

### 3.3 建议的补充（不违背"文件交换"定调）

`2.1` 的 sidecar 已在 `127.0.0.1:5001` 提供 HTTP，且 `/api/ops/sync-shop-metrics`(`app.py:2006`)、`/api/ops/profit-ladder-to-500`(`app.py:1970`)、`/api/ops/evaluate-product`(`app.py:1626`) 这类接口**接受纯 JSON、无状态、不依赖前端**。`D:\抖店` 用 Node 原生 `http` 直接 POST 过去，立刻就有了请求-响应，绕开局限 1 和 2。

## 5. 机会打分公式（节点 2 —— 本切片唯一新建的计算）

三个分量全部只用 MARKET 作用域字段，逐一说明取自哪个字段、数据不足时怎么办：

| 分量 | 用哪个字段算 | 数据不足时 |
|---|---|---|
| **需求量级** `demand` | `rangeToComparable(metrics.search_show_ucnt.extra_value.lower.value, ...upper.value).mid`（几何均值，`data-contract.js:237`） | 同时保留 `.reliable`（`upper/lower ≤ 4`）。`reliable=false` → 只进"待观察"，不进候选。`detectPrecision`(`:252`) 返回 `UNKNOWN`（无 `extra_value`）→ **丢弃该词，不猜** |
| **趋势** `trend` | `metrics.search_show_ucnt.out_period_ratio.value`（环比，实测存在） | 缺失标 `null`，**不按 0 处理**。0 = "持平"，null = "不知道"，两者不能混 |
| **变现密度** `monetization` | `rangeToComparable(metrics.pay_amt...).mid / demand` | 任一端 `reliable=false` → 只输出区间，不输出比值 |

**排序方式：分层筛，不做加权求和。** 权重是拍脑袋的，加权会把分量之间的矛盾（高需求 + 负趋势）平均成一个看不出问题的数。
